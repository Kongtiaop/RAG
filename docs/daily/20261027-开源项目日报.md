## 1. Flint（microsoft/flint-chart）— AI 时代的图表中间语言

- **GitHub**: https://github.com/microsoft/flint-chart
- **定位**: 微软出品的"可视化中间语言"——用一份人类可读、可编辑的图表规范（spec）描述图表，编译到 Vega-Lite、ECharts、Chart.js 或 Plotly 等多种渲染后端。核心卖点是让 AI Agent 把"简单可编辑的图表 spec"变成精美的成品图表，而不是手写坐标轴、比例尺和布局代码。

### 核心功能亮点
- 一份 spec 多端编译：同一份图表定义可输出到 4 种主流可视化引擎，避免厂商锁定
- 为 AI Agent 设计：spec 简洁、token 友好，天然适合作为 Agent 生成图表的输出格式
- 人类可编辑：生成结果不是黑盒，开发者可直接调整 spec 迭代
- 已达 1.0 里程碑（2026-10-21 发布），API 进入稳定期

### 技术栈
TypeScript；编译目标覆盖 Vega-Lite / ECharts / Chart.js / Plotly。

|---|---|

| Open Issues | 38 |

### 适用场景
- 在 LLM 应用 / Agent 中做"数据→图表"生成，替代让模型直接手写 ECharts 配置
- 需要图表 spec 跨引擎迁移或长期可维护的数据产品
- 报表平台中把图表定义作为版本化资产存储

### 可靠性评估
**高**。微软官方项目，昨日仍有推送，38 个 open issue 对新项目而言响应面健康；1.0 已发，API 承诺稳定；MIT 协议无商用障碍。风险点：23 位贡献者规模尚小，主要依赖微软团队驱动，社区生态还在早期。

### 上手建议
1. 从官方 README 的 spec 示例入手，先手写 2~3 个基础图表感受语法
2. 若已有 ECharts/Chart.js 存量代码，可对比编译输出评估迁移成本
3. 在 Agent 工作流中把 Flint spec 作为模型的 JSON 输出约束（schema 校验）再编译渲染，比直接生成渲染代码稳定得多

## 2. Pele（obsidianmd/pele）— 本月增速最猛的 Mermaid 渲染器

- **GitHub**: https://github.com/obsidianmd/pele
- **定位**: Obsidian 官方团队（作者 kepano，即 Obsidian CEO Stephan Ango）出品的 Mermaid→SVG 渲染库，主打**极致速度、零运行时依赖**。"比 Mermaid 官方渲染快一个量级"是它的核心卖点，目标是把 Mermaid 图表渲染做成浏览器里的"瞬时"体验。

### 核心功能亮点
- 零运行时依赖：渲染产物为纯 SVG，可嵌入任何环境
- 速度为先：针对大规模文档（如 Obsidian 库内成百上千张图）场景优化
- 出自 Obsidian 团队，已用于 Obsidian 生产环境，真实负载验证充分
- 发布节奏极快：3 周内迭代到 v1.12.0（2026-10-26 发布）

### 技术栈
TypeScript，输出标准 SVG。

- 静态站点构建（SSG）时预渲染 Mermaid 为 SVG，消除客户端运行时开销
- 想要 Mermaid 语法但嫌弃官方渲染包体积与速度的团队

### 可靠性评估
**高（但很年轻）**。3 周 3,627★ 是典型的爆款曲线；Open Issues 仅 4 个说明维护响应极快；背后是 Obsidian 这家有长期商业动机维护文档工具链的公司，且它自己就在用。风险点：v1.x 早期，API 与支持的图表类型覆盖面尚未冻结，生产使用建议锁版本。

### 上手建议
1. 先用 `npm` 安装跑一遍你现有的 Mermaid 文档全集，对比渲染耗时与输出兼容性
2. 关注它对 Mermaid 语法子集的覆盖范围（不支持的自研图先留官方渲染兜底）
3. 适合作为 SSG 插件集成；API 未冻结期用精确版本号锁依赖

## 3. Vela（LuxAlgo/Vela）— WebGL2 金融图表开源核心

- **GitHub**: https://github.com/LuxAlgo/Vela
- **定位**: 交易工具公司 LuxAlgo 开源的金融图表库核心——headless 架构 + 原生 WebGL2 渲染（Canvas2D 降级兜底）+ 插件 SDK，面向"浏览器里做专业级金融图表"的场景。TradingView Lightweight Charts 的开源替代选项之一。

### 核心功能亮点
- WebGL2 渲染：大数据量 K 线/指标的高帧率滚动与缩放，Canvas2D 自动降级
- Headless 核心 + 插件 SDK：自定义数据源、脚本引擎、渲染器均可替换，不锁 UI
- 金融场景原生：OHLC、时间序列、指标叠加等开箱即用
- 商业公司持续输血：LuxAlgo 以此为核心做商业产品，维护动力强

### 技术栈
TypeScript，WebGL2（Canvas2D fallback），无框架绑定的 headless 核心。

- 需要渲染数万根 K 线 + 实时推送不掉帧的场景（Canvas 方案通常扛不住）
- 想在图表内嵌自定义指标/脚本的量化工具

### 可靠性评估
**中高**。商业公司开源核心模式保证了持续投入（昨日仍在推送，周内刚发 v0.9.0）；Apache-2.0 宽松协议。风险点：v0.x 阶段，API 未冻结；11 位贡献者主要来自 LuxAlgo 内部；Fork/Star 比偏高说明围观多、沉淀少，生产采用前建议先做压力实测。

### 上手建议
1. 先跑官方 demo 验证你的数据量级下的帧率表现，再决定替换现有图表库
2. headless 架构意味着 UI 层要自己包（或参考示例），预留 1~2 天集成成本
3. v0.x 阶段跟随 release 节奏升级，不要追 main 分支

## 4. Perspective（perspective-dev/perspective）— 流式大数据的交互分析引擎

- **GitHub**: https://github.com/perspective-dev/perspective
- **定位**: 基于 Rust + WebAssembly 的浏览器端交互分析与可视化引擎——把 Arrow 数据表直接放进浏览器做查询、透视、流式更新，再配上图表组件，专为"大/流式数据集"设计。原属 FINOS 基金会（金融科技开源），近期已迁移至 perspective-dev 组织独立运作。

### 核心功能亮点
- Rust/WASM 内核：浏览器内秒级处理百万行级数据，无需后端往返
- 流式优先：为实时推送数据设计（行情、日志、IoT），支持增量更新与行历史
- 完整组件族：数据表、透视表、图表三层组件，可嵌入 React/Vue 等框架
- 老牌项目持续进化：2017 年创建，至今仍在活跃发版

### 技术栈
Rust（编译为 WASM）+ JavaScript/TypeScript 前端组件；数据格式为 Apache Arrow。

### 适用场景
- 实时监控大屏 / 金融终端：流式数据直接在浏览器聚合透视
- 数据密集型 SaaS：把"筛选-透视-出图"整条链路搬到客户端，省后端查询成本
- 需要离线可用的本地数据分析界面（WASM 可完全前端化）

### 可靠性评估
**高**。8 年项目，89 位贡献者，v5.x 成熟版本线，周内刚发 v5.6.1，open issue 仅 33 个对万星项目而言极健康；FINOS 基金会出身、多家金融机构生产验证；Apache-2.0。风险点：Rust/WASM 工具链让二次开发门槛偏高，好在多数场景只用 npm 包不需碰内核。

### 上手建议
1. 用官方 `@perspective-dev/viewer` + 自己的一份 Arrow/CSV 数据快速起一个透视页面
2. 流式场景先用 WebSocket + `update()` 接口验证增量更新体验
3. 注意组织已从 finos 迁移到 perspective-dev，旧链接/旧包名引用需更新

## 5. Umami（umami-software/umami）— 隐私优先的开源网站分析平台

- **GitHub**: https://github.com/umami-software/umami
- **定位**: 自托管、隐私优先的 Web/产品分析平台——流量、 campaign、行为、转化、收入一个面板全搞定，不依赖 Cookie、不做跨站追踪，是 Google Analytics 的主流开源替代品之一。

### 核心功能亮点
- 无 Cookie、合规友好：天然降低 GDPR/隐私合规负担，访客无需授权提示
- 自托管数据自主：数据落在自己的数据库里，不经过第三方
- 完整分析面板：实时访客、漏斗、留存、事件追踪、UTM 归因，覆盖产品分析诉求
- 轻量部署：单实例 + PostgreSQL/MySQL 即可运行，资源占用小

### 技术栈
TypeScript / Next.js + Prisma，支持 PostgreSQL 与 MySQL，Docker 一键部署。

- 给内网/私有化部署的系统配一个轻量访问分析

### 可靠性评估
**高**。2020 年至今持续维护，403 位贡献者、8.4k Fork 构成成熟社区；本周刚发 v3.4.1，issue 关闭节奏健康；MIT 协议 + 有官方云服务商业支撑，长期维护无虞。风险点：142 个 open issue 数量在今日名单中最多，属大规模用户基数下的正常水位，但小众 feature 的修复优先级可能靠后。

2. 从"页面浏览 + 事件追踪"两件事开始，漏斗与留存功能在 UI 的 Reports 区
3. 生产环境务必改默认管理员密码并配置反向代理 + HTTPS
