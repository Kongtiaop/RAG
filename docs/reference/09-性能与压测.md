## 1. 压测环境与方法

### 1.1 本地单节点基准环境

- 硬件：HP123（Ryzen 9 8945HX / 32GB / RTX 5060 8GB），服务跑在 Docker
- API：`http://127.0.0.1:8010`（初期单 uvicorn worker，后切 4 worker）
- 数据库：PostgreSQL 16.14（5433）、Redis（6380）
- 压测工具：自研异步压测脚本 `scripts/loadtest_api.py`（基于 httpx，100% Python，无第三方压测依赖）

定位说明：这是**本地单节点基准**，不是生产集群压测。结论口径是"单节点正确性已验证、性能有明确瓶颈与优化方向"。

### 1.2 压测纪律（Runbook 中的硬性护栏）

生产（p0，4C8G / 8010 / 4-worker）压测 Runbook 明确了几条纪律：

1. **先钉住环境事实再压**：压测前必须确认被测实例就是目标配置（worker 数、代码版本、端口归属）。`docker-compose.yml` 与 `docker-compose.p0.yml` 共享 8010 端口，极易压到旧实例。
2. **未执行的数字不记为结论**：Runbook 只提供待执行命令，服务器真实输出回填前，任何数值不得写成"结论"。
3. **阶梯并发**：read 基线从并发 20 → 50 → 100 逐级放大，每级观察 `RPS/P50/P95/错误率`，同时另一终端用 `docker stats` 观测 CPU。
4. **write 只用幂等安全的接口**：优先选无真实订单副作用、可重复执行、幂等可验证的接口（如客户偏好持久化）；NL order draft 会持续写 draft 行、确认后落 Order，不适合并发海量。write 阶段先 1~2 并发确认幂等语义，再决定是否放大。
5. **不压第三方依赖**：LLM/advisor-ask 不做拉满——第三方 DashScope 配额才是瓶颈，压它语义不干净。

实例确证命令示例：

```bash
# 确认 8010 归属 p0 4-worker 实例
docker inspect wealth-p0-api-1 --format 'image={{.Image}}\ncmd={{.Config.Cmd}}'
docker compose -p p0 ps --format '{{.Name}}'

# 确认认证链路可用
curl -s -X POST http://127.0.0.1:8010/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"customer_demo","password":"Demo@2026Customer"}'
```

### 1.3 一次经典的"测错实例"事故

早期一轮"多 worker 无提升"的结论**不成立**——当时占用 8010 端口的是 p0 compose 的旧单 worker 容器（`wealth-p0-api-1`，创建于 3 小时前、未带 `--workers 4` 与新代码），压测打的全是它，而不是真正的 4-worker 实例。修正后：真实 4 worker + 两项优化，吞吐提升 2.5~4.3 倍。

> 教训：压测前必须确认被测实例就是目标配置。两个 compose 共享同一端口时，"在压谁"比"怎么压"更容易出错。

| 场景 | 并发 | 样本 | RPS | P50 | P95 | P99 | max | 错误 |
|---|---|---|---|---|---|---|---|---|
| 混合（health+me+recommendations） | 100 | 5075 | **625** | **98ms** | 482ms | 786ms | 974ms | 0 |
| health-only | 200 | 6463 | **1052** | 162ms | **306ms** | 923ms | 1279ms | 0 |

**提升幅度**

| 场景 | RPS 提升 | 延迟改善 |
|---|---|---|
| 混合 100 并发 | 151 → 625（**4.1x**） | P50 606 → 98ms |
| health 200 并发 | 421 → 1052（**2.5x**） | P95 1517 → 306ms |
| profile/me 50 并发 | 95 → 406（**4.3x**） | P50 457 → 46ms |

所有场景 **0 错误**——并发下幂等/认证/DB 链路不崩、不超时出错。高并发下的 P95 劣化属于**容量性劣化**（请求排队等待），不是正确性错误。

### 2.2 数据量扩展：5k → 50k 不退化

通过 `scripts/loadtest_seed_large.py` 向 PG 灌入 **50,000** 个合成客户（users + profile + asset + risk），实测查询延迟：

| 查询 | 规模 | P50 | P95 |
|---|---|---|---|
| `GROUP BY customer_tier`（扫描 customer_profile） | 50k | 9.06ms | 11.97ms |
| `avg(total_asset)` 聚合 | 50k | 10.91ms | — |
| PK join 点查（profile+asset） | 50k | 0.44ms | 0.96ms |

结论：数据量从 5k → 50k，查询不退化——扫描类 10ms 级、索引点查 sub-ms，执行计划无劣化迹象（索引被正确使用）。

### 2.3 强幂等性（资金安全）验证

系统"安全"的核心是**强幂等性**（防重复下单/防资金重复副作用），机制为三层：**唯一索引兜底 + 行锁 + 确定性幂等键**。并发下验证通过：

- 并发幂等下单（TEST-0091/0092）：30 请求 0 失败，同一幂等键只产生 1 单，成功 201 / 竞争 409，无重复订单、无 500。
- MySQL 并发幂等（TEST-0100）：5 并发 → 仅 1 创建，其余 4 撞唯一索引抛 IntegrityError。
- 同一幂等键并发 HTTP 竞态（TEST-0203）：并发契约通过。

即系统在**吞吐**（优化后数倍提升）与**强幂等/数据一致性**（并发 0 重复）两个维度都有实测支撑。

### 2.4 容量外推：50k 用户适配（工程估算，非实测）

按 50k 用户、20% DAU（≈10k 日活）、每人每天 30 请求、峰值小时占日流量 40% 且突发 ×3 反推，峰值需求 ≈ **100 req/s**。

| 配置 | 估算混合 RPS | 相对 50k 需求 |
|---|---|---|
| 本地单节点（4 worker） | ~600（实测） | ~6x 富余 |
| 生产单节点（8 vCPU / 8 worker / SSD） | ~1200-2000（估算） | 12-20x 富余 |
| 生产 2-3 节点 + LB | ~2500-5000+（估算） | 25-50x 富余 |

边界说明：估算基于"吞吐 ≈ 核数 × 单核效率、瓶颈在 CPU/DB"，误差可 ±50%；生产会引入网络 RTT、TLS、真实客户端分布、更大数据量，实际值低于估算。**结论：对 50k 用户规模，单节点即足够且有富余。**

## 3. 瓶颈洞察与架构修正

### 3.1 瓶颈定位链

1. **单 uvicorn worker 是最大瓶颈**。启动命令未带 `--workers`，即单进程单事件循环：DB 型端点 ~90-150 RPS，health 在 200 并发即饱和 ~420 RPS，高并发下 P95 因排队/事件循环抢占明显劣化。
2. **health 端点不是"纯健康检查"**。`/api/v1/health` 走 `HealthService`，每次请求都探测 PostgreSQL + Redis 连通性，并不零成本，200 并发 P95 达 1.5s。
3. **`profile/me` 每次请求约 10 次串行 DB 往返（N+1 式）**，这是单请求 ~117ms 的根因：
   - 鉴权 `current_user`：从 DB 重载用户 + 角色 + 权限（selectinload）≈ 2-3 次；
   - `uow.profiles.get`：1 次；
   - `AssetSummaryService.latest_or_derived` → `calculate(revalue=True)`：`revalue_user` 重估持仓（读+写，最贵），加 account/holdings/assets 查询 ≈ 5-6 次，且 `calculate` 在快照查询之前**无条件执行**——即使当日快照已存在也每次全量重算；
   - 持仓列表：1 次；
   - `_risk_operation_for_user`（account + risk_alert）：2 次。
4. **recommendations 每次跑全产品适当性计算**：对全部在售产品执行 `SuitabilityService`，天然较重，30 并发即 ~94 RPS、P50 283ms。

关键判断：**瓶颈在串行 DB 往返，不在 CPU 计算**——这也是单纯加 `--workers` 提升有限的原因。

### 3.2 优化动作（按杠杆排序）

| 优先级 | 动作 | 预期收益 |
|---|---|---|
| P0 | 减少每请求 DB 往返 / 缓存鉴权（`profile/me` 单请求 ≈117ms 主要来自多次 DB + 鉴权重载用户） | 直接压下单请求延迟，最有效 |
| P0 | health 减负：去掉每次 PG/Redis ping，或降为进程存活检查 | health 从 ~420 RPS 上限释放 |
| P1 | recommendations 缓存适当性结果（短 TTL） | 重计算省掉，吞吐显著提升 |
| P1 | asyncpg 连接池调优（pool_size/overflow） | 减少高并发下 DB 连接排队 |
| P2 | 多 worker / 多节点：`--workers 4` 单机实测有效（混合 100 并发 RPS 151→625） | 已落地；更大规模需独立压测机/多节点 |
| P2 | 生产级：多节点 + 负载均衡 + 真实客户端分布 + 百万级数据 | 验证集群容量 |

实际落地的三项组合拳：**多 worker + 减少每请求 DB 往返（快照复用）+ health 缓存**。

### 3.3 读写不对称的实证与架构级约束

另一组来自 Agent Harness 真实测试的数据（44K Token 文档抽取任务，10+ 子代理并行）揭示了**读写的性能鸿沟**：

- 读取（Prefill）：纯矩阵乘法、并行计算 KV Cache，44K 上下文 1-2 秒读完；
- 写入（Decode）：自回归生成，每 Token 需重新计算全部上下文，44K 下仅约 1-2 Token/秒，写入超过 1 小时未完成。

核心结论：**"上下文大"只保证能"读"，不保证能"写"**——模型 API 输出上限远小于输入窗口，且生成速度随上下文长度急剧下降。

由此推出针对 Agent/RAG 架构的硬性约束：

1. **策略上卷"高并发只读"，不卷"高并发写入"**。金融场景天然读多写少：查持仓/风控/订单状态高频只读并行；下单/赎回低频但必须强一致、不截断。
2. **语义级限流**：业务层对同一客户/账户/幂等键，在订单终态之前，后续请求直接返回 `429` 或 `409`；AI 写入层禁止多个子代理同时调用高成本 `LLM.generate()` 写同一资源，批量写入走 Outbox + AsyncTask 队列。
3. **Write Budget**：写入 Token 消耗像数据库连接池一样被显式管理（如 `max_output_tokens=1500`），超预算返回 `needs_pagination`，由 Supervisor 异步分页完成，禁止模型"截断硬写"。
4. **输入侧强制分块**：子代理输入上下文超过 8000 Token 必须先分块，单次生成上下文上限 4000 Token。
5. **输出侧极简结构化**：输出限定 `{summary, pointers, truncated, continuation_token}`，禁止长篇自然语言转述。
6. **降级不阻塞**：写入超预算/超时/截断时，返回已完成摘要 + 完整内容写入 AsyncTask + Outbox 异步完成。

对应的性能验收基线：

| 场景 | 验收指标 |
|---|---|
| 单子代理写入（44K 上下文） | ≤ 3 分钟 |
| 10 子代理并行（分块后 4K 上下文） | ≤ 5 分钟 |
| 输出截断率 | 0%（截断必须触发分页或降级） |
| 写入 Token 消耗 | 单请求 ≤ 2000 Token（含所有子代理聚合） |

## 4. 并发死锁案例复盘

### 4.1 案例一：profile/me 50 并发死锁

**现象**

- `/profile/me` 并发 50：RPS 骤降，样本出现 170+ 个 `500` / `Server disconnected`；本机强机照崩，与机器强弱无关。
- 单/低并发正常（大量 200、250-350ms），一上 50 就崩。
- error.log 真实栈：

```
profile.py:92 my_summary → asset_summary_service.latest_or_derived
  → calculate(revalue=True) → holding_valuation_service.revalue_user
    SELECT customer_holding ... WHERE user_id=:u AND status='active' FOR UPDATE
  asyncpg.exceptions.DeadlockDetectedError
    Process 193 waits for ShareLock on txn; blocked by 293 …
    Process 306 waits for AccessExclusiveLock on tuple of customer_holding; blocked by 193
```

**根因（代码 + 数据双重确认）**

1. 压测账号当天的 `customer_asset_snapshot` 中 `source_type='derived'` 快照缺失（最近快照是昨天的）；
2. `latest_or_derived` 在"当日无派生快照"分支走 `calculate(revalue=True)` → `revalue_user` 对每条持仓执行 `SELECT … FOR UPDATE` 再 update；
3. **同一客户**多个并发请求同时首次命中该分支 → 都对该持仓行取 `FOR UPDATE` → 互相等待成环 → PostgreSQL 判定死锁 → 500 / 连接断开。

**修复**

在 `AssetSummaryService.latest_or_derived` 无当日快照分支，执行 `calculate` 前先取 per-user 事务级咨询锁：

```sql
SELECT pg_advisory_xact_lock(hashtextextended(:uid, 0))
```

同客户并发重估被串行化；第二个请求等第一个生成当日快照后**再查一次直接复用**（补充了二次查询），不再重复对持仓 `FOR UPDATE`，死锁消除。全量 pytest 233 passed。

**教训**

- 不是"本地好、服务器差"：本机与 4C8G 服务器都压 50 并发，本机 500 反而更多。根因在"每天对该用户首次读取 + 并发"这一**逻辑缝隙**——此前报告的"asset 快照复用"优化只在"当天已有 derived 快照"时生效，一旦当日缺失且多请求并发首次命中，无原子保护即死锁。
- 判断要多查数据：单请求单用户不暴露问题，必须查 `customer_asset_snapshot` 的 `source_type` 与最近 `snapshot_time`，才能确认是否每次都重算。

### 4.2 案例二：多 worker 启动期 seed 死锁

**现象（启动期偶发）**

API 使用 `uvicorn --workers 4`，启动日志反复出现：

```
lifespan → ensure_demo_customer_profiles
asyncpg.exceptions.DeadlockDetectedError
  Process waits for AccessShareLock (users) … blocked by AccessExclusiveLock …
Application startup failed. Exiting.
Child process failed to start
```

**根因**

- `--workers 4` 意味着 **4 个独立进程**各自执行 `app.main.lifespan`；
- 每个 worker 的 lifespan 内都执行 `ensure_schema`（一堆 `ALTER/CREATE INDEX/DROP INDEX`，拿 `AccessExclusiveLock`）之后再跑各 demo seed（`SELECT users ...`）；
- 两个 worker 同时执行这批 DDL/seed（幂等但顺序/锁竞争）→ 一个持 users 表的 AccessExclusiveLock，另一个等它、自己又在别处持锁被对方等 → 锁环 → 死锁 → 该 worker 启动崩溃、parent 反复重启；
- 偶发且常能靠重启自愈，所以难稳定复现、易被误判为"时好时坏"。

**修复**

启动段抽出为 `_seed_startup_locked(database, settings)`：

- 用 database.engine 的专用连接先 `SELECT pg_advisory_lock(:key)`（**session 级**，跨事务持有，key=727001）；
- 拿到锁后才执行 `ensure_schema` + 各 seed，`finally` 中 `pg_advisory_unlock`；
- 效果：4 个 worker 中仅一个能进 DDL/seed 段，其余等锁（拿到后再进，幂等重跑安全），锁环从根上消失。

与案例一的区别：**运行期用 per-user 事务级 advisory lock，启动期用全局 session 级 advisory lock**，二者不冲突。验证：py_compile + 全量 pytest 233 passed。

### 4.3 复盘共性结论

1. 并发压测前必须确证三件事：**被测实例即目标配置、账号可登录、数据状态符合预期**（如当日快照是否存在），否则易把"逻辑缝隙/数据状态"误当"机器差"。
2. `SELECT ... FOR UPDATE` 在"同一资源多个首次写/首个生成者竞争"场景是死锁温床。正确姿势是：**per-key advisory/xact 锁做创建者选举**，或**唯一约束/原子 upsert**。
3. 两类死锁本质相同：**多个并发执行体共享一个独占资源，出现锁环**。运行期（持仓行锁环）与启动期（schema/seed DDL 锁环）分别用不同粒度的 advisory lock 化解。

## 6. 总结

- **正确性**：所有压测场景 0 错误；强幂等三层机制（唯一索引兜底 + 行锁 + 确定性幂等键）在 30 并发下 0 重复订单。
- **性能**：优化前单 worker DB 型端点 ~90-150 RPS；优化后（4 worker + 快照复用 + health 缓存）混合 100 并发 RPS 151→625（4.1x）、P50 606→98ms。
- **数据量**：5k → 50k 查询不退化。
- **真正的杠杆**是多 worker + 减少每请求 DB 往返 + health 缓存，而不是堆机器。
- **并发的暗礁**在"首次生成"竞态：快照首次生成与启动期 DDL/seed 都因锁环死锁，均以 advisory lock 化解。
- 生产级 QPS 仍需多节点实测确认；容量外推仅供工程估算（误差 ±50%）。
