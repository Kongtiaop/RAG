## 1. 环境搭建与上手路径

### 1.1 项目形态

模块化单体（Modular Monolith）：前端 Vue 3 + Vite，后端 FastAPI + SQLAlchemy Async，PostgreSQL/pgvector 承担主业务库与向量检索，Redis Streams 承担异步任务与 Outbox 分发；知识库、客服 Agent、风控、交易、工单和后台运营共用一个后端进程及多个独立 Worker。

### 1.2 新成员 5 分钟启动

前置条件：Docker Desktop、Node.js/npm、PowerShell 7（Windows 推荐）。

```powershell
# 仓库根目录执行脚手架
.\scripts\team_bootstrap.ps1

# 另开终端启动前端
Set-Location frontend
npm run dev -- --host 127.0.0.1
```

访问入口：

| 入口 | 地址 |
|---|---|
| 前端 | `http://127.0.0.1:5173` |
| 后端健康检查 | `http://127.0.0.1:8010/api/v1/health` |
| 后端 OpenAPI | `http://127.0.0.1:8010/docs` |

脚手架行为：检查 Docker Compose / Node/npm → 不覆盖已有 `.env`（首次从 `.env.example` 复制）→ 创建 `uploads/knowledge`、`uploads/workorders` → `npm ci` 安装前端锁定依赖 → 构建并启动 `docker-compose.p0.yml` → 等待 API 健康检查通过。

常用参数：`-SkipBuild`（跳过镜像构建）、`-SkipFrontend`（只启动后端基础设施）、`-ResetData`（清空本地演示数据重新 seed，仅限 development/local）、`-StartAml`（额外启动 AML Scheduler）。

> **数据安全红线**：日常停止用 `docker compose -f docker-compose.p0.yml stop`；**不要使用 `docker compose down -v`**——会删除本地 PostgreSQL/Redis/Milvus 数据卷。

### 1.3 目录地图

```
app/
├── api/              # HTTP 路由、鉴权、参数校验、响应组装（不堆业务规则）
├── services/         # 业务用例、状态流转、风控、交易、知识库、记忆、任务编排
├── ports/            # Repository / Agent / 交易 / 向量库的抽象契约
├── repositories/     # PostgreSQL/MySQL 适配与 Unit of Work（跨库改动需走文档门禁）
├── agents/           # Agent 图编排
├── integrations/     # LangChain/Qwen 等集成边界
├── schemas/          # HTTP 输入输出 DTO（与 models 严格分离）
├── models/           # 数据库持久化模型
├── db/               # 数据库连接、schema 初始化、健康检查
├── infrastructure/   # Redis、Qwen、pgvector/Milvus 等外部依赖
└── main.py           # 启动生命周期、schema/seed、应用状态
workers/              # Outbox、通知、知识库、数据目录、客服超时、AML Scheduler
frontend/src/         # views（页面）/ api（客户端，统一走 http.ts 访问 /api）/ stores（登录态）
tests/ + scripts/     # HTTP/故障/并发测试；验收、迁移、专项诊断脚本
```

`docker-compose.p0.yml` 是**唯一的编排文件**（旧的 `docker-compose.yml` 全量栈已删除：它与 p0 使用同一组端口却挂另一个数据卷，混用会连到空库）。

### 1.4 代码约定

- 调用方向：API → Service → Port/Repository；路由层负责 HTTP，不直接拼装数据库细节。
- Service 通过 Repository/UoW 访问业务数据；不绕过已有抽象直接创建连接或写 SQL。
- `models` 是持久化模型、`schemas` 是 API DTO，二者不混用。
- 异步外部任务走 Redis Stream/Outbox/Worker；不在 HTTP 请求里同步执行长时间 embedding、批量通知或日批扫描。
- 异常集中在 `app/common/exceptions`；新增 API 同时补 schema、权限边界、HTTP/契约测试、API 文档。

### 1.5 危险区与修改前检查

| 危险区 | 风险 | 修改前检查 |
|---|---|---|
| `app/main.py` | 启动时执行 schema 与多类 demo seed | 完整重启并验证健康检查 |
| `trading_service.py` / `repositories/trading.py` | 订单/成交/持仓/状态历史耦合度高 | 先跑交易闭环和相关 HTTP 测试 |
| `customer_rag_service.py` 等 RAG 链路 | 依赖知识库、Embedding、Redis worker、外部 Qwen | 确认 API 与 Worker 都在运行 |
| `outbox_worker.py` / `notification_worker.py` | 重复消费、幂等、重试影响通知/任务 | 不能只用单元测试判断正确性 |
| `unit_of_work.py` 及 MySQL 适配 | MySQL 是迁移验证/隔离测试用途 | 不能把 MySQL 配成 HTTP 生产写库 |
| `http.ts` / `vite.config.ts` | 前端依赖 `/api` 代理 | 不要直接双击 `dist`（会 Network Error） |
| `uploads/`、`logs/`、数据卷 | 本地运行态 | 不提交 Git |

推荐阅读顺序：README 与工作流文档 → `app/main.py` → 目标业务的 `app/api/*.py` → 对应 `app/services/*.py` → ports/repositories/models/schemas → workers 与 infrastructure → 前端 views 与 E2E 测试。

新成员第一批任务建议：为前端模块补错误态/空态展示；为已有 Service 补边界测试；为已有 API 补文档、权限矩阵与 smoke 脚本。**第一次不要直接改交易状态机、数据库迁移、Outbox 投递协议或多 Worker 共享的 Redis Stream。**

## 2. CI/CD 搭建

### 2.1 流水线全貌

```
push main ──▶ GitHub Actions: Test & Build（pytest + 前端 build）
                    │ 通过
                    ▼
             Deploy to Aliyun（SSH 登录服务器 → docker compose build + up
                               → 健康检查带重试）
```

改完代码 push 即自动部署，无需手动上服务器；另支持 `workflow_dispatch` 手动触发。

### 2.2 搭建步骤

**GitHub 侧**：

1. 新建私有仓库，本地添加 remote 并推送；
2. 生成 SSH 密钥对（`ssh-keygen -t ed25519`）；
3. 仓库 Settings → Secrets and variables → Actions 添加：`SSH_HOST`、`SSH_USER`、`SSH_PRIVATE_KEY`（OpenSSH 格式私钥）、`SSH_PORT`；
4. 公钥加入服务器 `~/.ssh/authorized_keys`（让 Actions 能 SSH 登录服务器）。

**服务器一次性初始化**：

```bash
# 1) 装 Docker Engine + Compose plugin
curl -fsSL https://get.docker.com | sh && systemctl enable --now docker
docker compose version || apt-get install -y docker-compose-plugin

# 2) 克隆仓库（origin 指向 GitHub 私有仓库，需配 GitHub SSH key）
git clone git@github.com:<org>/<repo>.git /opt/wealth
cd /opt/wealth && cp .env.example .env   # 改数据库密码等

# 3) 首次手动部署验证
bash scripts/deploy.sh
```

**端口与防火墙**：应用对外端口 API=8010（compose 的 `API_PORT`）；云安全组放行 8010 与 SSH 22。

**服务器资源提示（4C8G）**：p0 compose 起 Postgres + Redis + API + 多个 worker（outbox/knowledge/memory/aml 等），演示够用；内存吃紧可只起核心：

```bash
docker compose -f docker-compose.p0.yml up -d postgres redis api memory-worker outbox-worker
```

**本地手动部署**（不想等流水线）：`SSH_USER=root SSH_HOST=<host> ./scripts/deploy_to_server.sh`。

## 3. 开发门禁与工作流

### 3.1 门禁分级

**新成员最小门禁**（每次提交前）：

```powershell
python -m py_compile app\main.py        # 基础语法
cd frontend && npm run build            # 前端构建
.\scripts\team_check.ps1                # API 健康检查
```

**完整门禁**（改动涉及后端、Repository/UoW、数据库迁移或 MySQL 双读时）：

```powershell
python -m py_compile app\main.py app\api\profile.py app\api\admin.py app\services\trading_service.py ...

python -m scripts.reset_mysql_dev_state --yes            # 清理本地 MySQL 隔离库
python -m scripts.migrate_core_to_mysql                   # 迁移
python -m scripts.test_mysql_migration_gate               # 迁移门禁
python -m scripts.compare_customer_summary_dual_read      # 双读一致性
python -m scripts.test_trading_flow                       # 交易闭环
python -m scripts.test_http_smoke --base-url http://127.0.0.1:8010/api/v1 --accounts DEMO_ACCOUNTS.txt
```

**通过标准**：全部命令成功；MySQL migration 输出 `schema_validation=PASS`；migration gate `pass=true`；双读 `differences=[]`；交易闭环 PASS；HTTP Smoke `status=PASS`。

**全量回归**（改代码后）：`python -m pytest tests/ -q` 全绿 + 前端 `npm run build`。

门禁按改动范围选择，没有 MySQL 隔离库时不盲跑全部迁移脚本。数据安全纪律：reset 脚本只清理本地 MySQL 隔离库，**不要在生产执行**；双读失败先记录差异，不要直接手工修改正式业务数据。

### 3.2 Docker 一键启动与 Worker 分离

后端使用独立镜像：`Dockerfile.api` 只运行 FastAPI，`Dockerfile.aml-scheduler` 只运行 AML 定时 Worker。

```powershell
# 启动 PostgreSQL、Redis、API（默认还起 Outbox Worker 和 Knowledge Worker）
docker compose -f docker-compose.p0.yml up -d --build
Invoke-WebRequest http://127.0.0.1:8010/api/v1/health

# 仅在需要定时 AML 时额外启动
docker compose -f docker-compose.p0.yml --profile aml up -d --build aml-scheduler
```

全量环境（含 Milvus）用 `docker compose up -d --build`；MySQL 通过 `--profile migration` 显式启用。

### 3.3 AML 日批 Worker

独立容器，默认不随基础设施启动。配置 `.env` 中 UTC 时间与窗口天数后显式启动：

```powershell
docker compose -f docker-compose.p0.yml --profile aml up -d aml-scheduler
docker compose -f docker-compose.p0.yml logs -f aml-scheduler
# 停止（不影响 PG/Redis/Milvus）
docker compose -f docker-compose.p0.yml --profile aml stop aml-scheduler
```

幂等保证：Scheduler 对同一个 UTC 分钟仅处理一次；扫描失败在下一轮轮询重试；服务层用 `batch_key` 复用同一扫描窗口——容器重启或人工补跑不会重复创建 AML 批次。

### 3.4 知识库上传自动管线

管理员在后台"知识库管理"上传 UTF-8 TXT/MD/DOCX（单文件 ≤ 20MB）。链路：

```
上传 API（存文件 + 元数据 + 写 knowledge.document_created Outbox 事件）
    → outbox-worker 发布到 Redis Stream
    → knowledge-worker 解析、切分、调 Embedding、写 knowledge_chunk.embedding（pgvector）
```

排障：文档长期"处理中"优先查 outbox-worker / knowledge-worker 日志；"处理失败"在后台文档列表看原因。`uploads/knowledge` 是容器内临时路径，生产应挂持久卷或换对象存储。

### 3.5 环境类坑位速查

| 坑 | 现象 | 处理 |
|---|---|---|
| 前端 Vite 代理未启动 | 页面统一 Network Error（登录/auth/上传全挂） | 必须从 `frontend` 目录 `npm run dev`；验证 `5173/` 与 `5173/api/v1/health` 都 200。8010 健康但 5173 拒绝连接时，先启 Vite，不要重建 Docker API |
| Windows 中文路径构建 | BuildKit gRPC header 错误 | `subst W: "C:\...中文目录..."` 后在 ASCII 盘符下构建 |
| 误删数据卷 | `down -v` 删除本地 PG/Redis/Milvus 数据 | 日常用 `stop`，禁用 `down -v` |
| 双 compose 共端口 | 容器名/端口互抢、连到空库 | 统一只用 `docker-compose.p0.yml`；旧全量栈已删除 |

## 4. 演示与 E2E 验收流程

### 4.1 部署开关（compose 默认已开，可在服务器 .env 覆盖）

| 开关 | 默认 | 作用 |
|---|---|---|
| `LLM_INTENT_FALLBACK_ENABLED` | `true` | 对**非交易**意图（推荐/只读/转人工）允许高置信 LLM 兜底；交易类仍走规则，LLM 永不创建/提交交易 |
| `BAD_CASE_COLLECT` | `1` | unknown / 低置信 / intent_misroute 落数据飞轮积累池 |
| `LLM_INTENT_SHADOW_ENABLED` | `false` | fallback 开启时本身会落影子审计，无需重复开 |

关闭方式：服务器 `/opt/wealth/.env` 写对应值后 `docker compose -f docker-compose.p0.yml up -d`。

### 4.2 E2E 验收脚本（服务器上）

服务器宿主无 python 依赖，统一进 **api 容器**执行（脚本已打进镜像，容器内 API 端口是 8000）：

```bash
cd /opt/wealth
docker compose -f docker-compose.p0.yml exec api \
  env E2E_BASE=http://127.0.0.1:8000/api/v1 \
  python scripts/test_recommendation_precision_e2e.py
```

验收点：推荐返回"精准 Top-N"（matches ≤ 5）且每条带 `recommendation_reason`；返回 `preference_note`；"我能购买什么产品"路由到产品推荐而非误入交易草稿；用户表达偏好后推荐理由能读到偏好。退出码 0=PASS，1=有字段缺失。

### 4.3 飞轮闭环验证

规则自信路由交易草稿、而高置信影子 LLM 判只读/推荐时，会落一条 `intent_misroute` 坏样本：

```bash
tail -n 20 logs/bad_cases.jsonl    # 应能看到含 intent_misroute 的记录
```

闭环链路：bad-case-worker 把新记录落库 → 人工标注界面显示"高置信误判(规则 vs 影子分歧)" → 标注 → 导出进黄金评测集 → auto_repair。线上实测闭环样例：合成 misroute → jsonl 出现 `{"reasons":["intent_misroute"],"rule_template":"T4_PURCHASE_DRAFT","llm_template":"T2_PRODUCT_RECOMMENDATION"}` → bad_case 表落库，采集→写文件→worker 落库全通。

## 5. 运维 Runbook 要点

- **日志**：`docker compose -f docker-compose.p0.yml logs -f api`；各 Worker 单独 `logs -f <worker>`。
- **扩缩**：内存吃紧只起核心服务（见 2.2）；AML 是可选 profile，不参与默认启动。
- **健康检查**：CI 部署带健康检查重试；本地验证 `8010/api/v1/health`。
- **配置变更**：服务器 `.env` 修改后需 `up -d` 重建生效；容器 environment 是白名单，新增开关须在 compose 显式声明，否则不透传（静默失效）。
- **数据安全**：升级/重建不删固定数据卷；`down -v` 禁用；reset 类脚本仅限本地隔离库。
- **升级注意**：涉及迁移时手工执行 `alembic upgrade head`（compose 与 CI 均未自动跑迁移）；多 worker 部署下启动期 schema/seed 有 advisory lock 保护，但重建后仍应观察启动日志。

## 6. 附：技术选型参考（实施期沉淀）

### 6.1 RAG 实现方案对比

| 方案 | 适用场景 |
|---|---|
| LangChain RetrievalQA | 快速上手，链式编排 |
| LlamaIndex VectorStoreIndex | 已有 LlamaIndex 经验 |
| 自建 Pipeline | 需要完全自定义控制流（Embedding → 向量检索 → Prompt 拼装 → LLM） |

Embedding 选型要点：选定后**全局统一**，所有向量集合使用相同维度（模型升级须配套重嵌入，见可观测性与数据飞轮篇的 embedding 模型守卫）。分块策略：FAQ 问答对每对一个 chunk 不再切分；长文档用递归切分（`chunk_size=512`、`chunk_overlap=64`）并保留标题层级元数据。

### 6.2 风控规则引擎（策略模式）

```python
class BaseRiskRule(ABC):
    rule_id: str
    rule_name: str
    risk_level: str

    @abstractmethod
    def evaluate(self, transaction: dict) -> bool: ...

class LargeTransactionRule(BaseRiskRule):
    rule_id = "R001"
    rule_name = "大额现金交易"
    risk_level = "低"
    threshold = 50000

    def evaluate(self, transaction: dict) -> bool:
        return transaction["amount"] >= self.threshold
```

规则按 `rule_id`/`rule_name`/`risk_level` 声明，`evaluate` 纯函数式判定，便于逐条测试与组合。

### 6.3 置信度计算（来源初始值 + 时间衰减）

```python
SOURCE_INITIAL = {"风评问卷": 0.9, "AI对话提取": 0.6, "用户自述": 0.4, "默认值": 0.2}

def calc_base_confidence(source: str, age_days: int) -> float:
    base = SOURCE_INITIAL.get(source, 0.2)
    decay = max(0, 1 - age_days / 365 * 0.2)
    return max(0.0, min(1.0, base * decay))
```

不同来源的信息给不同初始置信度（问卷 > AI 提取 > 自述 > 默认值），随时间衰减。

### 6.4 Agent 路由（工厂模式）与降级矩阵

```python
AGENT_REGISTRY = {"customer": CustomerAgent, "advisor": AdvisorAgent,
                  "risk": RiskAgent, "analyst": AnalystAgent, "operator": OperatorAgent}

def get_agent(agent_type: str):
    agent_class = AGENT_REGISTRY.get(agent_type)
    if not agent_class:
        raise ValueError(f"Unknown agent type: {agent_type}")
    return agent_class()
```

| 组件 | 降级策略 |
|---|---|
| LLM | 云端 API 不可用时切换到备用模型 |
| 向量库 | 向量检索超时时用关键词查询兜底 |
| 图数据库 | 图谱查询超时时跳过图谱增强，仅用 RAG 结果 |
| Redis | 连接失败时直连数据库，恢复后自动回填缓存 |

降级的原则与 BUG 台账教训一致：**组件故障不应改变业务结论**——降级路径要么给出带标注的近似结果，要么显式提示能力受限，不能静默产出看似正常的错误答案。
