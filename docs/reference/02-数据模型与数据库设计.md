## 1. 总体设计思路

### 1.1 事实源原则

客户、账户、订单、资金流水、风险、工单、权限、审计均以 **PostgreSQL 为唯一业务事实源**；Redis、Milvus、MySQL 迁移库不替代主库事实。

各存储分工：

| 存储 | 职责 | 定位 |
|---|---|---|
| PostgreSQL 16 + pgvector | 业务事实、文档元数据与版本、Chunk、任务状态、审计、1024 维向量 | 唯一事实源，容器 `wealth-postgres` |
| Redis | 短期会话、缓存、Embedding 缓存、队列与消费状态、幂等锁、限流 | **不作为最终事实数据库** |
| Milvus | 文档 Chunk 向量、FAQ 向量、记忆向量 | 检索加速；最终状态、版本、权限、审计仍以主库为准 |
| Neo4j（可选） | 客户/产品/行业/风险/政策关系、GraphRAG 增强 | 数据必须可从主库重建，不作为唯一事实来源 |
| MySQL 8 | 迁移验证（隔离容器） | 团队熟悉度备选，**禁止与 PostgreSQL 双写** |

### 1.2 主库选型理由

选择 PostgreSQL 作为主业务数据库的原因：

1. 异步 SQLAlchemy、`asyncpg`、PostgreSQL/pgvector 方案可直接复用。
2. PostgreSQL 对 JSONB、全文检索、事务、约束和复杂查询支持较好。
3. 向量从外部向量库回退到 pgvector 的迁移路径更顺。
4. 避免 MySQL/PostgreSQL 双主库带来的维护和数据一致性问题——双写会把项目从业务系统变成数据同步项目。

### 1.3 全局约定

- 主键统一使用 UUID（String(36)），便于异步任务、跨服务和数据导入。
- 金额使用定点数 `Numeric(18,2)`，**禁止使用浮点数**；份额使用 `Numeric(18,4)`。
- 时间统一存储 UTC `DateTime(tz)`（TIMESTAMPTZ）；前端按北京时间展示。
- 状态字段使用字符串而非数据库强绑定枚举，避免迁移负担。
- 核心表均含 `created_at` / `updated_at` 审计字段；交易、审计、风控记录原则上不物理删除，关键主数据用 `deleted_at` 软删除。
- 隐私字段（身份证、手机号、银行卡号）只保存脱敏值或加密值；密码/令牌只存哈希（Argon2、SHA-256）。

## 2. 表全景（49 张表）

```text
身份权限：users ─┬─ user_roles → roles → role_permissions → permissions
                 ├─ refresh_sessions（刷新令牌轮换）
                 ├─ customer_advisor_authorization（投顾授权）
                 └─ customer_enterprise_verification（企业认证）

客户画像/资产：customer_profile / customer_risk_assessment / customer_subjective_profile
              customer_asset_snapshot / customer_holding / product / product_suitability_rule / risk_rule

资金交易：account → orders → trades / order_status_history
         natural_language_order_draft（NL 草稿）→ orders
         advisor_operation_draft（投顾草稿）
         business_operation（赎回/转账）→ money_flow（资金流水）

风险/AML：risk_alert → risk_investigation / risk_report_draft
         aml_batch_run → aml_batch_alert / aml_scheduler_state

工单/通知：work_order → work_order_update / work_order_attachment
         notification

客服会话：customer_service_session → customer_service_message

记忆：customer_memory → customer_memory_event

知识库/RAG：knowledge_base → knowledge_document → knowledge_document_version → knowledge_chunk

数据目录/NL2SQL：data_catalog_domain → data_catalog_table → data_catalog_column
                data_catalog_relation / data_catalog_example_query / data_catalog_revision

异步基础设施：outbox_event（事务发件箱）/ async_task（后台任务）
审计：audit_logs

数据飞轮：bad_case（无外键，按 customer_id 逻辑关联 users）
```

## 3. 身份、权限与会话

### 3.1 users（用户主表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | UUID |
| username | String(128) unique | 登录名 |
| password_hash | String(255) | Argon2 密码哈希 |
| display_name | String(128) | 显示名 |
| status | String(20) | active / deleted / disabled |
| is_super_admin | Boolean | 超级管理员标志 |
| deleted_at | DateTime(tz) | 软删除时间 |

### 3.2 RBAC 关联表

- `roles`：`code` unique（customer、advisor、risk_manager、operations、auditor、super_admin 等）。
- `permissions`：`code` unique（如 `order:review`、`risk:alert_action`）。
- `user_roles`：`(user_id, role_id)` 复合主键，FK 均 CASCADE。
- `role_permissions`：`(role_id, permission_id)` 复合主键，FK 均 CASCADE。

### 3.3 refresh_sessions（刷新令牌会话）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | FK→users(id) CASCADE | |
| token_hash | String(64) unique | SHA-256，不存明文 |
| expires_at | DateTime(tz) | 默认 30 天 |
| revoked_at | DateTime(tz) 可空 | 轮换/撤销时间 |

### 3.4 customer_advisor_authorization（客户对投顾授权）

客户显式授权投顾代办的核心约束表：

| 字段 | 类型 | 说明 |
|---|---|---|
| customer_id / advisor_id | FK→users(id) CASCADE | 被授权客户 / 投顾 |
| allowed_actions | String(255) | 允许动作，默认 buy |
| product_scope | String(255) | 产品范围，默认 * |
| max_single_amount | Numeric | 单笔上限 |
| max_daily_amount | Numeric | 日上限 |
| risk_level_ceiling | String(8) | 风险等级上限，默认 C2 |
| effective_from / effective_to | DateTime(tz) | 生效期（空=长期） |
| requires_customer_confirmation | Boolean | 是否需要客户确认 |
| revoked_at | DateTime(tz) 可空 | 撤销时间 |

### 3.5 customer_enterprise_verification（企业认证）

`user_id` unique + CASCADE；`status`：pending / approved / rejected；含 `reviewed_by`、`reviewed_at` 审核留痕。企业类型不能由客户自助修改，只能走审核流。

## 4. 客户、产品、资产与适当性

### 4.1 customer_profile（客户画像）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | FK→users(id) CASCADE unique | 一人一画像 |
| age / occupation / annual_income / region | — | 基础信息 |
| customer_type | String(64) | individual / enterprise |
| customer_tier | String(64) | 普通/黄金/白金/钻石/私人银行 |
| investment_experience_years | Integer | 投资经验年限 |
| investment_goal / investment_horizon_years | — | 投资目标与期限 |
| liquidity_preference | String(16) | low/medium/high |
| source_type | String(32) | synthetic |

`investment_horizon` 为兼容遗留列，新代码使用 `investment_horizon_years`。

### 4.2 customer_risk_assessment（风险测评）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | FK→users(id) CASCADE | |
| risk_level | String(8) | C1-C5 |
| score | Integer | 测评分数 |
| answers_json | Text | 答题明细 JSON |
| status | String(32) | active 等 |
| source_type | String(32) | questionnaire |
| expires_at | DateTime(tz) 可空 | 过期时间 |

生命周期：注册默认 C1 provisional → 正式测评 → C1-C5 active → 参与产品适配与交易确认。

### 4.3 customer_subjective_profile（客户主观画像）

存对话中采集的主观字段：`field_name`/`field_value`/`source_text`，`source_type=user_declared`，`confirmed` 是否客户确认，`confidence Numeric(5,4)`。与结构化画像分离，避免未确认的对话信息污染正式画像。

### 4.4 customer_asset_snapshot / customer_holding

- `customer_asset_snapshot`：`total_asset`、`cash_balance`、`investable_asset`、`liability`、`net_asset`、`snapshot_time`，`source_type`：synthetic / trade_derived。
- `customer_holding`：`(user_id, product_id)` 维度的份额/成本/市值/盈亏，`status=active`。

### 4.5 product 与适当性规则

- `product`：产品主数据，`risk_level`（C1-C5）、`minimum_amount`（起购金额）、`daily_yield_rate Numeric(12,8)`、`target_customer_type`、`status`、`deleted_at` 软删除。
- `product_suitability_rule`：按产品挂适当性规则——`minimum_risk_level`、`investor_type`、`minimum_investable_asset`、`rule_text`。
- `risk_rule`：风控/AML 规则配置，`rule_code` unique、`config_json`、`enabled`、`version`、`source_document`。规则以配置行而非硬编码承载，便于审计与版本管理。

## 5. 交易、订单、资金

### 5.1 account（资金账户）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | FK→users(id) CASCADE unique | 一人一账户 |
| account_no | String(64) unique | 账号 |
| available_balance | Numeric(18,2) | 可用余额 |
| frozen_balance | Numeric(18,2) | 冻结余额 |
| risk_restriction_status | String(32) | none / restricted |
| risk_restriction_reason | Text | 限制原因 |
| risk_restricted_until | DateTime(tz) 可空 | 限制截止 |

余额只用可用/冻结两个字段表达：确认订单冻结资金（available 减、frozen 增），成交时从 frozen 扣减，拒绝/取消解冻。

### 5.2 orders（申购订单）

| 字段 | 类型 | 说明 |
|---|---|---|
| order_no | String(64) unique | 订单号 |
| user_id / account_id / product_id | FK | 下单客户 / 账户 / 产品 |
| amount / quantity | Numeric(18,2) / Numeric(18,4) | 金额 / 份额 |
| status | String(32) | pending_confirmation / pending_review / executing / executed / rejected / cancelled |
| idempotency_key | String(128) 可空 | 幂等键（唯一索引防重） |
| order_source | String(32) | customer_direct / advisor_assisted |
| advisor_id | FK→users(id) 可空 | 关联投顾 |
| confirmation_mode | String(32) | customer_order / nl_draft |
| review_note / failure_reason | Text | 审核/失败留痕 |

`idempotency_key` 唯一索引是并发防重下单的最终防线。

### 5.3 natural_language_order_draft（自然语言下单草稿）

Agent 辅助下单的「提案」表，是安全边界的关键设计：

| 字段 | 类型 | 说明 |
|---|---|---|
| customer_id / product_id | FK | |
| side / amount | buy / Numeric(18,2) | |
| version | Integer | 草稿版本，改参时 +1（原地升版本，不新建行），幂等键含版本号 |
| status | String(32) | awaiting_user_confirmation / expired / confirmed_order_created / cancelled |
| input_fingerprint | String(128) | 参数指纹 SHA-256（`customer_id|product_id|side|amount|version`） |
| confirmation_token_hash | String(128) unique | 确认令牌哈希，不存明文；**改参时轮换**，旧令牌随之失效 |
| precheck_snapshot_json | Text | 预检结果快照（含 product_name，用于复述） |
| expires_at | DateTime(tz) | 15 分钟有效期，改参后按新令牌重算 |
| order_id | FK→orders(id) 可空 unique | 确认后关联订单（作废/改参均不写此列） |

设计要点：草稿是「提案」而不是业务状态机，没有独立迁移表，合法动作只有确认建单 / 超时 / 客户作废 / 改参升版本，判断集中在 `NaturalLanguageOrderDraftService`；动作留痕在 `audit_logs`（`create_draft / confirm_draft / cancel_draft / revise_draft`，detail 含新旧参数与指纹）。「改参即令牌轮换」把确认建单的前提绑定到最新参数，杜绝确认旧参数的竞态。

### 5.4 trades / order_status_history

- `trades`：`order_id` FK unique——**一单一成交**；含 `trade_no` unique、金额、份额、`executed_at`。
- `order_status_history`：`(order_id, from_status, to_status, operator_user_id, note)`，状态机每次迁移留痕。

### 5.5 advisor_operation_draft / business_operation / money_flow

- `advisor_operation_draft`：投顾代客创建的操作草稿，`status=pending_customer_confirmation` 等，客户确认后才可转订单——投顾不直接扣款。
- `business_operation`：赎回/转账统一入口，`operation_type`（redeem/transfer）、`confirmation_mode`（customer/advisor）、`authorization_id` 关联授权来源、`idempotency_key` 幂等、`to_account` 转账目标。
- `money_flow`：资金流水，`flow_type`（buy/redeem/transfer 等）、`direction`（in/out）、`counterparty_id`、`channel`、`occurred_at`。转账结算在同一事务内写双方余额 + `transfer/out` + `transfer/in` 两条流水 + 审计。

## 6. 风险与 AML

### 6.1 risk_alert（风险预警/处置主记录）

预警是宽表设计，处置全流程字段都在一行内演进：

| 字段组 | 字段 | 语义 |
|---|---|---|
| 基础 | customer_id、order_id、rule_code、alert_level（low/medium/high）、confidence、evidence_json、recommendation | 预警来源与证据 |
| 状态 | status | open / acknowledged / investigating / pending_customer / report_pending / resolved / dismissed |
| 评估 | assessment_result、assessment_note、customer_consulted、customer_consultation_note | 复核结论与客户沟通 |
| 处置 | disposition_code / disposition_note、action_code、action_status、action_note | 处置编码与动作 |
| 限制 | restriction_status（none/restricted）、restriction_expires_at | 交易限制 |
| 关联 | investigation_id、report_draft_id、handled_by、handled_note | 关联调查/报告/处理人 |

**风险门禁**：预警处于未结案状态（open/acknowledged/investigating/pending_customer/report_pending）时，订单/赎回/转账在后端被 `RISK_CONTROL_BLOCKED` 拦截。

### 6.2 调查、报告与 AML 日批

- `risk_investigation`：`alert_id` FK unique（一预警一调查），`assigned_to`、`conclusion`。
- `risk_report_draft`：`alert_id` FK、`report_type`（large_transaction 等）、`payload_json`、`submitted_at`。
- `aml_batch_run`：日批扫描记录，`batch_key` unique、`scan_window_start/end`、`scan_days` 默认 7、成功/失败客户计数、`source_batch_id` 支持补跑溯源。
- `aml_batch_alert`：`(batch_id, alert_id)` 复合主键的批次-预警关联。
- `aml_scheduler_state`：调度器心跳与上次扫描状态（`last_heartbeat_at`、`last_scan_status`），API 侧据其判定 Worker 存活。

## 7. 工单、通知与客服会话

### 7.1 work_order 系列

- `work_order`：`ticket_no` unique、`category`、`priority`、`status`（open / pending_customer / in_progress / resolved / closed）、`risk_alert_id` 可空 unique（风险补件场景一预警一工单）。
- `work_order_update`：时间线，`author_user_id` + `author_role`，记录客户补件与处理意见。
- `work_order_attachment`：附件**元数据**，`stored_name` unique（受控存储文件名）、`content_type`、`size_bytes`，下载走带 JWT 的鉴权 API。

### 7.2 notification（站内通知）

`idempotency_key` 可空 + 部分唯一索引防重复通知；`resource_type/resource_id` 关联业务资源；`is_read/read_at` 已读状态。

### 7.3 customer_service_session / message

- `customer_service_session`：`status`（waiting_human / human_active / paused / resolved / closed / expired）、`assigned_agent_id`、`handoff_reason`（rag_low_confidence / customer_requested）、`agent_last_heartbeat_at`。
- 约束：`uq_customer_service_session_active_agent`——同一坐席同一时刻只有一条 human_active。
- `customer_service_message`：`(session_id, sender_type, content)`，是实时链路的事实源。

## 8. 记忆

### 8.1 customer_memory（长期记忆卡片）

| 字段 | 类型 | 说明 |
|---|---|---|
| customer_id | FK→users(id) CASCADE | |
| memory_type | String(32) | confirmed_parameter / service_preference / conversation_fact |
| key / value | String(128) / Text | 记忆键值 |
| source | String(32) | conversation / customer_confirmed |
| confidence | Numeric | 默认 1.0 |
| status | String(24) | active（支持软失效） |
| last_confirmed_at / expires_at | DateTime(tz) | 最近确认 / 过期 |

约束：`uq_customer_memory_active_key(customer_id, key)` **部分唯一索引**——同 key 只有一条 active，实现「记忆卡片」语义（新值覆盖旧值而非累积多行）。

### 8.2 customer_memory_event

记忆变更审计：`event_type`（upsert）、`payload JSON`、`conversation_id` 来源会话。配合 `customer_memory` 形成「卡片 + 流水」结构：卡片供读取，流水供追溯。

## 9. 知识库 / RAG

四层结构：`knowledge_base → knowledge_document → knowledge_document_version → knowledge_chunk`。

### 9.1 knowledge_document

| 关键字段 | 说明 |
|---|---|
| document_key | 文档稳定键；约束 `uq_knowledge_document_key(knowledge_base_id, document_key)` |
| content_hash | 内容 SHA-256，用于变更检测 |
| permission_level | public / internal / advisor 等——检索权限过滤的依据 |
| status | processing / active / failed |
| current_version_id | **当前激活版本指针** |
| deleted_at | 软删除 |

### 9.2 knowledge_document_version

| 关键字段 | 说明 |
|---|---|
| version_no | 版本号；约束 `uq_knowledge_document_version(document_id, version_no)` |
| content_hash | 版本内容哈希 |
| status | processing / active / superseded / failed |
| chunk_count | 分块数 |
| activated_at | 激活时间 |

### 9.3 knowledge_chunk

| 关键字段 | 说明 |
|---|---|
| version_id | FK→版本，分块归属具体版本 |
| chunk_index | 块序号；约束 `uq_knowledge_chunk_position(version_id, chunk_index)` |
| content / content_hash | 文本与块哈希（embedding 复用，避免重复计算） |
| title_path / page_number | 标题路径与页码，用于引用溯源 |
| embedding | `VECTOR(1024)` pgvector 向量 |
| status / deleted_at | active / 软删除 |

检索只 JOIN 激活版本 + active 文档。版本化设计的意义：文档重导入时旧版本整批 superseded、新版本激活，检索永远指向单一确定版本，且可回滚。

## 10. 数据目录 / NL2SQL

六表组成受控 NL2SQL 的数据目录（设计动机见架构篇）：

| 表 | 职责 | 关键约束 |
|---|---|---|
| `data_catalog_domain` | 业务域，`allowed_roles_json` 角色准入 | code unique |
| `data_catalog_table` | 目录表：物理定位 + 业务描述 + `is_queryable/is_active` + `embedding VECTOR(1024)` | `uq_data_catalog_table_physical_name(database_name, schema_name, table_name)`；FK→domain 为 RESTRICT |
| `data_catalog_column` | 目录列：`semantic_type`、`is_sensitive/is_queryable`、`allowed_aggregations_json`、别名与示例值、向量 | `uq_data_catalog_column_name(table_id, column_name)` |
| `data_catalog_relation` | 表关系：起点/终点、`cardinality`、`join_guidance`、`is_preferred` | `uq_data_catalog_relation_edge(...)` |
| `data_catalog_example_query` | **受审 SQL 模板**：`question`/`normalized_question`、`target_table_names_json`/`target_column_names_json` 白名单声明、`sql_template`、`is_approved`、向量 | 模板白名单是 NL2SQL 安全层的核心 |
| `data_catalog_revision` | 目录修订审计：`revision_no` + `snapshot_json` 快照 | `uq_data_catalog_revision_number(resource_type, resource_id, revision_no)` |

表/列/示例查询均带 1024 维语义向量，支持文本+向量混合召回；`allowed_roles_json` 在检索期做角色过滤。

## 11. 异步基础设施与审计

### 11.1 outbox_event（事务发件箱）

| 字段 | 类型 | 说明 |
|---|---|---|
| event_type | String(100) | 如 knowledge.document_created |
| aggregate_type / aggregate_id | — | 业务聚合定位 |
| payload_json | JSONB | 事件负载 |
| status | String(20) | pending / published / dead |
| attempt | Integer | 重试次数 |

与业务行**同事务**提交；`outbox_worker` 用 `FOR UPDATE SKIP_LOCKED` 认领，解决「数据库提交成功但事件发布失败」的一致性缺口。

### 11.2 async_task（后台任务）

| 字段 | 类型 | 说明 |
|---|---|---|
| task_type | String(100) | 任务类型 |
| idempotency_key | String(128) unique 可空 | 幂等键 |
| status | String(32) | queued / running / success / failed / dead / cancelled |
| attempt / max_attempts | Integer | 重试计数，默认 max 3 |
| payload_json / result_json | JSONB | 入参 / 结果 |
| available_at | DateTime(tz) 可空 | 延迟执行预留 |

### 11.3 audit_logs

`(actor_user_id, action, resource_type, resource_id, detail)`：所有关键动作（草稿创建/确认/改参、订单审核等）的统一留痕。审计与交易记录不物理删除。

## 12. 数据飞轮：bad_case

| 字段 | 类型 | 说明 |
|---|---|---|
| customer_id | String(36) | 逻辑关联 users.id，**未建外键** |
| query / query_hash | Text / String(64) index | 原始问句与哈希（去重） |
| intent / confidence | String(64) / Float | 规则或模型识别出的意图与置信度 |
| evidence_status | String(64) | RAG 证据状态（sufficient / low_confidence / …） |
| handoff / clarifications | Boolean / Integer | 是否转人工、澄清轮数 |
| reasons | JSON | 判定为 bad case 的信号列表（如 intent=unknown / 低置信 / 规则回退） |
| labeled_intent / requires_clarification / category / note | — | 人工标注结果 |
| split / labeled_by / labeled_at | String(16) / — | train/test 划分与标注留痕 |

运行时自动判定「当前问答是不是 bad case」并落库，形成可标注、可回流的数据集，支撑意图识别与 RAG 的持续评测。未建外键是有意为之：飞轮采集不应对主业务写入路径产生外键约束开销。

## 13. 关键约束与一致性原则

```text
幂等：
  orders.idempotency_key 唯一（并发防重下单）
  natural_language_order_draft.confirmation_token_hash 唯一（令牌）
  notification.idempotency_key 部分唯一（防重复通知）
  async_task.idempotency_key 唯一（防重复任务）

记忆：
  customer_memory 同 (customer_id, key) 仅一条 active

客服：
  customer_service_session 同坐席同一时刻仅一条 human_active

资金/订单一致性：
  冻结：available -= amount; frozen += amount（confirm_order）
  成交：frozen 扣减 → holding upsert → trade → 资产快照 → money_flow
  状态迁移唯一权威在 Order.transition()

风险门禁：
  risk_alert 未结案(open/acknowledged/investigating/pending_customer/report_pending)
  → 订单/赎回/转账被拦截
```

## 14. 设计取舍小结

| 取舍 | 理由 |
|---|---|
| UUID 字符串主键（String(36)） | 便于异步任务、跨服务和数据导入，不依赖序列 |
| 定点数存金额，禁用浮点 | 资金计算不能有精度误差 |
| 状态字段用字符串而非 DB 枚举 | 迁移成本低，状态机权威放在 Service 层（`Order.transition()`） |
| 软删除（deleted_at）用于产品/文档/Chunk/用户 | 保留审计与恢复能力；交易/审计/风控记录则完全不删 |
| 知识 Chunk 挂版本而非直接挂文档 | 版本切换时检索口径原子切换，可回滚 |
| 草稿表（NL/投顾）独立于订单状态机 | 草稿是提案不是业务事实，确认建单才进入订单状态机 |
| 宽表 risk_alert | 处置全流程（评估/处置/限制/关联）在一行内演进，避免多表 JOIN 重建处置上下文 |
| 幂等键唯一索引贯穿订单/草稿/通知/任务 | 网络重试与并发竞争的资金副作用防重，靠 DB 约束而非应用层判断兜底 |
| 部分唯一索引实现「单 active」语义 | 记忆卡片、坐席会话等「同键仅一条生效」场景，用索引表达不变量 |
| bad_case 不建外键 | 飞轮采集高频写入，不拖累主业务路径 |
| 目录修订带 snapshot_json | NL2SQL 模板与目录变更可审计、可回放 |

## 15. 维护规则

1. 新增实体时，必须同步：ORM Model、Alembic Migration、Schema/Repository/Service、测试和表结构文档。
2. 不在数据库客户端直接修改关键业务状态；资金、订单、风险限制应通过 API/Service 产生完整审计。
3. 结构演进优先使用 Alembic；`ensure_schema` 兼容补列只用于开发环境，不替代规范迁移。
4. 连接凭据仅适用本地 Docker 开发环境；生产必须独立账号、最小权限、TLS 和密钥管理。
