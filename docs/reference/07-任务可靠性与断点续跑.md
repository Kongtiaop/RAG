## 1. 任务可靠性：问题模型

### 1.1 组合失效

**功能正确 ≠ 系统正确。** 每个功能单独验证都通过，两个正确功能在共享状态或时序接缝上相遇后失效。同日出现五次：

| # | 功能 A（各自正确） | 功能 B（各自正确） | 接缝上的失效 |
|---|---|---|---|
| 1 | 办理词识别（"赎回".98） | 时效疑问（"多久"） | 问"多久到账"被当要下单 |
| 2 | 澄清补答拼接 | 换话题的新问题 | 新话题被旧话题劫持 |
| 3 | 保留失败结果（防丢失） | 换措辞重试成功 | 陈旧 error 残留 → 误转人工 |
| 4 | 活跃对象推进 | 省略追问补全 | 补全串写坏对象句 → 三阶链断 |
| 5 | 澄清态正确响应 | 跨轮累积 | 第 1 轮的错误污染第 2 轮 |

### 1.2 为什么这类失效特别伤

- **静默**：不报错，`completed`、有引用、指标全绿。监控抓不到，只有对照用户原问题才发现"没答问题"。
- **不一致**：换个问法就好了。用户以为是自己问法不对，**不报障**——因此能存活数月。
- **随功能增长**：每加一个功能，接缝数量是加法、组合空间是乘法。

### 1.3 三个结构性根因

1. **判定是单句的，组合发生在时间轴上**——轮与轮的接缝没有归属。
2. **标签和字段丢掉了"为什么"**——`intent=business_operation` 丢掉了"是因为『赎回』"，于是语境变化（出现"多久"）时没有任何机制重新审视这个标签。
3. **共享状态多方写而生命周期无人声明**——同字段被多语义写、后写者抹掉先写者。

### 1.4 失效模式的严重度分级（所有改进的北极星）

```text
编造答案（合规事故） ≪ 答非所问（烦） ≪ 澄清/转人工（可接受）
```

无法保证不失效，但**必须锁定失效的下限**：宁可"没答到点上"，绝不"自信地编造"。证据门控、确定性翻译、转人工兜底的存在意义就是守住这个下限。

## 2. 七条设计规则（新增功能时的"宪法"）

评审新功能时逐条对照。

### R1 语境优先于词表

疑问词/指令词是**语境信号**，先判语境，再让触发词在语境约束下生效。已落地：三个重分类规则（`customer_intent.py` plan() 内）——裸「怎么」+ 事实对象 → `workflow`；解释词在场 → 补知识任务；办理触发词 × `_TIMEFRAME_MARKERS` 且无 `_ORDER_COMMAND_MARKERS` → 改判 `workflow`。

### R2 同义疑问词成组考虑，不许"遇到一个加一个"

「怎么」能答、「为什么」不能——这种不一致最容易被当成"模型偶尔不准"而长期存活。**规则：新增任何触发词前，先列出它的全部同义形式，一次接入；并用测试钉住"成组"事实。**

### R3 状态字段三要素

新增任何会话状态字段，必须同时声明：**唯一语义、生命周期（何时写/何时清/何时失效）、唯一权威写入者**。三者缺一，就不许进状态。落地：`app/services/customer_session_state.py`（`first_query` / `context_query` / `active_fact` / `latest_query`，各自生命周期写在模块头）。

### R4 合并结果时枚举所有字段，逐个判断"保留还是刷新"

**"最后一次调用"才是当前状态。** 重试成功后，首次失败的 `error/status/clarification` 必须清掉——否则下游判定读到陈旧结论。落地：`customer_model_tools.py` 同意图结果合并分支。

### R5 能用调用身份/确定性确定的，不要用自然语言再判一次

工具名已表达路由（`get_my_workorder_status` 就是查工单），不再要求 query 文本含对象词；有限枚举的含义用确定性翻译表（`_ORDER_STATUS_TEXT`），不丢给检索。

### R6 每个接缝配两类测试

1. **结构性守卫**（源码/AST 断言）——防止"同一能力只改一个承载方"、"整块覆盖写状态"、"守卫被顺手删除"。已有：AST 扫描 `save_short_term(patch=)`、两路径都接 `resolve_coreference`/`context_keys`/`merge_clarification_query`、状态机全覆盖。
2. **非平凡序列测试**——多轮缺陷（先失败后成功、澄清中换话题、三阶追问）在单轮测试里**必然**抓不到。已有：`test_three_turn_chain_holds_end_to_end_on_the_contract` 等。

### R7 失效可回溯

任何一轮对话都能从 `audit_logs`（工具轮轨迹）+ Redis hash（会话状态）还原。这是所有接缝缺陷能在小时级定位的前提，**属于功能，不是运维附属品**。

### R8 输入判定禁止硬阈值/强关键词/强正则；输出端允许确定性枚举翻译

- **输入判定**（这句话是什么意图？要不要打断？）——**禁止**关键词/正则/阈值。正解是语境（R1）+ 状态判据（本轮是否自足、pending 是否非空）+ **确认兜底**。
- **输出翻译**（这个枚举值对用户怎么表述？）——**允许且应当**用确定性映射表（状态码翻译、intent→业务名）。它不判定输入，只翻译已确定的输出。

落地范例：挂起任务可见化（`suspended_task_notice`）的触发条件全部来自状态（pending 非空 + 本轮 completed），文案引用用户原话，**零关键词、零正则、零映射表**；并有结构性自证测试禁止函数体内出现 `re.` 与任何信号词。

### 已建成的可靠性基础设施盘点

| 层 | 组件 | 作用 |
|---|---|---|
| 状态 | `customer_session_state.py` | 字段契约（语义/生命周期/唯一写入者）、拼接判据、指代消解唯一入口 |
| 状态 | `memory_service` 字段级写入 | Redis hash `HSET` + AST 守卫，消灭整块覆盖（lost update） |
| 判定 | `customer_intent` 重分类规则 | 语境优先于词表（3 条） |
| 执行 | `customer_model_tools` | schema 裁剪、结果回灌用 citations、引用并集、陈旧 error 刷新、停止信号、轮次预算告知 |
| 答案 | `customer_query_router` | 状态码确定性翻译（未知值不猜）、`route_hint` |
| 测试 | 760 单测 | 含 AST 守卫、结构性守卫、非平凡序列 |
| 测试 | `scripts/acceptance_dialogues.py` | 9 场景 16 轮多轮接缝回归（真实 HTTP） |
| 观测 | trace 面板 + `audit_logs` + BUG_LOG | 逐轮还原；BUG_LOG 记录被证伪的假设 |

### 流程性改进（对单人作战最重要）

改代码后的验证序列（顺序执行，不跳步）：

```text
1. pytest tests/ -q                     # ≥760，低了即回归
2. 对话回归（改意图/状态/工具轮/转人工时必跑）
   docker exec wealth-p0-api-1 python scripts/acceptance_dialogues.py   # 16/16
3. 改了模型可见上下文（提示词/回灌/schema）→ 按轮量 token，同会话连跑 ≥6 次
4. 涉及两路径的改动 → 双跑对照 compare_graph_vs_pipeline.py
5. 新场景手工多轮验收（至少 3 轮序列，覆盖"轮与轮的接缝"）
6. BUG_LOG 记录（必须含被证伪的假设与方法论教训）
```

新功能设计时的两个自问：

1. **它写入的每个字段，别的读者会读出什么？**（R3/R4）
2. **它依赖的前置判定，在什么语境下会变成错的？**（R1/R2）

验收即检测器：验收不是确认，是最贵的检测器。新功能上线前的手工验收必须按"非平凡序列"设计（正常轮→澄清轮→换话题→追问），而不是 happy path。

## 3. 打断判定树（挂起对象下的信号通道）

### 3.1 问题：同一个输入，在有挂起对象时是另一个意思

「算了」在没有挂起对象时是闲聊，「金额改 5 万」在没有挂起对象时是残缺问句——但当用户手里有一笔待确认草稿时，这两句分别是**放弃这笔**和**修改参数**。**含义不在句子里，在句子的语境里。**

实测缺陷形态：草稿卡出现后输入「算了」或「金额改 5 万」，前端 `isPurchaseIntent` 正则不命中 → 落到普通问答 → 草稿行完全没被触碰，仍停在 `awaiting_user_confirmation`，直到 15 分钟过期。用户以为取消了、系统认为还在。这是**状态分叉型缺陷**：双方对同一对象的认知不一致，且没有任何一方会报错——因为对象是**钱**，是"静默"家族里最贵的一类。

### 3.2 判定树

```text
本轮用户输入
   │
   ├─ 第 0 步 状态判据（零词表、零模型）：本客户此刻有挂起对象吗？
   │     · 澄清待补   ：context_query / pending_intent_plan 非空      （既有）
   │     · 待确认草稿 ：草稿表存在 awaiting_user_confirmation 且未过期  （新增）
   │
   ├─ 无挂起对象 → 常规规划（既有路径，行为一字节不变）
   │
   └─ 有待确认草稿 → 闭集归类（模型，每次至多一次调用）
         signal ∈ {keep, cancel, revise}
         │
         ├─ keep   → 正常回答 + 挂起提示（草稿仍在有效期内）
         ├─ cancel → 回问「确认放弃？」+ 行动卡
         │             └─ 用户确认 → 确定性取消接口 → cancelled + 审计留痕
         ├─ revise → 复述全部参数 + 行动卡
         │             └─ 用户确认 → 确定性改参接口 → 重跑全套预检 + 版本+1 + 令牌轮换
         └─ confirm→ 本通道**不做**（见 3.4 不变量 I2）
```

**入口唯一性**：挂在 `_run_customer_agent`（`app/api/customer_service.py`）——图/管线 × HTTP/WS 四种组合都会经它，两条 Agent 路径 + 两个传输通道只接一次。

### 3.3 为什么不是关键词表（R8 的正面回答）

1. **状态判据（第 0 步）**："有没有待确认草稿"是**查表事实**，不是语义猜测——R5 的直接应用。附带收益：绝大多数轮次（没有挂起草稿）**零模型调用、零新增开销**。
2. **语境归类**：把"这句话对**这笔草稿**而言是什么"交给模型，且**标签集是闭集（3 个）**。闭集归类比开集意图分类可靠得多——它不需要理解领域，只需要判断"相对这个对象"的关系。模型不可用/超时/无 key/输出非法 → **一律 `keep`**（失效下限：宁可不动）。
3. **确认兜底**：**归类的任何结果都不直接执行**，只产出"复述 + 回问 + 行动卡"。模型判错的代价被限制为**多问一句**，而不是"改错单/误取消"。

**参数抽取反而必须确定性**：新金额一律用既有解析器从**用户原话**抽（`parse_purchase_intent(...).amount`），**不采信模型给出的数字**——避免模型做算术或幻觉金额。抽不到金额 → 不构成修正 → 回问"要改成多少"。

### 3.4 三条不变量（各配守卫）

| # | 不变量 | 守卫 |
|---|---|---|
| I1 | **惰性**：无待确认草稿时，通道不产生模型调用、不读写任何状态、不改变控制流产物 | 无草稿场景断言零模型调用 + 走原路径 |
| I2 | **通道永不自执行**：任何归类结果都只产出文本 + 行动卡，执行必须经确定性接口 | 源码断言通道模块不 import 交易服务、不写库 |
| I3 | **失败不破坏**：归类失败、预检失败一律不改变既有草稿状态 | 改参失败的序列测试（失败后旧草稿仍可确认） |

**I2 里最需要解释的一条**：本通道**不实现"确认建单"**。建单必须携带令牌，而令牌只在草稿创建时下发；若在自然语言通道里复制一条建单路径，就会出现"**两条建单路径、其中一条没有令牌门禁**"。多一条路径就是多一个接缝，而这条路径通向的是**资金动作**。

### 3.5 取消分支与修正分支

**取消（"算了"）**：
- 通道只回问、不动手：返回 `overall_status="needs_confirmation"` + `draft_action.kind="cancel_pending"`，文案含草稿编号/产品/金额/有效期（引用真实字段）。
- 用户确认 → `POST /trading/order-drafts/{id}/cancel`：客户本人校验；状态必须 `awaiting_user_confirmation`，否则 409——**刻意不幂等吞掉**：对一笔"已确认建单"的草稿做取消必须报错而不是静默成功（静默成功会让用户以为订单被撤销了，而订单其实已经存在——那才是真正的资金事故）。
- 置 `cancelled` + `AuditLog(action="cancel_draft")`，detail 含原参数与指纹（R7 可回溯）。
- **副作用等级与令牌门禁的不对称**：取消是**降级动作**（草稿 ≠ 订单，无资金冻结），不要求确认令牌；而建单（confirm）必须带令牌。取消只能减少动作，改参只能收紧门禁。
- **为什么二次确认**：用户说"算了"可能是"算了不问了"，不是"算了不买了"；且草稿作废不可撤销。

**修正（"金额改 5 万"）**：
- 触发：`signal=revise` **且**从用户原话抽到了新金额（两个条件都要）。
- **复述必须复述全部关键参数**（产品、方向、原金额、新金额、有效期），不是只复述变化的那个数字。
- 确认 → `POST /trading/order-drafts/{id}/revise {amount}`：
  1. **重跑全套预检**（在售 → 起投金额 → 账户可用余额 → 风控限制 → 适当性）。**绝不只改金额字段**——金额变化会改变起投判定、余额判定与适当性结论。
  2. **预检不通过 → 旧草稿保持 `awaiting_user_confirmation` 不变**，只回失败原因（不变量 I3）。
  3. **预检通过 → 原地升版本**：`version+1`、重算 `input_fingerprint`、**轮换 `confirmation_token_hash`**（新令牌随响应返回给同一已认证客户）。
- **顺带得到的安全属性**：改参使旧确认令牌自动失效——`version` / `input_fingerprint` / `confirmation_token_hash` 三个字段本来就是为改参设计的，令牌轮换实现参数-令牌绑定，不需要新增机制。
- 幂等键 `nl-draft:{id}:v{version}` 天然按版本区分，同版本重复确认仍幂等。

### 3.6 已知缺口（诚实清单）

| # | 缺口 | 说明与建议 |
|---|---|---|
| 1 | **刷新丢令牌** | 草稿卡只存在前端内存，刷新后卡片消失、令牌不可再取。建议：待确认草稿改成从后端回灌（读表渲染），并把"进入待确认态即轮换令牌"标准化 |
| 2 | **前端输入判定仍是正则词表，且抢在后端通道之前** | `AgentBubble.isPurchaseIntent` 是 R8 的残留；草稿待确认时输入「申购 B 产品 3 万」会被前端直接建成第二笔草稿。建议：前端在存在待确认草稿时把话交给后端 |
| 3 | **多笔待确认草稿无约束** | 表上无 `(customer_id, status)` 唯一约束，通道只认最新一条。建议：改参/新建语义先收敛，再加约束 |
| 4 | **产品维度改参未支持** | 换标的等于换风险，应重走一次完整申购确认。本期只支持金额修正；模型判为 revise 但抽不到金额时，回问"要改成多少"而不是猜 |

## 4. 长时运行 Agent 断点续跑设计

### 4.1 问题与目标

已有长时运行场景：

| 场景 | 当前实现 | 风险 |
|---|---|---|
| AML 日批扫描 | `DailyAmlScanService` 扫描全部客户 | 单客户失败导致全批次重跑 |
| Agent 多意图查询 | `CustomerTaskExecutor` 执行多个子任务 | Worker 崩溃后客户需重新提问 |
| 知识库文档导入 | `KnowledgeIngestionService` + Embedding | 文档更新时全量重建向量 |
| 客服 ReAct 推理 | 多轮 LLM 调用 | 第 3 轮崩溃后前 2 轮 Token 浪费 |
| 外部 API 等待 | 未来对接银行/支付接口 | 进程阻塞，无法释放资源 |

设计目标：

1. **任务级恢复**：Worker 崩溃后，从断点继续执行，不重跑已完成步骤
2. **会话级恢复**：Agent 多轮推理可中断恢复，不浪费已消耗的 Token
3. **批次级恢复**：批量扫描中单个客户失败不影响其他客户
4. **外部等待恢复**：长时等待不阻塞 Worker，通过 Webhook 唤醒

已有基础设施：`AsyncTask`（任务状态、重试次数、失败原因、幂等键）、`OutboxEvent`（事件持久化、重试、死信）、`AmlBatchRun`（批次幂等、失败客户统计、补跑入口）、`WorkOrder` 状态机（`pending_customer` 暂停-恢复）、`CustomerServiceSession`（`waiting_human → human_active → paused`）、LangGraph（`MemorySaver` / `AsyncPostgresSaver` 原生支持）、Redis 短期记忆（会话级 `TaskPlan`、`task_results`）。

**缺口**：这些能力散落在不同模块，没有统一到 Agent 执行层——`CustomerTaskExecutor` 执行到一半崩溃后无法恢复、`DataAnalysisAgent` 的批准模板执行无快照、Agent 调用外部 API 无等待恢复机制。

### 4.2 总体架构：三层恢复模型

```text
┌─────────────────────────────────────────────────────────────────┐
│                    请求层（客户/内部用户）                       │
├─────────────────────────────────────────────────────────────────┤
│              会话级恢复（LangGraph Checkpointer）               │
│         多轮 LLM 推理中断后从 Checkpoint 继续                   │
├─────────────────────────────────────────────────────────────────┤
│              任务级恢复（Agent Execution Snapshot）             │
│         多意图任务执行中断后从快照恢复                          │
├─────────────────────────────────────────────────────────────────┤
│              批次级恢复（AmlBatchRun + 补跑）                   │
│         批量扫描中单个客户失败不影响其他客户                    │
├─────────────────────────────────────────────────────────────────┤
│              外部等待恢复（Outbox + Webhook）                   │
│         长时等待不阻塞 Worker，回调后唤醒                       │
└─────────────────────────────────────────────────────────────────┘
```

| 层级 | 适用场景 | 恢复粒度 | 存储位置 |
|---|---|---|---|
| 会话级 | 客服/投顾 Agent 多轮推理 | 单个 LLM 调用轮次 | PostgreSQL `checkpoint` 表 |
| 任务级 | 多意图任务执行 | 单个子任务 | Redis 快照 + `AsyncTask.payload_json` |
| 批次级 | AML 日批扫描 | 单个客户 | `AmlBatchRun.metadata` |
| 外部等待 | 银行接口/人工审核 | 单个外部请求 | Redis 快照 + `AsyncTask` 状态 |

### 4.3 Phase 1：Agent 执行快照

目标：`CustomerTaskExecutor` 执行多意图任务时，Worker 崩溃后重启能从断点继续，而不是让客户重新提问。

#### 快照 Schema

```python
# app/schemas/agent_snapshot.py
class AgentExecutionSnapshot(BaseModel):
    """Agent 执行快照，用于断点恢复"""
    # 会话标识
    conversation_id: str
    user_id: str
    # 原始请求
    original_query: str
    created_at: datetime
    # 任务计划
    task_plan: List[IntentTask]
    total_tasks: int
    # 执行状态
    completed_task_ids: List[str] = []
    current_task_id: Optional[str] = None
    failed_task_id: Optional[str] = None
    subtask_status: Dict[str, str] = {}  # pending | running | completed | failed
    # 已完成结果
    tool_results: Dict[str, Any] = {}  # task_id → result
    # 恢复控制
    resume_count: int = 0
    max_resume_count: int = 3
    # 时间戳
    last_checkpoint_at: datetime
    expires_at: datetime  # 默认 7 天
```

`AsyncTask` 模型扩展：新增 `conversation_id`（索引）、`snapshot_json`（JSON）、`external_request_id`（索引）；status 增加 `waiting_external`：

```text
status: queued | running | waiting_external | success | failed | dead
```

#### 快照存储（Redis + AsyncTask 兜底）

```python
# app/repositories/agent_snapshot.py
class AgentSnapshotRepository:
    """Agent 快照读写（Redis + AsyncTask 兜底）"""

    async def save(self, snapshot: AgentExecutionSnapshot) -> None:
        # 1. Redis 短期存储（TTL 7 天）
        key = f"agent:snapshot:{snapshot.conversation_id}"
        await self.redis.setex(key, 7 * 24 * 3600, snapshot.model_dump_json())
        # 2. AsyncTask 持久化兜底（用于 Worker 重启恢复）
        await self.async_task_repo.update_snapshot(
            conversation_id=snapshot.conversation_id,
            snapshot_json=snapshot.model_dump())

    async def load(self, conversation_id: str) -> Optional[AgentExecutionSnapshot]:
        # 1. 尝试 Redis
        data = await self.redis.get(f"agent:snapshot:{conversation_id}")
        if data:
            return AgentExecutionSnapshot.model_validate_json(data)
        # 2. 兜底：从 AsyncTask 恢复
        task = await self.async_task_repo.get_by_conversation(conversation_id)
        if task and task.snapshot_json:
            return AgentExecutionSnapshot.model_validate(task.snapshot_json)
        return None

    async def delete(self, conversation_id: str) -> None:
        """快照完成或过期后清理"""
```

#### 执行器改造要点

```python
# app/services/customer_task_executor.py
async def execute(self, conversation_id: str, query: str, user_id: str):
    # 1. 尝试恢复快照
    snapshot = await self.snapshot_repo.load(conversation_id)
    if snapshot and snapshot.resume_count < snapshot.max_resume_count:
        return await self._resume(snapshot)
    # 2. 首次执行：生成任务计划并保存快照
    ...

async def _execute_loop(self, snapshot):
    for task in snapshot.task_plan:
        if task.task_id in completed:
            continue  # 已完成，跳过
        snapshot.subtask_status[task.task_id] = "running"
        await self.snapshot_repo.save(snapshot)       # 执行前保存
        try:
            result = await self._execute_task(task, snapshot)
            # 每完成一个任务就保存快照
            snapshot.subtask_status[task.task_id] = "completed"
            snapshot.last_checkpoint_at = datetime.utcnow()
            await self.snapshot_repo.save(snapshot)
        except Exception:
            snapshot.subtask_status[task.task_id] = "failed"
            snapshot.failed_task_id = task.task_id
            await self.snapshot_repo.save(snapshot)
            raise
    await self.snapshot_repo.delete(snapshot.conversation_id)
```

#### Worker 启动恢复

```python

class AgentRecoveryWorker:
    async def recover_pending_tasks(self):
        # 1. 查询未完成的 Agent 任务（task_type="agent_execution"，
```

#### 验收标准

| 场景 | 预期行为 |
|---|---|
| Worker 执行第 3 个任务时被 kill | 重启后从第 3 个任务继续 |
| 客户页面刷新 | 展示已完成的中间结果，不丢失 |
| 同一会话重复提交 | 复用已有快照，不重复执行 |
| 快照过期（7 天） | 自动清理，客户需重新提问 |
| 恢复超过 3 次 | 标记失败，转人工处理 |

### 4.4 Phase 2：LangGraph Checkpointer（已接入）

> 实施状态：`app/agents/checkpointer.py`（`memory_checkpointer` / `postgres_checkpointer` / `thread_config` / `with_interrupt`）已接入；`SupervisorGraph.build(checkpointer=..., interrupt_before=..., interrupt_after=...)` 已支持。**MemorySaver 可用并测试通过**（`tests/test_agent_graph.py` 覆盖"summarize 前中断→恢复续跑→完成"）。**AsyncPostgresSaver 代码就绪**，需装 `langgraph-checkpoint-postgres` 额外包 + DB。

目标：客服 Agent 的多轮 LLM 推理（ReAct 循环）可以中断恢复，避免重复消耗 Token。

```python
# app/agents/graph.py
from langgraph.checkpoint.postgres import AsyncPostgresSaver

checkpointer = AsyncPostgresSaver(async_engine)

async def build_customer_agent_graph():
    workflow = StateGraph(AgentState)
    # ... 添加节点和边 ...
    return workflow.compile(checkpointer=checkpointer)
```

执行时以 `conversation_id` 作为 `thread_id`：

```python
config = {"configurable": {"thread_id": conversation_id}}
# 首次执行
result = await self.graph.ainvoke({"messages": [HumanMessage(content=query)]}, config=config)
# 断点恢复时，用同一个 thread_id 再次调用
# LangGraph 自动从上次中断处继续，不重放已完成的步骤
result = await self.graph.ainvoke(None, config=config)
```

Checkpoint 存储在 PostgreSQL 表 `checkpoints` / `checkpoint_writes` / `checkpoint_blobs`（由 AsyncPostgresSaver 自动创建）。配 `CheckpointCleanupWorker` 定期清理 7 天前的过期 Checkpoint（调用 `checkpointer.delete_threads_before(cutoff)` 或直接 SQL），防止表膨胀。

**与 Phase 1 的关系**：两者互补——Phase 1 负责"哪些子任务已完成"（Redis + AsyncTask），Phase 2 负责"当前 LLM 推理到哪一步"（PostgreSQL）。

验收：ReAct 循环执行到第 2 轮时 Worker 崩溃 → 重启后从第 2 轮继续；恢复时不重复调用前几轮的 LLM（Token 消耗不增加）；`checkpoints` 表有对应记录可审计；7 天后自动清理。

### 4.5 Phase 3：AML 批次完整恢复

目标：`DailyAmlScanService` 扫描全客户时，单个客户失败不影响其他客户，且支持定向补跑。已有基础：`AmlBatchRun` 记录批次状态和 `error_summary`、`POST /risk-alerts/batches/{batch_id}/retry` 补跑入口。

核心：批次内客户级断点——从批次元数据读取已成功客户集合，逐个客户扫描，每成功一个就更新 `metadata.succeeded_customer_ids`，失败记录后**继续下一个客户**（不中断批次）：

```python
metadata = batch.metadata or {}
succeeded_ids = set(metadata.get("succeeded_customer_ids", []))
for customer in customers:
    if customer.id in succeeded_ids:
        continue  # 已成功，跳过
    try:
        await self._scan_customer(customer, batch)
        succeeded_ids.add(customer.id)
        metadata["succeeded_customer_ids"] = list(succeeded_ids)
        await self._update_batch_metadata(batch, metadata)
    except Exception as e:
        await self._record_failure(batch, customer.id, str(e))
        # 不中断批次
```

迟到流水补扫使用独立 batch_key，不覆盖原批次：

```text
daily_aml:late_rescan:{source_batch_id}:{days}:{window_start.isoformat()}:{window_end.isoformat()}
```

验收：5000 客户扫描第 300 个失败 → 批次状态 `completed_with_errors`；调 retry → 从第 300 个客户继续，不重扫前 299 个；补扫重复调用幂等复用已有补扫批次。

### 4.6 Phase 4：Webhook 唤醒长时等待

目标：Agent 调用外部 API（如银行接口、人工审核）需要等待数分钟甚至数小时，进程不阻塞。

数据模型 `ExternalWaitState`：`conversation_id`、`task_id`、`external_request_id`、`callback_url`、`status`（waiting | completed | failed | timeout）、`created_at`、`expires_at`（默认 24 小时）、`result`。

发起外部调用的流程：

1. 生成 `external_request_id = f"ext_{uuid4().hex[:16]}"`；
2. 保存等待状态（callback_url = `/api/v1/webhooks/external/{external_request_id}`）；
3. 更新快照子任务状态为 `waiting_external`；
4. 异步发起外部调用（提交即返回，不等待）；
5. 返回 `AgentResult(status="waiting_external")`，释放 Worker。

Webhook 回调唤醒：

```python
@router.post("/external/{request_id}")
async def external_callback(request_id: str, payload: Any, background_tasks: BackgroundTasks):
    wait_state = await ExternalWaitRepository.get(request_id)
    if not wait_state:
        raise HTTPException(404, "EXTERNAL_REQUEST_NOT_FOUND")
    wait_state.status = "completed"
    wait_state.result = payload
    await ExternalWaitRepository.save(wait_state)
    # 后台恢复执行（不阻塞回调响应）
    background_tasks.add_task(resume_agent_execution,
                              conversation_id=wait_state.conversation_id,
                              external_result=payload)
    return {"status": "accepted"}
```

恢复执行：加载快照 → `_resume_with_external_result` 继续执行 → 通过 WebSocket 通知客户端。

验收：Agent 调用外部 API 立即返回 `waiting_external` 不阻塞；外部回调后从断点继续；24 小时无回调自动超时转人工。

### 4.7 实施优先级与风险

| 阶段 | 内容 | 工期 | 紧急度 | 依赖 |
|---|---|---|---|---|
| Phase 1 | Agent 执行快照 | 2-3 天 | 高 | 已有 AsyncTask + Redis |
| Phase 3 | AML 批次完整恢复 | 1-2 天 | 高 | 已有 AmlBatchRun + 补跑接口 |
| Phase 2 | LangGraph Checkpointer | 3-5 天 | 中 | 已安装 langgraph |
| Phase 4 | Webhook 唤醒 | 3-5 天 | 低 | 已有 Outbox + WebSocket |

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Redis 快照丢失 | Agent 无法恢复 | AsyncTask 兜底持久化 |
| Checkpoint 表膨胀 | PostgreSQL 性能下降 | 定期清理 Worker |
| Webhook 回调丢失 | 外部等待永久挂起 | 超时机制 + 人工兜底 |
| 快照版本不兼容 | 旧快照无法恢复 | 版本字段 + 迁移脚本 |

### 4.8 核心设计原则

1. **渐进式增强**：不推翻现有架构，在已有组件上叠加恢复能力
2. **分层恢复**：会话级、任务级、批次级、外部等待级各司其职
3. **至少一次投递**：Outbox + Redis Streams 保证事件不丢失
4. **幂等是关键**：所有恢复操作必须幂等，防止重复执行
5. **审计可追溯**：所有恢复操作写入审计日志

> 一句话概括：**断点续跑不是从零建设，而是把 AmlBatchRun 的批次恢复、WorkOrder 的状态暂停、AsyncTask 的任务重试、LangGraph 的 Checkpointer 这四件事，统一到 Agent 执行层。**

### 4.9 恢复机制的故障注入评测

断点续跑落地前应注入以下故障做评测（对应评测指南要求）：Worker 崩溃、超时、外部等待、重复回调、权限变化和已完成步骤重放，验证恢复成功率和重复执行风险。
