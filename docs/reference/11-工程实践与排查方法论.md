## 1. 一次长链排查：从"答案重复"到 8 层缺陷

### 1.1 起点

```
query = 你们公司的主营业务是什么
pipeline task t1 company_info     答：基金销售 + 保险经纪
pipeline task t2 company_business 答：基金销售 + 保险经纪      ← 与 t1 几乎相同
graph    同样两个 task，答案也重复
```

第一反应（错的）：规划器"过度拆分"。实际情况：拆分是对的，是下面八层里出了各种问题。这一个症状背后是 **8 层相互独立的缺陷**，跨语料、索引、检索、意图、编排、数据、生成七个层面——**单修任何一层都不够**，这也是中途多次出现"修好了但现象仍在"的原因。

### 1.2 八层缺陷逐层剥开

**第 1 层：语料 —— 权限错配导致"孤儿数据"**

- 现象：`company_business` 意图检索回 5 条文档全部是 `company_info` 类目；top_k=25 也一条都检索不到（而库中有 39 个该类目 chunk）。
- 根因：对账脚本发现 39 个 chunk 的权限是 `staff`，而 `staff` **不在任何客户 scope 的允许列表里**——是没有任何 scope 能取到的孤儿内容。另有 `faq` 类目是测试残留、`business` 类目名与代码用的 `company_business` 不符。
- 解决：新写客户可见语料并**导入前校验**（拒绝孤儿权限与错配类目）；清理测试残留。原始内部文档权限标 `staff` 本身没错，错的是意图把它当客户可见资料。
- 关键修正：一度认为是"类目过滤没生效"，部分成立但主因是权限——权限先把它拦掉了，与类目无关。

**第 2 层：镜像 —— 语料没进容器**

- 现象：容器内导入脚本报"文件不存在"，但文件在仓库里明明存在。
- 根因（两处叠加）：`Dockerfile.api` 没有 `COPY knowledge_corpus`；且 `.dockerignore` 含 `*.md`，把 4 个作为**数据用的** markdown 语料全部排除——即便补了 COPY 也拷不进去。
- 解决：加 COPY；`.dockerignore` 加两条例外（仅写目录名无法让目录内文件生效），顺序须在 `*.md` 之后。用 `tests/test_corpus_image_wiring.py` 固定该配置，并**验证测试能失败**（回退修复后 3 failed）。

**第 3 层：索引 —— BM25 写入全面失败（P0）**

- 现象：导入报 `No key field defined`；最小写入、裸 INSERT 同样失败——**该表上任何写入都不行**。当时就该意识到这不是导入脚本的问题。
- 排查（三次推断，两次被数据推翻）：

| # | 推断 | 结果 |
|---|---|---|
| 1 | 配置是 tsvector、BM25 索引是遗留物 | 证伪：`FULLTEXT_BACKEND=pg_search`，索引真在用 |
| 2 | 索引由旧版 DDL 创建，key_field 无法解析 | 证伪：`reloptions=['key_field=id']` 且查询可用 |
| 3 | 索引元数据陈旧，REINDEX 可修 | 证伪：REINDEX 成功但写入仍失败 |

- 关键转折：注意到**读写不对称**——读侧正常、写侧失败。若 key_field 真无法解析，查询也会失败，故问题只在写入路径。
- 最终定位（临时表对照实验）：`key_field` 指名的列**必须出现在索引字段列表中**（`bm25 (id, content)`），只写在 `WITH` 里不够；B 形态（`bm25(content) WITH key_field='id'`）能建索引、能查询，但任何 INSERT 都报错。
- 过程中的坑：ParadeDB 一表只能有一个 bm25 索引，"先建新再切换"架构上不可能，只能单事务 DROP+CREATE+写入探测、失败整体回滚；而诊断脚本自身有个 bug——探测无论成败都 `session.rollback()`，会把同事务的 DROP+CREATE 一起撤销却报告"成功"（**假成功**），改用 SAVEPOINT 并用 sqlite 做反例验证。
- 附带发现：该索引不在版本管理内，故与扩展版本脱节而无人察觉；已补 migration。

**第 4 层：检索 —— 各意图共用 scope，检索同一批文档**

- 现象：语料修好后，两个 intent 的检索结果仍逐字节相同（Jaccard=1.000）。
- 三口径对照实验：

| 口径 | 做法 | Jaccard | 相似度虚高 |
|---|---|---|---|
| 现状 | 向量腿=原始 query，scope 全开 | 0.708 | 0 处 |
| 改嵌入源 | 向量腿=各自 normalized | 0.448 | 5/6 组虚高 |
| scope 收窄 | scope 各自类目 | 0.000 | 0 处 |

- "改嵌入源"被否决：它把相似度抬高了 0.046，**跨过 answer=0.65 阈值**，等于绕过证据门控。"收窄"被采纳：分化彻底且相似度零虚高。
- 但必须按意图分别决定——全意图实验显示 `workflow`/`risk_public` 语料为 0，收窄即答不出。解决：`_NARROWABLE_INTENTS` 只收窄有语料的 3 个意图，**不能一刀切**。
- 同时发现一个"冗余设计"：两个意图的扩展词只喂给文本腿，决定排序的向量腿用同一个原始 query 嵌入，故结果必然相同。这不是 bug，是设计未达成意图。

**第 5 层：意图 —— `policy` 从不触发（P1）**

- 现象：反查 31 条候选问句，`policy` 意图**无任何问句可触发**（"什么是双录"→unknown），而 policy 类目下有 24 个 chunk——**合规类问题走不到那批资料**。
- 根因：policy 的唯一触发词是"政策"，用户不会问"什么是政策"，而是问制度名词。
- 修复走了三版才到位：第一版加裸词导致**过度触发**（"开户有什么规定"只命中 policy，正确答案 workflow 丢失——比多一个 task 更糟）；第二版又过度收紧退化成 unknown；第三版补回制度域搭配 + 流程类说法达到平衡。
- 教训：触发词是**精确率与召回率的权衡**，需要**双向验证**（该命中的命中 + 不该命中的不命中）。
- 深层认识：**意图从不触发，比意图映射错误更隐蔽**——映射错会答非所问（有输出、可发现），从不触发则表现为"走到别的意图"，看上去像识别能力不足。

**第 6 层：数据 —— `risk_restriction` 不读风险等级**

- 现象：答案自相矛盾（"当前未显示风险限制，但存在一条待处理风险记录……是的，您有风险限制"），而 `overall_status` 报 `completed`——状态机看不出问题。
- 根因（两层）：`risk_restriction` 只读账户的限制状态字段，**从不读客户风险等级**（C1-C5）；而 `summarize` 只把各 task 的 answer 换行拼接、intent 完全丢弃——缺的是"用事实套规则"的比对步骤。
- 关于状态机的关键认识：`summarize` 的输入只有每个 task 的 status，两个 task 确实各自都成功了，必然判 completed。**不是状态机判错了，而是它根本没在看这件事**——现有维度是[完成度]，缺少[一致性]。不建议"再加一个状态值"：自相矛盾需要跨 task 语义比对，没有廉价确定的判据，用 LLM 判定则引入误判/不可复现/成本。
- 解决：`risk_restriction` 补读风险等级，按测评状态分措辞。

**第 7 层：编排 —— graph 不遵守 `depends_on`，事实不传递**

- 现象：C4 客户问"我有没有风险限制"，pipeline 答对了，graph 答"未包含您的具体风险评估得分"——而它明明查到了 C4。
- 根因（读码确认）：`model_tool_node` 把 plan.tasks 压成一串意图名一次性交给模型循环，`depends_on` 完全不可见——既不参与调度，前序答案也不传递，结果取决于模型是否碰巧记住。
- **第一次尝试（失败，已回退）**：在工具循环内部做"确定性工具预执行"，连打三版补丁都被测试击退——各自打破不同类别的约束（精确匹配去重失效 / 跳过越界安全校验 / 空转到预算耗尽）。
- 回退换落点：改为在 `model_tool_node` **按 `depends_on` 拓扑分层**（同层并行、层间串行），层间用 `prior_facts` 传事实——**一次通过，既有测试零改动**。
- 分层后又引入三个缺陷并修掉：task_id 重名（加层前缀）、轨迹混叠（按层保存按 `data.layer` 附加）、停止原因不可读（按层拼接）。其中"轨迹混叠"修了两次：第一次改了 runner 并加测试 → 测试通过但实际无效；第二次才发现真因是 `model_tool_layer_traces` **未在 AgentState 声明**，LangGraph 把未声明的顶层键**静默丢弃**（不报错不告警）。
- 为何第一次没抓到：测试是"直接调用节点 + 手工合并 patch"，**绕过了真实图的状态归并**，而状态的归并规则正是被测对象。已新增"用真实 StateGraph 跑一遍"的测试。

**第 8 层：生成 —— 制度 task 编造个人事实 + 事实到不了生成阶段**

- 现象 A（编造）：policy/risk_public 检索的是制度文本、无从知道客户个人状态，但其检索 query 是用户原问句（"我有没有风险限制"），模型顺着问句直接断言个人事实。
  - 关键判断：**不靠改写检索 query 解决**——实测改写后相似度从 0.5820 掉到 0.5242 跌破阈值（改写丢掉了语境词）。只在生成提示里加角色约束：只陈述制度规定、绝不断言"您有/您没有"、不用假设例子替代结论。
- 现象 B（矫枉过正）：约束生效后变成通篇讲通用规则、完全不提 C4。根因是**同一件事 pipeline 做了、graph 没做**——pipeline 把依赖上下文附到生成 query，graph 的 generate_node 对所有 task 一律用原问句。
- 解决：分层时把事实写入每条结果的 `data.prior_facts`，`generate_node` 读取并并入**生成** query。放 `data` 而非 AgentState 顶层键——`task_results` 是自由形态 dict 列表，内部键不会被 LangGraph 过滤（吸取第 7 层教训）。

### 1.3 长链排查方法论总结（比具体修复更可复用）

1. **先补观测，再谈诊断**。第 7 层最初无法排查，是因为模型自述理由（`message.content`）在产生那一刻就被丢弃了。在断言某个模型行为倾向之前，先确认动机证据是否被保存——若观测通道本身被丢弃，"模型就是爱这样、改不好"不是结论，是**缺数据的症状**。
2. **能跑的探测 > 推理**。第 3 层连错三次推断，每次都被一个具体探测推翻；真正解决问题的是临时表对照实验，一次就指出唯一可行形态。若早做对照实验，能省下三轮。
3. **单样本不能下机制性结论**。本议题至少三次因单样本下错判断（"多意图拆分无增量""模型改写更差""图有合规问题"）。集合类指标必须多次采样；LLM 输出缺陷需先排除随机性。
4. **打补丁打不动时，质疑方案本身**。连续多版补丁各自破坏不同类别的约束，是"方案与结构不契合"的强信号，正确动作是回退并重新选落点。
5. **"节点返回了某键" ≠ "状态里能读到该键"**。测状态传递必须走真实图；"直接调用 + 手工合并"模拟的是想象链路。
6. **一个用户可见症状，常是多层缺陷叠加**。
7. **一个字段承担不了两个正交维度**。`overall_status` 表达完成度，无法表达一致性；加值只能覆盖"它能测量的"那一类问题。

## 2. BUG 台账提炼：系统性教训

280+ 条缺陷台账中反复出现的坑，可以归为六类：

### 2.1 高频坑类别

| 类别 | 典型特征 | 代表条目 |
|---|---|---|
| **静默失效** | 出错不报错，用默认值/空结果继续跑 | 配置从未加载、`except: pass` 吞异常、LangGraph 丢弃未声明键、文档 status=failed 被静默排除 |
| **接缝问题** | 两段各自正确、接缝处丢信息 | 事实类意图被压成模板桶后丢失、模型自述理由被丢弃、失败提示鼓励无效重试 |
| **配置分层不一致** | 代码默认 ≠ compose 默认 ≠ 文档表述 | LLM 回退"默认关闭"实际线上开启、开关未透传容器、双 compose 共端口 |
| **词汇/口径漂移** | 同一概念两套叫法、两套实现 | 语料 R1–R5 vs 数据库 C1–C5、等级比对规则两处分叉、同一文案两处定义 |
| **环境差异** | 本地过、容器挂；共享资源互踩 | 容器无 libpq、镜像源/tag 兼容、nginx 缓存旧容器 IP 502、双 compose 容器名冲突 |
| **评测陷阱** | 单样本下结论、评测参数造成假象、test 污染 | RRF top_k 截断假象、few-shot 含 test 原文、假 client 污染指标文件 |

### 2.2 代表性案例

**案例一：配置运行时从未加载（静默回退默认）**

`config/understanding.yaml` 相关的难度路由、灰度、检索参数**可能从未在生产生效**。根因两个叠加：① 路径计算多套了一层 `os.path.dirname()`，配置文件解析到不存在的路径；② 全仓库只有测试调用 `reload()`，模块级单例创建后 `_data` 恒为空。**长期未被发现的原因**：多数代码默认值与 yaml 恰好一致，掩盖了"配置未加载、一直在用默认参数"。

> 推论：凡是"模块级单例 + 需要外部加载"的设计，都要问一句"谁负责初始化它？没初始化会怎样？"——本例的答案是"静默用默认值"。

**案例二：记忆持久化 `except: pass` 静默吞错**

用户说"我比较激进"后偏好未落库。根因两层：① 部分 query 被 Agent 先拦截，没走到统一 `execute()` 的持久化点；② `conversation_id` 列是 `VARCHAR(36)`，带前缀的 id 超长触发 `StringDataRightTruncationError`，且被 `except: pass` 吞掉。教训：**持久化失败静默吞掉 = 数据丢失且无告警**；列宽按业务最坏情况给足。

**案例三：高置信事实类意图被降级成 faq（接缝丢信息）**

线上用户问"查一下我的持仓"被回复"没有足够依据、建议转人工"——而数据就在库里。排查先排除了阈值问题：高置信保护**确实生效**，但保护结果下一步被丢弃——映射表把 16 种意图压成 4 个模板桶，信息在映射那一步就丢失，之后无论怎么保护都无法恢复。修复是**让原始意图穿越整个流程**：resolver 判定规则胜出时原样返回 plan，绝不用有损模板重建。

**案例四：judge 故障伪装成"知识库没有依据"（P1）**

同一问句时好时坏。三个假设前两个被探针证伪（检索是确定性的；4 种改写全部 sufficient），第三个证实：best_sim 落在 judge 裁决区间时，答案取决于一次额外 LLM 调用，而旧代码 `except Exception: judge_result = False` 把**"没跑成"当成"判为证据不足"**。即：限流/超时/网络抖动被伪装成事实性结论"知识库没有依据"，用户因此被转人工。修复：区分"judge 判为不足"与"judge 没跑成"，故障时退回确定性阈值兜底——**组件故障不应改变业务结论**。

**案例五：文档说"默认关闭"，线上实际开着（配置三层）**

6 份文档都写"LLM 回退默认关闭"，实际生产 compose 里 `${LLM_INTENT_FALLBACK_ENABLED:-true}` 是开启的。排查时正是被这一表述误导，把生产降级缺陷当成"仅 shadow 模式"而未优先处理。

> 通用教训：排查"某能力是否生效"时，必须追到部署清单（compose）的最终值，不能只看代码默认值。默认值有三层：代码默认 / compose 覆盖 / 本地 .env，文档只写其中一层就会误导。

**案例六：LangGraph 静默丢弃未声明键**

`AgentState` 没有 `clarification` 字段，而 LangGraph 会**静默丢弃**节点返回的未知键（不报错）→ 澄清话术从未进入 state。另一处：图与管线共享 handler 但图缺 4 个持久化副作用（澄清计数落库、转人工建单、短时记忆回写、情景记忆入队），直接切流会功能回归。还有一处部署接缝：容器 environment 是**白名单**，双 compose 只改一个会静默失效。

**案例七：nginx 缓存旧容器 IP 导致 502**

API 直连健康、走 nginx 502。根因：`proxy_pass http://api:8000` 在启动时把容器名解析成当时 IP 并缓存；CI/CD 每次重建 api 容器换新 IP，frontend 未随之重建 → 一直连旧 IP。解决：`resolver 127.0.0.11 valid=10s` + 变量式 `proxy_pass` 运行时解析。教训：**容器化环境下 IP 会漂移，任何"启动时解析一次"的配置都会过期**。

**案例八：语料词汇与数据模型不一致**

知识库文档用 R1–R5，而 `product.risk_level` 实际是 C1–C5（R1–R5 在数据模型中根本不存在），答案同一句话混用两套词汇（"C4 进取型可购买 R1 至 R4"）。修复时发现语料有两个来源，只改一个会漏（第一次就漏了 policy 目录）——最终统一 72 处 + 导入期词汇校验。

### 2.3 被证伪的假设清单（避免重复走弯路）

台账中明确记录"推断 → 被证伪"的案例，方法论价值高于修复本身：

| 被证伪的假设 | 证伪方式 | 教训 |
|---|---|---|
| "多 worker 无提升" | 压的是旧单 worker 容器（共享端口） | 压测前先确证被测实例 |
| "qwen-plus 在 tool_choice=auto 下太慢导致 16.8s 超时" | 三模型 × 8 query 实测：p95 最大仅 1.6s | 归因前先测数据；顺手把"模型选型"变成可复现的延迟+匹配率对比 |
| "检索集合在边界抖动，单次采样不可信" | 同一 query 重复采样 8 次：8/8 完全相同 | 提出假设后**先设计证伪实验**，而不是照着假设改代码 |
| "图丢掉了已成功的答案" | task 级明细探针：两个 task 都失败，图没丢答案 | 聚合指标看不到 task 级差异 |
| "模型不肯调第二个工具" | 诊断脚本打印中间值：模型主动调了 3 次且全部失败 | 三轮"修复"修的都是不存在的问题 |
| "embedding 降级导致拒答" | 读码：`best_sim=None` 明确不拒答 | 初始推断经实测证伪 |
| "Function Calling 的 arguments 保证合法 JSON" | 长 few-shot 下偶发截断/畸形 | API 行为要有兜底，不能信文档 |
| "BM25 索引是遗留物 / key_field 解析不了 / REINDEX 可修" | 三个推断各自被具体探测推翻 | 读写不对称是关键线索；对照实验一次定位 |
| "prompt 没写导致 X" | 先证伪"最省事的假设"再往下走 | 省事假设往往最先被推翻 |

还有一条反向教训：**"三层证伪"只排除那三层，不自动指向根因**——证明了后端对、产物对、浏览器加载对，仍然到不了真正的答案（最终根因在别处）。证伪能缩小范围，但不能替代对未知区域的探查。

## 3. 设计级 vs 上线级差距

架构/异步/安全/数据正确性达到生产级设计水准后，距离"可上线"还差**运营化最后一公里**。按优先级归类的差距清单（P0 = 上线前必做）：

| 领域 | P0 项 | 说明 |
|---|---|---|
| CI/CD 与质量门禁 | CI 流水线、测试门禁、发布流水线（打 tag → 构建 → 滚动/蓝绿 → 回滚预案） | CI 已存在；核心测试集须入 CI、失败即阻断 |
| 可观测性 | 指标采集（Prometheus）、可视化 + 告警（P95 超时、错误率、dead 事件、队列积压） | 异常要能**主动告警**而非靠用户报障 |
| 压测与容量 | 生产级接口压测报告、并发正确性压测（幂等唯一索引、FOR UPDATE 下 0 重复单） | 本地基准 ≠ 生产级全链路 |
| 安全加固 | 密钥外置（仓库无真实密钥）、生产关闭演示账号、强制 TLS + CORS 白名单 | `.env` 明文入库与确定性演示密码是两个高危项 |
| 部署与基础设施 | Worker 进程管理（systemd/k8s + 健康检查）、反向代理网关、环境隔离（生产禁止演示数据/调试开关） | 裸 `asyncio.run(main())` 崩了没人拉起 |
| 备份恢复 | PG 定时全量 + WAL/PITR、**定期恢复演练** | 没有 RTO/RPO 目标的备份等于没备份 |
| 仓库卫生 | 构建产物不入库、垃圾文件清理、密钥残留扫描（gitleaks）、依赖锁版本 | 构建可复现 |

P1 层包括：迁移自动验证、双库契约回归、依赖漏洞扫描、结构化日志、容量规划、慢查询治理、密钥轮换、最小权限运行、多实例水平扩展、连接池校准、上传内容安全、前端权限驱动与交易意图收敛等。

一句话结论：从"设计级"到"上线级"**不用重写**，缺的是运营化这最后一公里。

## 4. "实现了但没接线"的清单与启示

### 4.1 接线现状

**"确定性执行底座"几乎全部已接线**：Agent 编排管线、交易状态机 + 风控闸门、订单幂等（DB 唯一索引）、RBAC + Subject Scope、RAG 全链路（上传→outbox→worker→embedding→pgvector→混合检索→转人工）、受控 NL2SQL、短期/长期记忆、Outbox + Worker + 死信。

**定义了但没真接（或曾没接）的能力**：

| 能力 | 状态 | 启示 |
|---|---|---|
| LangGraph 真图 | 曾"实现 + 单测齐全但 0 个调用方"；后经三开关渐进接线（默认关），切流前补齐 4 个持久化副作用，用影子双跑对照验收 | **有单测 ≠ 在生产路径上**；切流必须双跑对照 |
| 通用任务分发 `runner.execute` | AsyncTask 表/重试/死信就绪，execute 是占位，不按 task_type 分发 | 基础设施先于业务是合理阶段化，但要明示 |
| Milvus 生产检索 | adapter 可切换，在线检索实际走 pgvector | pgvector 同库 JOIN（向量+全文+权限+版本）是当前架构优势，不建议切 |
| Redis 幂等组件 | 有实现，交易链路未接线（订单用 DB 方案） | 备用组件要写明"为什么不用" |
| 自由 NL2SQL | `nl2sql_ready=False` 明确关闭 | 金融场景下模板 + 白名单 + 绑定参数比模型自由生成 SQL 更可证明安全 |
| LangChain 检索外壳 | try/except 可选定义，非主检索路径 | 装饰性集成要防止被当成主路径 |
| 前端交易意图 | 部分仍走前端本地关键词旁路，未收敛到后端受控工作流 | 前端旁路是权限/一致性缺口 |

### 4.2 开关默认值的分层陷阱

渐进式开关的"默认值"分三层，**代码默认与部署默认可以完全不同**：

| 开关 | 代码默认 | compose 部署默认 |
|---|---|---|
| `AGENT_GRAPH_ENABLED` | `False` | `false` |
| `AGENT_GRAPH_SHADOW_ENABLED` | `False` | `false` |
| `AGENT_CHECKPOINT_ENABLED` | `False` | `false` |
| `AGENT_MODEL_TOOL_SELECTION_ENABLED` | `True` | `false`（覆盖） |

最后一行的不一致意味着"本地直跑启用模型工具轮、容器内默认关闭"——两侧行为不同，排查时容易误判。

接线后的风险预判也值得记录：图侧影子双跑**任何异常都被吞掉，绝不穿透真实请求**；checkpointer 初始化失败只降级不阻塞启动但**必须打 ERROR**（见下文静默降级）；多 worker 下每个 worker 都会跑 checkpointer `setup()`，并发 `CREATE INDEX CONCURRENTLY` 可能冲突。

### 4.3 启示

1. **"未接线"应是明示决策而非遗漏**——每项未接线能力都应写明现状、依据、接线后收益/风险/前提。本项目中多数未接线项是计划书里的阶段化交付决策，可以理直气壮地说明。
2. **实现 + 单测齐全 ≠ 在生产路径上**——LangGraph 图曾编译通过、单测通过、全仓 0 个业务调用方。发现手段：全仓搜调用方 + 读部署配置。
3. **切流要走渐进式开关 + 影子双跑**——图与管线是两套调用路径，权限/scope/幂等校验须逐点对齐；双跑对照确实抓到了图缺 4 个持久化副作用这类"直接切流会出问题"的差异。
4. **开关生效性要追到部署清单**——compose environment 是白名单 + `${VAR:-default}` 覆盖，代码默认与线上实际可以完全不同。

## 5. 依赖注入与中间件实现

### 5.1 DI 形态："lifespan 构造单例 + app.state 取用"

不用 DI 容器（dependency-injector/punq 等），理由：单体应用、依赖图只有一层（Service 依赖 database/settings）、无多环境装配与循环依赖，引入容器只增加间接层。

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()
    understanding_config.reload()          # 全局单例必须在此加载
    database = Database(settings)
    redis_client = RedisClient(settings)
    await _seed_startup_locked(database, settings)   # 多 worker 加锁

    app.state.settings = settings
    app.state.database = database
    app.state.redis = redis_client
    app.state.health_service = HealthService(...)
    ...
    try:
        yield
    finally:                               # 释放顺序与创建相反
        await redis_client.close()
        await database.dispose()
```

**分界线：有连接/需释放 → 挂 `app.state`；无状态轻量 → 端点内新建**（如 `QwenProvider(settings)`、`KnowledgeRepository(database)` 每次请求新建，构造成本 ≈ 一个 `__init__`）。

**已知缺口**：`app/common/dependencies/request.py` 定义了 `get_database/get_redis/get_settings`，但全仓 **0 处调用**（217 处直接 `request.app.state.xxx`）——"看起来像 DI 的装饰"。后果：无法用 `app.dependency_overrides` 在测试里替换 DB；且误导新同事写出风格不一致的代码。不是 bug，但是负债——要么全量改用，要么删掉。

### 5.2 认证依赖（唯一"真正的"DI）

```python
async def current_user(request, credentials=Depends(bearer)) -> User: ...

def require_permission(code: str):          # 工厂：参数化依赖
    async def dependency(user: User = Depends(current_user)) -> User:
        if user.is_super_admin: return user
        permissions = {p.code for role in user.roles for p in role.permissions}
        if code not in permissions: raise HTTPException(403)
        return user
    return dependency
```

设计要点：`selectinload` 预加载角色→权限（避免 N+1）；`User.status == "active"` 使被禁用用户的旧 token 立即失效；拒绝 refresh token 当 access 用；工厂返回闭包使 FastAPI 可缓存依赖（同一请求只查一次库）。

### 5.3 启动期并发保护

`uvicorn --workers 4` 时每个 worker 都跑一次 `lifespan`。若不加锁，两个 worker 并发执行 schema DDL（AccessExclusiveLock）→ PostgreSQL deadlock → 部分 worker 启动崩溃并反复重启。解法：专用连接持 session 级 `pg_advisory_lock` 覆盖整个 schema+seed 段。两个易忽略细节：锁必须持在同一条连接上；非 PG 环境退化为不加锁直接跑（保证本地测试环境可启动）。

### 5.4 条件依赖与静默降级

```python
app.state.agent_checkpointer = None
if getattr(settings, "agent_checkpoint_enabled", False):
    try:
        app.state.agent_checkpointer = await ensure_postgres_checkpointer(...)
    except Exception as exc:
        logger.error("agent_checkpointer_init_failed ...", exc)   # ERROR 而非 warning
```

两个设计判断：**失败不阻断启动**（checkpointer 建不起来时图仍可跑，只是没有跨进程断点）；**打 ERROR 而非 WARNING**——开关开着却没生效属于"用户以为开了、实际没开"的静默降级，这类问题在日志里必须显眼。项目同类开关沿用此约定。

### 5.5 中间件栈

注册只有两行起步（后加 RequestGuard），但**顺序很讲究**。Starlette 是逆序包裹——后注册的在外层，实际执行流：

```
请求 → RequestGuard → TraceId → CORS → GZip → 路由
响应 ← RequestGuard ← TraceId ← CORS ← GZip ← 路由
```

TraceId 在外层（Guard 之内）的原因：Guard 拒掉的请求也要进 trace 日志；而 TraceId 在 CORS 之外，才能记录**所有**请求——包括被 CORS 拒绝的、404 的、认证失败的。若反过来，这些请求不会产生 trace 日志，排障时"请求明明发了却查不到日志"。

**TraceIdMiddleware 实现要点**：

```python
trace_id = request.headers.get("X-Trace-Id") or str(uuid4())  # 复用或新建（支持跨服务串联）
token = trace_id_context.set(trace_id)                        # ContextVar 而非全局变量（async 并发隔离）
...
response.headers["X-Trace-Id"] = trace_id                     # 回写响应头（用户报障可直接定位）
...
finally:
    trace_id_context.reset(token)                             # 必须还原，防上下文泄漏
```

异常分支也记耗时——失败请求的耗时同样重要（慢失败最难查）。

**RequestGuard（请求护栏）**：请求体大小（413）、全局超时（504）、按 IP 限流（429）、GZip、CORS 白名单。三个关键设计判断：

1. **限流器故障必须"放行"而非"拒绝"**——Redis 抖动时保守拒绝会让一次抖动拖垮整个服务。限流是保护措施，不是业务前置条件。
2. **健康检查路径豁免限流**——否则探活被 429，编排系统误判服务不健康。
3. **默认关闭限流**——开启会改变既有压测/回归行为（并发测试出现 429），由 env 显式打开。

限流 key 取 `X-Forwarded-For` 首段（经反代时 `client.host` 是反代 IP，会把所有用户算成同一个桶）；XFF 可被伪造，仅在可信反代后有意义。

### 5.6 中间件与 DI 的已知缺口

| 缺口 | 现状 | 建议 |
|---|---|---|
| WebSocket 无 trace | `BaseHTTPMiddleware` 只处理 HTTP，实时 Agent 链路无 trace_id/耗时日志——**恰恰是最需要观测的链路** | TraceId 改纯 ASGI 中间件（可同时覆盖 http 与 websocket） |
| DI 辅助函数 0 调用 | 见 5.1 | 全量改用或删除 |
| 无 Prometheus 指标 / 无安全响应头 | 未做 | 见差距清单 |

一个实测注意事项：`TestClient(app)` 不进入上下文管理器时**不会执行 lifespan**，`app.state` 为空，访问任何依赖它的端点直接 `AttributeError`——既说明测试写法要求，也说明所有依赖的生命周期都绑在 lifespan 上。

## 6. 总纲：五条可迁移的排查纪律

1. **先补观测，再谈诊断**——动机证据被丢弃时，任何行为归因都是不可证伪的猜测。
2. **能跑的探测 > 推理；提出假设后先设计证伪实验**，而不是照着假设改代码。
3. **单样本不下机制性结论**；集合指标必须多次采样；LLM 缺陷先排除随机性。
4. **警惕静默失效**——配置没加载用默认值、`except: pass` 吞错、状态框架丢弃未声明键、状态位让文档消失，都不报错；"看起来正常"不等于"配置生效"。
5. **接缝处最容易丢信息**——映射/压缩是有损通道，让原始意图/事实/理由穿越全流程；排查"能力是否生效"要追到部署清单的最终值。
