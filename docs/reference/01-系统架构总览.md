## 1. 系统定位与设计目标

系统采用**模块化单体架构**，核心原则是：AI 只做「理解、推荐、解释、辅助决策」，权限、风控、适当性、确认与执行始终由确定性业务系统负责，把模型限制在可解释、可审计、可验证的辅助范围内。

架构优先保证：

1. 业务规则可解释、可审计。
2. 客户、产品、风险、订单和资产数据保持一致。
3. Agent 可以替换和扩展，不直接掌控资金、权限和风险决策。
4. 数据库和向量数据库通过 Port/Adapter 抽象，支持后续迁移。
5. 当前可以本地演示，未来可以逐步拆分服务。

## 2. 技术栈

FastAPI · SQLAlchemy Async · PostgreSQL + pgvector · Redis Streams + Outbox · LangChain / LangGraph · Qwen（DashScope）· Vue 3 + Vite · Docker Compose · GitHub Actions CI/CD · Pytest

### 3.1 前端层

目录：`frontend/src/`

主要页面：

- 客户中心：账户、个人画像、风险测评、企业认证、订单。
- 产品中心：产品展示、风险等级、客户类型和购买资格提示。
- 员工后台：客户管理、订单审核、产品管理、企业认证审核、审计和回收站。

前端职责边界：

- 展示业务状态和规则原因。
- 提交用户操作。
- 对明显不适配的产品提前置灰。
- **不承担最终权限、资产、风险和交易判断**——前端按钮和菜单不是安全边界。

### 3.2 API 层

目录：`app/api/`

API 只负责四件事：

- 身份认证和权限依赖。
- 参数校验。
- 调用 Service。
- 统一响应和错误转换。

不允许在 API 路由中直接编写复杂交易、风控和资产逻辑。

### 3.3 Service 业务层

目录：`app/services/`

核心服务：

| 服务 | 责任 |
|---|---|
| `AssetSummaryService` | 账户现金、持仓市值和资产快照汇总 |
| `RiskAssessmentService` | C1-C5 风险测评和 provisional 默认等级 |
| `SuitabilityService` | 风险等级、客户类型、资产门槛适配 |
| `TradingService` | 订单、确认、冻结、审核、执行和持仓 |
| `CustomerTierService` | 普通、黄金、白金、钻石、私人银行分层 |
| `AuthService` | 注册、登录、令牌和密码 |
| `KnowledgeRepository` | 知识库文档、分块和检索 |
| `AgentOrchestrator` | Agent 注册、选择和调用 |

业务决策原则：

```text
确定性后端规则决定结果
Agent 负责理解、解释和建议
```

层间职责切分：

```text
Repository：SQLAlchemy 查询和持久化
Service：业务规则、事务、权限、幂等和状态变更
Tool：Schema、权限、参数转换、Service 调用和结果格式化
```

Agent 不得直接访问 Repository，Tool 不得直接拼接 SQL、修改数据库或操作 Redis 队列。

### 3.4 Port / Adapter 层

Port 层只描述能力，不绑定具体厂商。当前接口：

```text
app/ports/agent.py          # Agent、AgentContext
app/ports/vector_store.py   # VectorStore、VectorDocument、VectorHit
app/ports/repositories.py   # Customer/Product/RiskAssessment Repository
app/ports/trading.py        # Account/Order/Holding/Asset Repository
```

已建立的 Repository Port：

```text
CustomerRepository
ProductRepository
RiskAssessmentRepository
AccountRepository
OrderRepository
HoldingRepository
AssetRepository
```

调用链固定为：

```text
API / Service
    ↓
Port（Agent / VectorStore / Repository）
    ↓
Adapter（本地 Agent / pgvector / Milvus / PostgreSQL / MySQL）
```

Agent Tool 的调用链同理：`Agent Tool → Application Service → Repository / External Adapter`。

## 4. 可替换基础设施设计

### 4.1 配置抽象

```env
DATABASE_BACKEND=postgresql
VECTOR_STORE_BACKEND=pgvector
AGENT_BACKEND=local
MILVUS_URI=http://127.0.0.1:19530
MILVUS_COLLECTION=wealth_documents
```

配置开关只是选择 Adapter 的入口。**切换到 MySQL/Milvus 前必须完成迁移、契约测试和回归验证**，当前不切换生产链路。

### 4.2 向量存储双实现

```text
VectorStore
├── PgVectorStore        # 当前主检索
└── MilvusVectorStore    # 已实现集合初始化、upsert、search、delete
```

Milvus 正式集合 `wealth_documents` 字段：`id`（知识块 ID）、`vector`（1024 维 embedding）、`text`、`document_id`、`version_id`、`title_path`、`content_hash`，索引为 `AUTOINDEX + COSINE`。Milvus 适配器可在不修改业务服务的情况下新增。

### 4.3 数据库迁移边界

- PostgreSQL 是主业务库；MySQL 8 作为迁移验证的隔离容器（`wealth-mysql-migration`，宿主端口 3307），已完成最小核心表（`users`、`customer_profile`、`product`、`customer_risk_assessment`、`account`）的 DDL 与类型兼容验证，`aiomysql` 驱动已接入，`MySQLRepository` 提供连接池与参数化查询能力。
- 全量业务表迁移、MySQL Repository 完整实现、双读对比和回滚方案尚未完成，MySQL 因此**未声明为可直接切换**。

## 5. Agent 架构

### 5.1 多 Agent 编排模式

采用 **Supervisor 统一编排 + 领域 Agent** 模式：

```text
Supervisor
    ├── CustomerServiceAgent   # 客服
    ├── AdvisorAgent           # 投顾
    ├── RiskAgent              # 风控
    ├── AnalystAgent           # 数据分析（只读 NL2SQL）
    └── OperationAgent         # 业务操作（受控）
```

- 基于 LangGraph 状态机实现条件分支、迭代与工具调用预算、受控 ReAct。
- 领域 Agent 是受 Supervisor 管理的策略模块，不允许互相无限递归调用。
- Supervisor 按场景选择 Agent 组合（如产品推荐 = Advisor + Risk + CustomerService），不能默认调用所有 Agent。
- 意图识别上，**确定性规则规划器为权威**；可选的 LLM 影子/兜底仅用于非交易意图，交易类永远走规则。

### 5.2 接入契约

所有实验 Agent 必须适配为统一签名：

```python
async def run(
    message: str,
    context: AgentContext,
) -> AgentResult:
    ...
```

统一返回结构：

```text
AgentResult
├── agent_name
├── status
├── summary
├── data
├── evidence
├── tool_calls
├── confidence
├── requires_confirmation
└── errors
```

ReAct 循环必须受预算约束，`AgentContext` 包含迭代、Tool 调用、Token 和耗时预算，默认单 Agent：`max_iterations=4`、`max_tool_calls=8`。达到预算即安全停止，完整隐藏思维链不返回前端、不写入普通日志。

### 5.3 Agent 能力边界

Agent 可以：

- 理解用户意图。
- 查询知识库。
- 生成产品或风险解释。
- 给出分析建议。
- 调用只读分析工具。

Agent 不可以直接决定：

- 账户余额。
- 订单状态。
- 客户类型。
- 客户层级。
- 正式风险等级。
- 是否绕过适当性检查。
- 是否执行真实资金交易。

权限分层模型：

```text
L0：只读数据和分析
L1：建议和操作草稿
L2：确定性业务 Service（不属于自由 Agent，不能由模型绕过调用）
```

安全边界由能力白名单前置过滤、按角色权限与授权客户范围（Subject Scope）限制 Agent 与工具调用实现——模型无法越权读取他人数据或直接提交交易。

### 5.4 受控子代理并行

原则：**部分领域可并行（只读分析），严格场景必须确定性**。

- 可并行：风控只读分析、产品解释、RAG 检索、画像分析——通过 `SubagentExecutor` + 只读工具 + 并发信号量 + 结构化结果 + 确定性融合实现。
- 绝不并行：订单、资金、赎回、风控结论、写操作——走确定性 Service + 人工。
- 安全配套：只读工具强制、RBAC + capability、SubjectScope 数据范围注入、三重预算、审计、失败降级。

## 6. 关键业务链路

### 6.1 交易流程

```text
客户浏览产品
      ▼
前端展示适配状态
      ▼
创建订单 pending_confirmation
      ▼
客户确认订单
      ├── 账户余额检查
      ├── 客户类型检查
      ├── 风险等级检查
      └── 产品金额检查
      ▼
账户冻结金额增加
      ▼
pending_review
      ▼
工作人员审核
      ├── rejected
      └── executing
              ▼
          持仓更新
              ▼
          Trade 记录
              ▼
          executed
              ▼
          派生资产快照
```

所有关键状态转换写入 `order_status_history` 和 `audit_logs`。

资金与订单一致性规则：

```text
冻结：available -= amount; frozen += amount（confirm_order）
成交：frozen 扣减 → holding upsert → trade → 资产快照 → money_flow
状态迁移唯一权威在 Order.transition()
```

适当性适配顺序：

```text
客户类型 → 风险等级 → 资产/金额门槛 → 订单状态
```

### 6.2 企业客户流程

```text
普通客户
   ▼
提交企业资料
   ▼
pending
   ▼
超级管理员审核
   ├── rejected
   └── approved
           ▼
customer_type = enterprise
customer_tier = enterprise_standard
source_type = enterprise_verified
```

客户不能直接修改企业类型。

### 6.3 资产口径

```text
User
 ├── Account
 ├── CustomerProfile
 ├── CustomerRiskAssessment
 ├── CustomerAssetSnapshot
 ├── CustomerHolding
 └── Order ─── Trade
```

实时派生资产口径：

```text
现金资产 = available_balance + frozen_balance
持仓资产 = 有效持仓 market_value 总和
总资产 = 现金资产 + 持仓资产
净资产 = 总资产 - 负债
```

### 6.4 知识库与检索链路

```text
原始文档
   ▼
文档解析与分块
   ▼
Embedding Provider
   ▼
PostgreSQL knowledge_chunk + pgvector
   ├── 主检索
   └── Milvus wealth_documents（迁移/验证）
```

RAG 与业务事实职责分离：RAG 负责解释层（公司信息 / 流程 / FAQ），业务事实直接查 PostgreSQL，**冲突以业务表为准**；检索采用 dense/BM25 混合检索 + Reranker + 引用溯源。路由优先级：实时业务事实优先，RAG 只用于流程、条款和背景解释，不能覆盖实时状态或执行受控操作。

### 6.5 客服实时链路

人工客服消息的同步链路分三层：

```text
PostgreSQL customer_service_message
        │ 事实源
        ├── HTTP GET /customer-service/sessions/{session_id}/messages
        │       └── after={last_message_id}：断线后的增量补偿
        └── Redis Pub/Sub customer-realtime:{customer_id}
                └── WebSocket relay：在线低延迟通知
```

- WebSocket/PubSub 只是低延迟通知通道；HTTP 增量查询和 PostgreSQL 才是断线恢复依赖的事实链路。
- 该链路只负责「已落库消息的可见性」，不改变客服会话状态机，也不替代 HTTP API 的权限校验。
- 会话状态机：

```text
waiting_human
  ├─ 坐席 claim → human_active
  └─ 超过 CUSTOMER_SERVICE_WAITING_TIMEOUT_SECONDS（默认 1800 秒）未接入 → expired

human_active
  └─ 超过 CUSTOMER_SERVICE_HEARTBEAT_TIMEOUT_SECONDS（默认 90 秒）无心跳 → paused

paused
  └─ 坐席重新 claim → human_active
```

`resolved`、`closed`、`expired` 都是终态：不得 claim，不得作为通知自动聚焦目标，不得恢复浏览器中的人工会话缓存。

## 7. 异步可靠性（Outbox / Redis Streams / Worker）

### 7.1 Outbox 模式

- 业务行与 `outbox_event` 在**同一事务**提交，避免数据库提交成功但事件发布失败。
- `outbox_worker` 用 `FOR UPDATE SKIP_LOCKED` 认领 → 发布到 Redis Stream → 至少一次投递 + 幂等消费 + 死信重试。

### 7.2 Redis Streams

- `XREADGROUP` 消费组 + `XCLAIM` 30 秒崩溃接管 + `MAXLEN ~10000` 控制流长度。
- 消费可靠性要求：消费组 ACK、Pending 列表巡检、最大重试次数、指数退避、Dead Letter Stream、任务幂等键、任务状态落库。

### 7.3 Worker 与任务模型

Worker 分类：

```text
流消费者：knowledge / notification / authorization / tasks
定时轮询：aml_scheduler / customer_service_timeout
通用任务执行器：runner（业务分发占位）
```

AsyncTask 状态机：

```text
queued → running → success / failed / dead
```

带幂等键与死信处理；任务状态、重试次数、审计记录统一落 PostgreSQL，Redis 只负责投递。事件与任务严格区分：

- **任务**：必须被某个 Worker 完成，有状态、重试和幂等要求（如 `knowledge.ingest`、`risk.evaluate_transaction`）。
- **事件**：表示事实已经发生，可被多个消费者订阅（如 `transaction.created`、`risk.alert.created`）。

## 8. 分层记忆

记忆分两层实现：

| 层 | 存储 | Key / 结构 | 内容 |
|---|---|---|---|
| 短期 | Redis | `customer:memory:short:{customer_id}:{conversation_id}`，TTL 30 分钟 | 澄清上下文、待执行计划、转人工状态 |
| 长期 | PostgreSQL | `CustomerMemory`（记忆卡片）+ `CustomerMemoryEvent`（事件审计） | 客户明确确认的参数、服务偏好、非敏感会话事实 |

关键约束与边界：

- `CustomerMemory` 通过部分唯一索引保证同 key 只有一条 active（记忆卡片语义）。
- **业务事实表永远高于记忆**：风险、资产、持仓、订单、产品状态、限制和授权信息不能从记忆中读取为最终依据。
- 只存客户确认参数/偏好/非敏感事实，不得形成模型推断的金融「人格画像」。
- 演进方向：版本化卡片（valid_from/valid_to）+ 乐观锁（if_version）+ 记忆污染过滤。

记忆处理同步/异步划分原则：

```text
明确表达并影响当前回答 → 同步
历史推断、分析、摘要、批量校准 → 异步
```

同步记忆有超时降级（默认 `MEMORY_SYNC_TIMEOUT_MS=2500`）：超时后保留用户原始表达、将 `memory.extract` 投递到异步流、当前请求使用未持久化的候选记忆（`persisted=false` + 幂等键防重）。

## 9. 受控 NL2SQL 与数据目录

核心策略：**不让模型自由生成 SQL**，采用「数据目录召回 + 批准模板 + 参数契约 + 只读执行」，`nl2sql_ready=False` 明确关闭自由 SQL。

数据目录由 `data_catalog_domain/table/column/relation/example_query/revision` 六表组成；表/列/示例查询带 `VECTOR(1024)` 语义向量；目录检索为文本+向量混合，叠加 `allowed_roles_json` 角色过滤与 `retrieval_mode` 可观测。

安全四层防护：

1. **入口**：只收自然语言，直接 SELECT 拒绝。
2. **模板白名单**：`is_approved` + 角色 + 只读结构校验。
3. **目录引用范围**：SQL 引用表/列 ⊆ 模板声明 ⊆ 活跃可查询目录非敏感列。
4. **执行层**：SQLAlchemy 绑定参数 + 外层 LIMIT + 失败 rollback。

实现模块：`app/services/data_analysis_agent.py`、`nl2sql_policy.py`、`data_catalog_service.py`。

## 10. 数据飞轮

闭环链路：

```text
信号（评测 Bad Case）
   → 积累（记忆/Skill）
   → 落地（配置库）
   → 控制（人机审核/灰度/回滚）
   → 回流评测
```

- 线上 bad case（含高置信意图误判 `intent_misroute`）自动回流 → 人工标注 → 导出进黄金评测集 → 修复。
- 已有基础：Bad Case 收集（6 类信号）、回归集、100% 审计、证据状态门禁、动态模型路由。
- 核心原则：**「评测可信度 > 系统复杂度」**——先保证评测信号准，再谈自动化。

## 11. 关键架构决策汇总

| 决策 | 理由 |
|---|---|
| 模块化单体，而非微服务起步 | 可演示、可扩展，未来可逐步拆分服务 |
| PostgreSQL + pgvector 为主库与主检索 | JSONB/全文检索/事务/约束支持好，向量可兜底，避免双数据库一致性负担 |
| Port/Adapter 抽象（DB、向量库、Agent） | 业务层不绑定具体厂商，切换前完成契约测试与回归即可替换 |
| 确定性 Service 决定业务结果，Agent 只做理解/解释/建议 | 业务规则可解释、可审计，模型不可越权 |
| Supervisor + 领域 Agent，而非五个完全自治 Agent | 降低路由/Prompt/上下文/调试/审计复杂度，Agent 间不允许无限递归 |
| Redis 不作为事实数据库 | 只承担会话、缓存、Streams 队列、Outbox 发布；最终状态与审计在 PostgreSQL |
| Outbox + Streams + Worker 的异步链路 | 保证「数据库提交成功」与「事件发布成功」的原子性，至少一次投递 + 幂等消费 |
| 记忆永远低于业务事实表 | 防止模型推断覆盖真实金融事实 |
| 受控 NL2SQL（模板白名单 + 参数契约 + 只读执行） | 模型自由生成 SQL 在金融场景不可接受 |
| 评测信号优先于系统复杂度（数据飞轮） | 自动化的前提是评测可信 |

## 12. 安全与业务边界

- 本系统交易为 Mock。
- 所有金额和权限由后端确定。
- 风险适配由确定性规则决定。
- 企业客户必须经过审核。
- Agent 不得绕过权限、风控和交易确认。
- 生产环境不得保存明文演示密码。
- 对外接口由后端 RBAC + 资源数据范围校验；工作人员代办必须满足客户授权、确认、额度、风险和审计约束。
