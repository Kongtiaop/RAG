## 1. RBAC 设计原则

1. **角色不等于权限**：用户可拥有多个角色；最终授权由权限集合和数据范围共同决定。
2. **后端为最终边界**：前端菜单/按钮隐藏只改善体验，不能作为授权依据；每个受保护 API 必须执行服务端鉴权。
3. **本人、已授权、全量范围分离**：客户只能访问本人数据；投顾只能访问有效授权客户；工作人员按岗位权限访问必要范围。
4. **最小权限与职责分离**：客户资料维护、投顾建议、风险处置、交易审核、审计只读、系统管理不得用一个粗粒度权限混用。
5. **高风险操作可审计**：交易审核、交易限制、解除限制、可疑交易报告、角色权限修改必须记录审计日志；需要时追加二次确认与业务状态机约束。
6. **超级管理员例外受控**：保留超级管理员的系统维护能力，但矩阵测试中仍需验证其明确允许的行为，不能以"默认全放行"代替契约。

## 2. 认证机制

### 2.1 密码与注册

- 密码哈希：Argon2（`app/services/auth_service.py`，模块级单例 `password_hasher = PasswordHasher()`）。`verify_password` 捕获 `InvalidHashError` 和 `VerificationError` 统一返回 `False`——不区分"用户不存在/密码错"，防枚举。
- 注册：`POST /auth/register`，username 正则 `^[A-Za-z0-9_.-]+$`，密码 ≥8 位。员工注册必须提供 `company_code` 且等于 `settings.employee_registration_code`，否则拒绝。
- 注册只分配两种角色：`customer` 或 `employee_pending`（零权限待分组员工）。正式岗位角色只能由管理员通过 `PUT /admin/users/{user_id}/roles` 分配。

### 2.2 登录与 JWT

- 登录：`POST /auth/login`，三重校验：用户存在、`status == "active"`、Argon2 密码正确。
- JWT 生成：payload 含 `sub=user.id`、`username`、`roles=[r.code ...]`、`is_super_admin`、`type="access"`、`exp`（默认 1440 分钟=24h）；算法 HS256（`settings.jwt_algorithm`），密钥 `settings.jwt_secret`。
- 校验（`current_user`，`app/common/security/auth.py`）：`HTTPBearer` 取凭据 → `jwt.decode`（任何 `PyJWTError` → 401）→ 校验 `type == "access"` → **每次都从数据库重新加载用户**（`selectinload(User.roles).selectinload(Role.permissions)`，且 `status=="active"`）。
- **设计要点**：JWT 只是"身份 + 过期"的无状态凭证，**权限永远以数据库当前值为准**——角色/权限/禁用状态变更即时生效，不需要等 token 过期或强制重新登录。
- WebSocket 版本 `websocket_current_user` 从 `query_params["access_token"]` 取 token，同样的 decode + 重载用户流程。
- `/auth/me` 返回当前用户 id、roles、权限并集、is_super_admin。

### 2.3 Refresh Token：轮换与撤销

- 数据表 `RefreshSession`：`user_id`（FK CASCADE）、`token_hash`（SHA-256、unique、index）、`expires_at`、`revoked_at`、`created_at`。
- **只存哈希**：数据库只存 `sha256(token)`，明文 token 只出现在响应里。
- **每次刷新必轮换**：`POST /auth/refresh` 把旧行 `revoked_at=now` 再签发新 token 入库。旧 token 一旦被用过即作废——重放已轮换的旧 token 查不到有效行而 401，天然具备**重用检测**语义。
- **可撤销**：`POST /auth/logout` 按哈希把有效行置 `revoked_at`。
- 默认有效期 30 天（`settings.refresh_token_expire_days`）。

## 3. RBAC 数据模型与权限矩阵

### 3.1 表结构

| 表 | 说明 |
|---|---|
| `users` | `id`(UUID)、`username`(unique)、`password_hash`、`status`(active/deleted/disabled)、`is_super_admin`、`deleted_at`；`roles` 多对多 |
| `roles` | `code`(unique)、`name` |
| `permissions` | `code`(unique)、`name` |
| `user_roles` | 关联表，`(user_id, role_id)` 复合主键，FK CASCADE |
| `role_permissions` | 关联表，`(role_id, permission_id)` 复合主键，FK CASCADE |
| `refresh_sessions` | 见 §2.3 |
| `customer_advisor_authorization` | Subject Scope 授权记录，见 §5 |

### 3.2 角色目录（10 个）

| 角色代码 | 名称 | 定位 |
|---|---|---|
| `customer` | 普通客户 | 仅处理、查看本人金融资料与业务申请 |
| `customer_service` | 客服 | 客户服务、基础查询；不承担资金类高风险写操作 |
| `customer_manager` | 客户经理 | 客户资料维护、服务工单、代客户转账申请等客户经营职责 |
| `advisor` | 理财顾问 | 在客户授权范围内分析画像、推荐产品、创建投顾操作草稿、发起风险复评 |
| `product_manager` | 产品工作人员 | 产品、状态、适配规则、产品知识资料管理 |
| `risk_manager` | 风控专员 | 预警、AML 扫描、调查、风险动作、报告草稿/上报 |
| `operations` | 运营/交易运营 | 待审核业务、订单/赎回/转账审核执行、业务异常处理 |
| `auditor` | 审计人员 | 只读审计、业务、风险、权限与配置记录；绝不具备状态变更权限 |
| `super_admin` | 超级管理员 | 用户、角色、权限、系统配置与全局治理 |
| `employee_pending` | 待分配员工 | 尚未授予业务权限的内部账号 |

角色迁移约束：

- `customer_service` 不再兼任"客服/客户经理"；资金和敏感客户维护类职责归 `customer_manager`。
- `product_manager` 不再被用作临时投顾身份；投顾仅认可 `advisor` 角色。
- 历史角色兼容仅可作为短期数据迁移策略，必须记录迁移窗口和移除日期。

### 3.3 权限码目录（12 个权限域）

权限域：`customer:* / product:* / advisor:* / order:* / transfer:* / operation:* / task:* / workorder:* / risk:* / audit:* / admin:*` 等。代表性权限码：

| 权限码 | 说明 |
|---|---|
| `customer:read_all` | 查看工作人员职责范围内客户列表/详情 |
| `customer:read_assigned` | 查看已分配/已授权客户 |
| `profile:risk_assessment` | 录入、发起或复评客户风险测评 |
| `advisor:recommend` / `advisor:create_operation_draft` | 为授权客户生成推荐 / 创建操作草稿 |
| `order:submit_staff` | 工作人员代授权客户提交申购/赎回申请 |
| `transfer:submit_staff` | 客户经理代客户发起转账申请 |
| `order:review` | 审核、通过、拒绝并执行订单/赎回/转账 |
| `operation:read_staff` / `operation:audit_read` | 查看待办与业务操作详情 / 查看业务审计（不含待办或审核） |
| `task:create` / `task:read` | 通用异步任务 |
| `risk:alert_read` / `risk:alert_handle` / `risk:alert_action` / `risk:scan_execute` | 预警查看 / 调查结案 / HOLD·冻结·限制与解除 / AML 扫描 |
| `audit:read` | 只读审计日志（限制为只读） |
| `admin:write` | 用户、角色、权限、系统治理 |
| `workorder:create/read/handle/assign` | 工单权限域（见 §6） |

**旧权限清理记录**：`customer:read` 不再分配给 customer（工作人员/投顾使用 `customer:read_all`/`customer:read_assigned`）；`order:write`、`risk:read`、`risk:write` 不再被运行时 API 或前端源码引用，权限定义已从种子权限字典移除；新增 `scripts/check_rbac_legacy_runtime_permissions.py` 扫描运行时旧权限引用。

### 3.5 权限矩阵的种子实现

- 权威文档：RBAC 权限矩阵规范。
- 可执行种子 `app/services/auth_seed.py`：`PERMISSIONS`（25 个权限码列表）、`ROLE_PERMISSIONS`（角色→权限码映射表，即矩阵的实现；`super_admin` = 全部权限，`employee_pending` = 空）。
- 种子装载 `ensure_auth_seed`：仅当 `demo_accounts_enabled` 且 `app_env ∈ {development, dev, local}` 时执行；`Settings.validate_p0` 强制生产环境关闭演示账号。幂等且并发安全：逐条 SELECT 后补 INSERT，并在下次 SELECT 前 `flush()`；角色/用户存在则每次启动把矩阵收敛到种子定义的状态。

### 3.6 鉴权依赖注入

```text
require_permission(code)          # is_super_admin 直接放行；否则校验角色权限并集，缺 → 403
require_staff_permission(code)    # 权限之外额外拒绝持有 customer 角色的用户（防客户调员工接口）
require_advisor_permission(code)  # 必须同时具备 advisor 角色 + 该权限码
advisor_user                      # require_advisor_permission 组合
staff_customer_user               # require_staff_permission("customer:read_all")
```

### 3.7 管理端 RBAC 接口

- `PUT /admin/roles/{role_id}/permissions`：校验权限码全部存在、**禁止修改 super_admin 角色权限**、写审计日志、查询该角色全部受影响用户并逐个 `bump_permission_context_version`（触发缓存失效）。
- `PUT /admin/users/{user_id}/roles`：**禁止给自己移除 super_admin**、校验角色存在、写审计、`bump_permission_context_version`。
- 双通道管理员判定 `ensure_admin`：`is_super_admin` **或** 拥有 `super_admin` 角色。
- 角色/权限/用户变更与审计日志在同一 session 内提交，保证事务一致性。
- 系统自我保护：不能通过 API 删除自己的 super_admin、不能改 super_admin 角色的权限集、不能禁用/删除自己。

### 3.8 测试矩阵与通过标准

每个受保护 API 至少覆盖：

| 场景 | 预期 |
|---|---|
| 未登录 | `401` |
| 有对应权限且在数据范围内 | `200/201/204` |
| 无对应权限的内部角色 | `403` |
| 客户访问工作人员接口 | `403` |
| 工作人员跨客户或投顾未授权客户 | `403`（或按接口规范统一为 `404`） |
| 审计员访问状态变更接口 | `403` |
| 超级管理员 | 根据明确授权契约通过，不以默认放行为测试依据 |
| 前端入口 | 不显示无权菜单/按钮；即使手工请求仍由后端拒绝 |

## 4. 权限版本化缓存（permission_scoped_cache）

### 4.1 Cache Key 组成

`PermissionContext`（frozen dataclass）建模"**能影响一个缓存读结果的全部授权维度**"：`user_id`、`role_codes`（排序元组）、`permission_codes`（所有角色权限的排序并集）、`tenant_id`、`data_scope_version`、`catalog_policy_version`。

```text
fingerprint = SHA-256(规范化 JSON(context))[:24]     # sort_keys + 紧凑分隔符 + ensure_ascii
cache_key   = {key_prefix}:{namespace}:pc-{context.fingerprint()}:sc-{scope_fingerprint}
```

- `namespace` 是逻辑名（如 `data_catalog_search`），**禁止含 ":"**，防止调用方构造注入 key。
- `scope_fingerprint` 对查询级参数（如 `{"query","top_k","domain_code"}`）同样做规范化 JSON + SHA-256。
- 效果：**"谁的（指纹）+ 查什么（scope 指纹）"共同决定缓存条目**，不同用户/权限/范围天然物理隔离。

### 4.2 失效机制：版本号而非删 key

版本键：`wm:permission-context-version:{user_id}` 与 `wm:subject-scope-version:{user_id}`。

- **读侧**：每次构造 `PermissionContext` 时从 Redis 读两个版本号，`data_scope_version = "{permission版本}:subject-{scope版本}"`——版本号进入指纹。
- **写侧**：
  - `bump_permission_context_version`：`INCR wm:permission-context-version:{user_id}`。触发点：管理员改用户角色、改角色权限（遍历受影响用户逐个 bump）。
  - `bump_subject_scope_version`：`INCR wm:subject-scope-version:{user_id}`。触发点：客户-投顾授权变更（经 Outbox 事件驱动）。
- **失效原理**：版本号变了 → 指纹变了 → `build_key` 生成的新 key 与旧 key 不同 → 旧条目"逻辑上不可达"，靠 TTL（默认 60 秒）自然回收。**不需要扫描/删除任何 key**。

### 4.3 设计要点

1. **缓存永远不改变授权结果**：`get_json` 任何异常都返回 `None`（走实时查询）、`set_json` 失败返回 `False`。"Cache is an optimization only. A backend failure must never change authorization behavior."
2. **双重保险**：指纹里本来就含实时角色/权限码——即使版本号 INCR 失败，角色/权限本身变了也会改变指纹。版本号是"主动/急切失效"，指纹是"安全底线"。**安全性从不依赖缓存**。
3. **原子且无竞态**：`INCR` 原子递增，O(1) 失效且不依赖 Redis SCAN。
4. **失效粒度精确**：按 `user_id` 精确失效，不误伤其他用户。
5. **与 TTL 协同**：版本化 + 短 TTL 双保险，即使漏 bump 也最多延迟一个 TTL。
6. **数据范围维度独立**：subject scope 版本号独立于权限版本号，授权变更（更频繁）与角色变更互不串扰。

实际应用：`DataCatalogService.search` 先按 `PermissionContext` + 查询 scope 查缓存（命中直接返回并标注 `+permission-cache`），未命中走真实检索后 `set_json(..., ttl_seconds=60)`。

## 5. Subject Scope：数据范围控制

### 5.1 授权记录数据结构

`CustomerAdvisorAuthorization`：

- `customer_id`、`advisor_id`（均 FK `users.id`，CASCADE，index）——**被授权客户 = advisor 对 customer 的一行记录**。
- 业务约束字段：`allowed_actions`（默认 "buy"）、`product_scope`（默认 "*"）、`max_single_amount`、`max_daily_amount`、`risk_level_ceiling`（默认 "C2"）——**scope 不只是"客户 id 集合"，还携带金额/产品/风险等级上限**。
- 有效期：`effective_from`（默认 now）、`effective_to`（可空=长期）、`status`（active）、`revoked_at`。

### 5.2 计算入口

`SubjectScopeService.authorized_subject_ids(session, user)`：

1. **超级管理员**：返回 `set()`——空集合仅对 super_admin 表示无限制（显式约定而非隐式全放行）。
2. **advisor / customer_manager**：查询授权表，条件 `advisor_id == user.id`、`status == "active"`、`effective_from <= now`、`(effective_to IS NULL OR effective_to >= now)`、`revoked_at IS NULL`，返回 `customer_id` 集合。
3. **其他员工**：只能访问自己上下文 `{user.id}`。

### 5.3 防越权核心：参数服务端改写为授权闭包

绑定点：数据分析执行前计算 `authorized_subject_ids`，传入 `DataAnalysisAgent.analyze_template_attempt`。

`DataAnalysisAgent.bind_template_parameters`：

- 从用户问题里提取的 subject 引用与授权集合求交集，**凡是请求里出现不在授权集合内的客户标识 → 直接拒绝**（`invalid_parameters` 理由，走澄清/拒绝路径）。
- SQL 模板的 subject 参数**由服务端替换**为 `subject_scope`：super_admin 且授权集为空 → `None`（不限制）；否则 = 授权 id 集合；普通用户 = 本人 id。**客户提供的任意 customer_id 都无法进入最终 SQL**——不是靠"前端传参后校验"，而是**参数在服务端被改写为授权闭包**。

路由层与范围层**两层独立可组合**：投顾接口用 `advisor_user` / `require_advisor_permission`（角色+权限门），范围层用 `SubjectScopeService`。

### 5.4 授权变更的单一写入口与缓存失效

- `AdvisorAuthorizationService`：`grant_or_update`（`with_for_update` 行锁防并发重放）、`revoke_ids`、`revoke_for_customer`——所有变更走这一处，保证"单一写边界"。
- 管理端批量接口 `PUT /admin/advisor-authorizations/batch`：批量 grant/revoke + 审计 + **事务内写入 Outbox 失效事件**（`authorization.subject_scope_invalidate`）——事件与数据变更同事务提交，进程崩溃可重试（允许重放 dead 的该类事件）。
- 订阅方执行 `bump_subject_scope_version` 使受影响的投顾/客户经理缓存整体失效。

### 5.5 为什么权限/数据范围放在服务端，而非前端/模型层

1. **前端只做体验，不做法定依据**：前端可被手工请求、调试工具、爬虫绕过。
2. **JWT claims 不可信为授权源**：token 里的 roles 只是便捷快照；`current_user` 每次请求从数据库重载用户 + 角色 + 权限。
3. **权限与数据范围分层，而非模型层全局过滤**：
   - 操作级（能不能做）→ FastAPI 依赖注入 `require_permission / require_staff_permission / require_advisor_permission`，声明式、可组合、可单测。
   - 数据级（能做哪些客户）→ `SubjectScopeService` + 模板参数绑定（SQL 的 subject 参数服务端改写为授权闭包）。
   - 不做 ORM 模型层全局 query filter 的原因：隐式、难以审计、多角色并集/交集语义混乱、join 复杂、且无法覆盖"模板 SQL 参数"这种动态路径；显式传参 + 显式校验可测试、可读、可审计。
4. **缓存不承担任何授权职责**：授权结果 100% 来自数据库实时计算。
5. **变更即审计**：角色/权限/状态/授权变更全部写 `AuditLog` 且与业务变更同事务提交。

## 6. 工单权限最小闭环

### 6.1 闭环与类型

最小闭环：

```text
创建 → 读取 → 分派（可选）→ 处理中 → 解决/关闭
```

工单不是交易订单，**不得复用 `order:*` 权限**；工单状态变化必须写入 `audit_logs`。

工单类型：`customer_service`（客户服务）、`complaint`（投诉）、`risk_investigation`（风控调查）、`business_exception`（业务异常）。

### 6.2 状态机

```text
open
  → assigned
  → in_progress
  → pending_customer
  → resolved
  → closed

辅助终态：cancelled
```

MVP 约束：

- 创建时状态为 `open`；分派后变为 `assigned`；
- 处理动作可设置 `in_progress`、`pending_customer` 或 `resolved`；
- 只有 `resolved` 工单可以关闭；`closed`、`cancelled` 不允许继续修改；
- 所有非法状态跳转返回 `409`。

### 6.3 数据模型与 API

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `ticket_no` | 可读工单编号，唯一 |
| `customer_id` | 关联客户；系统工单可为空 |
| `created_by` / `assigned_to` | 创建人 / 当前处理人（可空） |
| `category` / `priority` | 工单类型 / low/normal/high/urgent |
| `status` | 状态机状态 |
| `resolution_note` | 处理/结案说明（resolved 时必须非空） |
| `resolved_at` / `closed_at` | 处理/关闭时间 |

| API | 权限 |
|---|---|
| `POST /workorders` | `workorder:create` |
| `GET /workorders` | `workorder:read` |
| `GET /workorders/{id}` | `workorder:read` |
| `POST /workorders/{id}/assign` | `workorder:assign` |
| `POST /workorders/{id}/handle` | `workorder:handle` |
| `POST /workorders/{id}/close` | `workorder:handle` |

### 6.4 数据范围与执行契约

- 客户：只能创建和读取自己的工单；不能分派、处理或关闭。
- 客服：可创建、读取、处理客户服务/投诉工单；客户经理：业务服务工单；风控：风控调查工单；运营：业务异常工单（均可创建、读取、分派、处理）。
- 理财顾问：MVP 不自动获得工单权限（无处理权限，不能作为处理人）。
- 审计：只读所有职责范围内工单；超级管理员：系统级放行（`workorder:assign` 对 `is_super_admin` 明确放行）。
- **处理边界**：即使有 `workorder:handle`，非超级管理员也只能处理/关闭 `assigned_to == 当前用户` 的工单；处理人可通过 `GET /workorders?scope=assigned` 查看自己的分派工单。
- 权限码不替代数据范围：客户本人接口通过资源归属二次校验。
- 分派持久化：写入 `work_order.assigned_to`、状态变 `assigned`、`audit_logs.action=assign`。

### 6.5 站内通知与客户补充材料闭环

- 通知：`notification` 表 + `/notifications` API，用户只能读取/标记已读自己的通知。分派成功向 `assigned_to` 创建 `workorder_assigned` 通知（分派目标必须有处理权限）；`pending_customer`/`resolved`/`closed` 时向客户（或创建人）创建进度通知。
- 客户补充材料闭环：

```text
工作人员填写补充要求并置为 pending_customer
  → 要求写入 work_order_update，客户可查看
  → 客户提交补充内容（写入 work_order_update，状态自动回到 in_progress）
  → assigned_to 收到客户补充通知
  → 原处理人继续处理，才能 resolved / closed
```

- 权限边界：客户只能为自己的、且状态为 `pending_customer` 的工单提交补充；工作人员不能伪造客户补充。
- 附件：`work_order_attachment` 表；客户仅能给自己 `pending_customer` 的工单上传；仅允许 JPG、PNG、PDF，单文件上限 10 MB；服务器存储使用随机文件名，避免原始文件名路径穿越；上传写入 `audit_logs.action=upload_attachment`。
- 附件下载认证：`<a href>` 直接受保护下载 URL 不会携带 Bearer Token（401）——改为 axios `responseType=blob` 请求下载接口，由 HTTP 拦截器自动携带 Authorization。

### 6.6 非目标

不接入外部工单系统；不实现邮件/短信/移动推送（站内持久化通知除外）；不实现复杂 SLA 计时和自动升级；不把工单直接绑定到风险报告上报或交易审核。

## 7. 数据分析 Agent 的安全执行边界

数据分析 Agent 只执行**批准模板**内的受控 SQL，核心是多层白名单 + 参数边界 + 审计。

### 7.1 批准模板命中与角色过滤

- `analyze_template` 只接受 `is_active=True` 且 `is_approved=True` 的模板。
- 非超级管理员必须与模板 `allowed_roles_json` 至少命中一个角色。
- 模板未命中、未批准、停用或角色不允许时统一拒绝执行。
- API 层模板命中使用评分选择（而非简单字符串判断）；候选阶段即按当前用户角色过滤已批准模板，无权限模板不参与匹配。

### 7.2 SQL 表/字段白名单

- 模板 SQL 只能是单条只读 `SELECT`/`WITH` 查询。
- 拦截写操作、危险关键字、注释、分号和不支持的分隔符；禁止空字节、多语句（允许合法 PostgreSQL `$` 标识符）。
- 校验 SQL 实际引用的表、字段是否落在模板声明的 `target_table_names_json` / `target_column_names_json` 中。
- 数据目录校验：仅允许 active/queryable 表；字段必须 queryable 且不能是 sensitive（列级安全以 `is_queryable` 和 `is_sensitive` 为准）。白名单在真实 HTTP 执行链路中生效（执行前从数据库读取目录表/字段传入）。

### 7.3 参数边界与结果限制

- 限制 SQL 长度、参数数量、字符串参数长度、整数范围和日期区间（最长 366 天）。
- 默认参数包含 `start_date`、`end_date`、`month_start` 和最大 `limit`。
- 使用外层 `LIMIT :__result_limit` 并以 `fetchmany(MAX_RESULT_ROWS)` 双重限制结果行数，最大 100 行。
- subject 参数绑定见 §5.3：服务端改写为授权闭包，客户端无法注入任意 customer_id。

### 7.4 审计与可观测性

- 增加 `TemplateAnalysisAttempt`：模板执行返回受控的结果状态和拒绝原因（`role_denied`、`invalid_sql:*`、`catalog_denied:*`、`invalid_parameters:*`、`execution_failed`），**不把底层异常暴露给用户**。
- `/customer-service/sessions/agent/execute` 写入 `audit_logs`：
  - 成功执行批准模板：`data_analysis.template_executed`；
  - 未命中或被安全策略拒绝：`data_analysis.template_rejected`。
- **审计详情脱敏**：仅记录会话 ID、查询长度、模板 ID、受控拒绝原因、最终分析模式和 `free_sql=false`；**不记录用户完整查询内容，也不记录 SQL 参数值**，降低敏感信息进入审计日志的风险。
- 后台 `GET /admin/audit-logs` 支持 `action_prefix` 和 `resource_id` 筛选（需 `audit:read` 权限），可审计 `data_analysis.*` 事件。
