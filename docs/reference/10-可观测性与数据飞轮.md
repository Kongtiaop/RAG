## 1. 可观测性分层设计

### 1.1 三支柱现状盘点

可观测性不是"上 Prometheus"。三支柱回答的问题不同，优先级也不同：

| 支柱 | 回答什么问题 | 落地状态 | 优先级 |
|---|---|---|---|
| **Metrics** 指标 | 数值趋势如何？是否越界？ | LLM 指标已落库 + 管理端看板已上线；Prometheus 集成为计划 | P0 |
| **Logs** 日志 | 某个请求具体发生了什么？ | 已有 trace_id 贯穿 + 工具调用审计 100% 落库 | P2 |
| **Traces** 追踪 | 一次调用跨了哪些服务、慢在哪？ | 有 trace_id，未接 OpenTelemetry | P3 |

关键认知：大多数教程接完 Prometheus 只给你 HTTP 延迟/QPS/错误率——通用指标差异化价值一般。**真正值钱的是 AI 特有指标**：TTFT（首 token 延迟）、token 成本、按 agent 类型的耗时分布、LLM 失败率。正确顺序是**先把自己的业务指标捞出来，再上通用基础设施**；反过来做会得到一个"有 Grafana 但没什么可看"的空壳。

### 1.2 现状勘查结论："原料已齐八成，缺的是接线和渲染"

链路追踪面板动手前的勘查发现——思维链与工具链数据**后端已全部产生并随响应返回前端**，只缺渲染和三个字段：

- `ToolRound` 数据类（`customer_model_tools.py`）已记录：`tool`（调了什么）、`arguments`（做了什么）、`success`/`error`（成功没）、`reasoning`（模型自述的调用理由，即思维链）、`citations`/`evidence_status`；
- `ModelToolOutcome.decisions` 还记录了**被护栏拦截**的调用（越界/重复）；
- 轨迹已按层注入 `task_results[].data.model_tool_trace` 随 SSE 响应到达前端；
- 每次工具调用已落审计（`action="customer_agent.tool_call"`），是历史回溯的现成数据源；
- 系统级指标侧：TTFT/token/耗时只有 `logger.info`，未落库未暴露；`/metrics` 端点已预留限流豁免但从未实现——典型的"埋了没接线"。

### 1.3 阶段一：对话内链路追踪面板（✅ 已落地）

给 `ToolRound` 补齐观测字段并新增前端面板 `AgentTracePanel.vue`：

```python
@dataclass
class ToolRound:
    round_index: int
    tool: str
    arguments: dict
    success: bool
    error: str | None = None
    evidence_status: str | None = None
    citations: int = 0
    reasoning: str = ""
    duration_ms: float | None = None        # 本轮工具调用耗时
    llm_duration_ms: float | None = None    # 决策 LLM 耗时（与工具耗时分开记）
    prompt_tokens: int | None = None
    completion_tokens: int | None = None
    output_preview: str = ""                # 结构性摘要，脱敏，截断
```

实现要点（都是踩坑后得出的口径纪律）：

1. **token 归因到轮次**：在 provider 上挂 `last_call_usage` 属性，每轮决策后**读取并清空**——用量是"最近一次"语义，不清空会让下一轮沿用上一轮数字导致 token 虚高。不改 `request_tool_call` 返回值，避免破坏既有测试契约；观测字段缺失用 `getattr` 降级，不让观测失败拖垮工具链路。
2. **`duration_ms` 与 `llm_duration_ms` 分开记**：工具慢说明下游查询慢，LLM 慢说明模型侧慢，合并记就分辨不出来。
3. **确定性路径不记 token**（规则补齐不经 LLM，记 0 会让成本显得"免费"）；**被拦截的轮次要记 token**（决策 LLM 调用已真实发生，只给成功轮次记账会系统性低估成本）。
4. **`output_preview` 必须脱敏**：只保留结构摘要（"命中 N 条知识块；返回 M 条记录"），不落客户资产等敏感原文。

历史回溯接口（✅ 已实现）：

```
GET /api/v1/customer-service/conversations/{conversation_id}/trace
```

数据源直接查 `AuditLog`（`action='customer_agent.tool_call' AND resource_id=:conversation_id`）。权限拆两条路径：客户只能看自己的会话（`actor_user_id == user.id`）；坐席/风控凭 `audit:read` 可看任意会话；无归属记录返回**空列表**而非 403/404——避免用错误码差异泄露他人会话是否存在。

前端面板渲染纪律：默认折叠；顶部摘要一行给出四个数字（调用次数/被拦截次数/总耗时/总 token）；状态三色徽章（成功绿/失败红/被拦截黄）；`reasoning` 单独弱化显示；token 为 `None` 显示"—"不显示 0。

**面板上线当天就暴露了两个此前完全不可见的问题**（可观测性的价值实证）：

1. **同一意图重复检索**：面板摘要直接显示"4 次工具调用 · 28668ms · 6651 tokens"，同一 query 连续 4 次调用 `search_customer_knowledge`、命中同一批知识块，一路调到 `budget_exhausted`。根因是"同一意图已成功过"只回灌相同内容、不提示模型。修复后同一 query 调用次数 4 → 2。
2. **护栏可视化**：模型自行"多调一个工具去解释"，越出计划范围被拦（`tool_out_of_plan_scope`），**被拦调用连同自述动机都留存在面板上**——"安全护栏真的在工作"的直观证据。

经验：摘要行数字异常比逐条查看更容易发现问题；耗时必须按轮归因（决策 LLM vs 工具执行分开）。

注意：链路面板只在 LangGraph 图路径下产生，依赖两个默认关闭的开关 `AGENT_GRAPH_ENABLED` 与 `AGENT_MODEL_TOOL_SELECTION_ENABLED`（实机验收时已在 compose 中改为默认 `true`）。另有一次未通过的对照验收：graph vs pipeline 对照 9/14 完全一致，4 条为 LLM 生成波动可接受，但 1 条知识类问答结构性退化（`completed` → `partially_answered`），按"有差异即切流阻塞项"口径，切流需知情决策。

### 1.4 阶段二：LLM 指标落库与管理端看板（✅ 已落地）

**架构选择：异步落库，不同步写库。** `qwen.py` 属于 infrastructure 层没有 db session，硬塞会破坏分层。复用数据飞轮已有的模式：**写 jsonl → worker 异步消费 → 落库**。不阻塞主链路，LLM 超时失败时采集不受影响。

```
qwen.py 埋点(_emit_llm_metric, 全异常吞掉)
    │ 追加写
    ▼
logs/llm_metrics.jsonl
    │ tail + offset
    ▼
metrics_worker ──批量 INSERT──▶ llm_call_metric 表
                                      │
                                      ▼
                    /admin/metrics/{llm,business,infrastructure}
                                      │
                                      ▼
                    管理端 MetricsDashboardView（手写 SVG 图表，零图表依赖）
```

表结构核心字段：`trace_id`/`conversation_id`（关联）、`agent_type`/`model`/`call_kind`（chat/stream/tool/classify）、`status`/`error_type`、`ttft_ms`/`duration_ms`、`prompt_tokens`/`completion_tokens`。

**TTFT 口径修正**：原代码在第一个 chunk 就记 `ttft_ms`，但流式首个 chunk 通常是空包（`delta.content=""`），量到的是"首个网络包"而非"首个可见 token"，偏乐观。改法：把赋值移到拿到非空 `delta` 之后。

分位数计算用 PostgreSQL 原生函数，且**必须过滤 `call_kind='stream'`**——`ttft_ms` 只有流式调用才有，否则 NULL 污染分位：

```sql
SELECT
  percentile_cont(0.50) WITHIN GROUP (ORDER BY ttft_ms) AS ttft_p50,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY ttft_ms) AS ttft_p95
FROM llm_call_metric
WHERE call_kind = 'stream' AND status = 'ok'
  AND created_at >= NOW() - INTERVAL '24 hours';
```

**看板的三条渲染纪律（各配 E2E 断言）**——前端最容易在"看起来没问题"的地方撒谎：

1. **`null` ≠ 0**：`ttft_p50_ms` 为 null 表示窗口内没有流式样本，必须显示"—"且附原因，同时断言页面不出现 `0 ms`（后者会被读成"首字延迟极低"）。
2. **分母为 0 时不给百分比**：后端 0 分母返回 `0.0`，直接渲染会把"还没有已决草稿"显示成 `0.0%`——与"客户从不采纳草稿"是两件事。
3. **趋势必须补齐时间轴**：`GROUP BY date_trunc('hour')` 只返回有数据的桶，直接连线会把"某两小时没人用过"画成连续下滑线。前端补齐空桶置 null，图表在 null 处断开。

**实施中发现并修掉的两个隐性缺陷**（都属于"指标错了没人会发现"那一类）：

1. **测试污染真实指标文件**：pytest 用例走真实 QwenProvider + 假 client，瞬时返回写出 `ttft_ms=0` 记录，聚合出的 TTFT P50/P95 全是 0。修复：`_emit_llm_metric` 增加 `PYTEST_CURRENT_TEST` 守卫。看板是用来举证的，被假样本污染比没有数据更糟。
2. **文件轮转让管线静默死亡**：偏移停在旧位置时，`line_no <= offset` 会跳过之后所有新行——worker 一直在跑、日志不报错、指标却再也不更新。修复：检测"总行数 < 已消费偏移"即复位重扫（重复由主键兜住）。

**比照抄更严的一处**：参照的 `bad_case_worker` 是"读的时候就推进偏移"，会留下"读到了但入库失败 → 永久丢这批"的窗口。本 worker 改为**提交成功之后才推进偏移**——实测第一次启动就撞上建表竞态，照抄版本那 3 条指标就永久丢了。

看板最终形态含：调用/失败趋势、首字延迟趋势、Token 堆叠分布、按模型表、错误类型、业务可用率四卡（一次成功率/澄清率/转人工率/草稿采纳率）、Outbox 健康度，及可折叠的口径说明。业务与基础设施指标不新增表、不新增 worker——数据本来就在留痕表里，缺的只是聚合与呈现。

**实施偏差记录**（文档比代码早，要写明免得下次照着错）：迁移版本实际为 `0027`（方案写完后链上又加了 0026，接错会产生两个 head 导致 `alembic upgrade` 失败，已加"迁移链恰好一个 head"的结构性守卫测试）；trace 工具实际路径为 `app.common.middleware.trace`；端点实际为 3 个而非 1 个。

### 1.5 阶段三/四：Prometheus 与分布式追踪（计划，未实施）

阶段三（计划）：`prometheus-fastapi-instrumentator` 两行接管 HTTP 延迟/QPS/错误率；自定义 AI 指标：

| 指标名 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `llm_ttft_seconds` | Histogram | `model`, `agent_type` | 首 token 延迟，buckets 0.1/0.25/0.5/1/2/5 |
| `llm_duration_seconds` | Histogram | `model`, `call_kind` | 整体耗时 |
| `llm_tokens_total` | Counter | `model`, `direction` | prompt / completion |
| `llm_calls_total` | Counter | `model`, `status` | 调用数与失败率分母 |
| `llm_tool_calls_total` | Counter | `tool`, `blocked` | `blocked=true` 为被护栏拦截 |
| `outbox_pending_events` | Gauge | — | 异步队列积压 |
| `outbox_dead_events_total` | Counter | — | dead 事件累计 |

其中 `outbox` 两项比 LLM 指标更重要——**异步系统的生命体征**。最少 3 条告警：LLM P95 延迟超阈值持续 5 分钟、`outbox_dead_events_total` 增长 > 0、`outbox_pending_events` 持续超阈值。

阶段四（可选）：`trace_id` 已贯穿全链路，接 OpenTelemetry + Jaeger 打通 API → Outbox → Worker → 外部 LLM 的 span 链路，优先级最低。

其他注意事项：token 用量适合趋势与成本估算，**不适合对账**（上游 usage 可能延迟到达或流式中断时缺失）；指标采集函数必须吞掉所有异常——观测手段一旦能让业务失败，就是设计事故。

## 2. 数据飞轮机制

### 2.1 飞轮的本质：改运行时，不改代码

飞轮不是"系统自动改代码、自动微调模型"。**飞轮在运行时层面持续优化系统的动态配置**，修改对象：

| 修改对象 | 相当于什么 | 修改方式 |
|---|---|---|
| Skill 文件 | Agent 的"操作手册" | 修改文件 |
| Prompt 模板 | Agent 的"指令" | 修改配置库 |
| top_k / temperature | 检索和生成的"调参" | 修改配置库 |
| Query 改写规则 | RAG 的"入口" | 修改配置库 |
| 长期记忆 | Agent 的"经验库" | 记忆写入 |
| 知识库内容 | RAG 的"资料库" | 补充/修正文档 |

一句话：改的是 Skill/Prompt/记忆/配置，不是代码、不是模型参数。改完立即生效，错了立即回滚。

**飞轮的能力边界**——飞轮解决的是"已有能力没用好"的问题：

| 问题类型 | 飞轮能解决吗 | 原因 |
|---|---|---|
| 检索策略不对 | ✅ | 改 top_k、权重、query 改写 |
| 知识缺失 | ✅ | 补充文档、修正错误片段 |
| 指令不清 | ✅ | 改 Skill、改 Prompt |
| 口语表达没覆盖 | ✅ | Query 归一化、同义映射 |
| 工具本身有 Bug | ❌ | API 返回数据是错的，改 Skill 没用 |
| 数据源有问题 | ❌ | 文档本身是错的 |
| 模型能力不足 | ❌ | 模型做不了复杂逻辑推理 |
| 架构设计缺陷 | ❌ | 底层架构限制能力上限 |

### 2.2 四齿架构

```
┌──────────────────────────────────────────────────────────┐
│                        数据飞轮                           │
│                                                          │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐ │
│  │ 信号（评测）   │──▶│ 积累（记忆）   │──▶│ 落地（修复）   │ │
│  │ 发现什么问题   │   │ 记住什么经验   │   │ 怎么改配置    │ │
│  └──────────────┘   └──────────────┘   └──────────────┘ │
│        Bad Case收集     Skill/记忆库      配置库更新       │
│        失败模式归因      版本控制          灰度发布          │
│                                     │                    │
│                                     ▼                    │
│                              ┌──────────────┐            │
│                              │ 控制（人机）   │            │
│                              │ 审核/门控/回滚 │            │
│                              └──────────────┘            │
│                                     │                    │
│                                     ▼                    │
│                               下一轮评测（回流）           │
└──────────────────────────────────────────────────────────┘
```

| 齿 | 职责 | 产出 |
|---|---|---|
| 信号（评测） | 发现问题、判断好坏 | 失败模式分类、归因报告 |
| 积累（记忆） | 沉淀经验、防止遗忘 | Skill/记忆/知识库更新 |
| 落地（修复） | 生成候选、验证效果 | 配置库更新、灰度发布 |
| 控制（人机） | 审核门控、安全回滚 | 通过/拒绝/回滚决策 |

### 2.3 已落地的飞轮组件

| 组件 | 作用 |
|---|---|
| 评测集 `scripts/intent_eval_cases.json` | 48 条（train 23 / val 13 / test 12），覆盖 clear/口语/否定/指代/模糊/多意图/歧义/对抗/转人工/政策，每条带 `split` 字段 |
| 评测 runner `run_intent_eval.py` | `--mode rules/llm` + `--split`，输出准确率 + 澄清率 + 失败清单 |
| 自动修复 `auto_repair_intent.py` | 读失败案例 → LLM 生成 Diff 式修复候选 → `--validate` 验证 + `--apply` 落地 |
| 候选自动验证 | 候选注入理解层配置，在 **train+val**（不碰 test）上跑"基准 vs 带候选"，只落地提升/非降的批次 |
| test 回归门禁 `check_intent_regression.py` | 改配置后跑 test 集对比存档基线，回归则拦截（退出码 1） |
| 配置版本化 `config_versioning.py` | live = `config/understanding.yaml`，`config/history/` 存不可变快照；`--apply` 自动落版本，`rollback` 一键回滚 |
| 灰度发布 | 按查询哈希分流放量（`start/status/promote/abort`），影响 few-shot/模型路由 |
| RAG 评测集 + runner | 18 条（train 12 / val 3 / test 3），query → 期望命中的 gold_fragments；跑真实混合检索算 fragment_recall / hit_rate / evidence_rate |
| RAG 参数调优 `tune_rag_params.py` | 在 val 上网格搜 top_k/rrf_k/min_score 最优组合，`--apply-best` 落地（自动落版本） |
| RAG 回归门禁 `check_rag_regression.py` | 检索参数改动后跑 test 集对比基线，hit/recall 回归则拦截 |
| bad case 自动检测 `bad_case_collector.py` | 按意图 unknown/低置信/规则回退、RAG 证据不足/转人工、澄清卡住等信号自动判定 bad case |
| bad case 积累 `BadCaseStore` | 去重落 `logs/bad_cases.jsonl`（`BAD_CASE_COLLECT=1` 才开，异常安全） |
| bad case 审查/导出 `review_bad_cases.py` | 按原因分布查看，`--export` 导出待标注清单 |

**bad case 回流闭环的诚实边界**：

```
线上 query ──自动检测──▶ bad case 判定 ──自动积累──▶ logs/bad_cases.jsonl
                                                        │
                                                   --export 导出
                                                        ▼
                                              人工确认期望意图（标注 gold）
                                                        ▼
                                              追加进 intent_eval_cases.json
                                                        ▼
                                        auto_repair 生成候选 → val 验证 → test 门禁
```

- **已自动化**：bad case 的运行时检测与积累；
- **仍为人工**：升级进评测集必须人工确认期望意图——不能把未标注的线上 query 当 gold 硬塞（会污染评测）；且全流程需人工触发命令，非常驻 daemon。

一句话："线上自动检测 + 自动积累"已成，"自动标注 + 自动加评测集 + 自动常驻"仍是人工。

### 2.4 评测集三分法

- **train**：诊断失败、调 prompt/规则，可反复改；
- **val**：筛选改进候选，防止对 train 过拟合（改完先看 val）；
- **test**：**最终验证**，调优过程中不碰，衡量真实泛化。

各 split 都覆盖全部类别，test 特意含硬案例（否定、指代、多意图、歧义、对抗）。

### 2.5 安全边界：模型只能改理解层，不能改执行层

理解层旋钮已外部化到 `config/understanding.yaml`（模型路由、难度权重、检索参数、意图 prompt/few-shot、关键词映射），运行时加载、可被 `auto_repair --apply` 写入。

**执行侧的安全闸门绝不能让模型自改**：交易永不升级、`explicit_confirmation=False`、`must_not_submit`、非法改数据硬门禁、SubjectScope、幂等、审计。模型最多只能改"理解层"（prompt/关键词/示例），**不能改"执行层"（权限/风控/确认/写操作）**——否则模型改自己意图规则时可能无意削弱安全。

### 2.6 飞轮核心原则

1. **评测的可信度 > 系统的复杂度**。评测不可信的系统，自动化程度越高，犯错速度越快。
2. **飞轮解决"已有能力没用好"**。工具 Bug、数据源错误、模型能力不足必须靠改代码/加工具/换模型。
3. **闭环的价值在环节之间的衔接**。评测信号必须能流进配置更新；更新后必须能被评测验证；验证结果必须反哺下一轮。
4. **先跑通 Phase 0**。一个能手动转一圈的粗糙飞轮，好过一个精美但静止的蓝图。

## 3. 意图识别评测：方法与结果

### 3.1 意图识别实现改造

| 改动 | 作用 |
|---|---|
| Function Calling（`tools` + `tool_choice`） | 原生结构化输出，API 保证合法 JSON，去掉"文本→json.loads"脆弱层 |
| few-shot 示例 | 教模型规范格式（模板码/任务结构/实体 `{value,certainty}`），含多意图连词示例 |
| 模板/实体容错 | 模板不可靠时按意图派生；实体字符串归一化为 `{value,certainty}` |
| 中文→规范意图映射 | `canonical_template` + 中文关键词别名 |
| 非法改数据硬门禁 | "改余额/删账户/注销" → 强制 unknown + 拦截 |
| 安全闸门 | 交易永不升级、`explicit_confirmation=False`、`must_not_submit` |

### 3.2 评测指标口径（三个率）

每条用例打三个判断：

```python
intent_match  = exp_intents <= set(actual_intents)      # 期望意图 ⊆ 实际意图（子集匹配，多识别不算错）
clarify_match = exp["requires_clarification"] == actual_clarify   # 澄清布尔判断是否一致
完全准确率 = count(intent_match and clarify_match) / n   # 意图对 且 澄清对
```

- **意图匹配率**：模型是否**覆盖**该条期望的所有意图（多意图须全命中，多识别不算错）——语义能力；
- **澄清匹配率**：对"要不要向用户追问"的布尔判断是否与期望一致——金融场景关键：**该澄清没澄清可能带错下单，所以"认错也要澄清/转人工，不出资金事故"**；
- **完全准确率**：意图对且澄清对才算，最严综合分。

"意图对但完全失败"的例子：`common_11 "我要买1000元稳健型产品"` 期望 `[business_operation]`、不需澄清；模型给了 `[product_recommendation, business_operation]`（意图子集命中）但判了需澄清 → 完全准确率记失败。这解释了为何"意图 95.3%、完全仅 81.2%"。

### 3.3 评测基线（64 条：48 难例 + 16 常见）

原 48 条刻意偏难（口语/否定/指代/歧义/多意图/对抗），不能代表真实分布；补 16 条常见用例后得"总体"基线。

| 模式 | 完全准确率 | 意图匹配率 | 澄清率 |
|---|---|---|---|
| 规则 | 37.5% | 43.8% | 71.9% |
| LLM v1.2（修复前） | 60.9% | 70.3% | 81.2% |
| LLM v1.4（健壮性修复后） | 68.8% | 79.7% | 84.4% |
| LLM v1.5（紧凑 few-shot 后） | 70.3% | 82.8% | 85.9% |
| LLM v1.6（语义映射 few-shot 后） | 79.7% | 92.2% | 85.9% |
| **LLM v1.7（意图映射收敛后）** | **81.2%** | **95.3%** | **82.8%** |

规则路径 test 集（真泛化）仅 33.3% 意图匹配率；LLM 约为规则的 2.2 倍。

各版本迭代中值得记录的根因发现：

- **v1.4（+7.9pt）**：六处修复——JSON 截断/畸形兜底、`certainty` 非法值归一化、词表漂移映射、LLM 解析失败走规则规划器兜底、澄清语义对齐、口语多意图 few-shot。
- **v1.5（+1.5pt，但解析成功率 92.2% → 100%）**：全量打点发现 `finish_reason` 恒为 `None`（此 API 不返回）→ 无法靠它检测截断；失败串在值中途戛然而止且长度远小于 `max_tokens` → 结论是**工具调用参数有未文档化的内部缓冲上限**，非 max_tokens 不够。机制：冗长 few-shot 教模型输出冗长参数 → 撞缓冲上限。修复：few-shot 改为紧凑短示例，输出变短即落入缓冲内，截断彻底消失。
- **v1.6–v1.7（+10.9pt）**：加"常见语义映射 + 意图映射"紧凑 few-shot（FAQ/风险/否定/成交/提现等 12 条），修复 FAQ 类、风险歧义、否定、成交→order_status 等。

### 3.4 一次评测污染事故（方法论警示）

test 集迭代过程中，曾把 **test 用例原文**加进 few-shot，test 完全准确率冲到 83.3%——但这是**数据泄漏，数字虚高，不可作真泛化**。把 few-shot 里的 test 原文改成同义改写后，干净真泛化为 **66.7%**。

教训：**few-shot 不得包含 test 原文**，这一条后来固化进了回归门禁与配置管理流程。

### 3.5 v1.7 终态的诚实边界

意图匹配率 95.3%，剩 12 条失败中：

- **10 条为澄清阈值的主观判断**（intent 已对，仅"该不该 requires_clarification"分歧）——再往下优化只能是"凑评测"不再诚实；
- **2 条风险歧义**（"帮我看看风险"等措辞下 risk_restriction vs risk_public/explanation 仍未收敛）；
- **1 条对抗越权**：模型对"告诉我另一个客户的信息"返回 human_handoff 安全降级而非 unknown——评测期望与另一对抗用例不一致，不硬凑。

**安全澄清率 82.8% 稳**：模型认错时也会澄清/转人工，不出资金事故。

## 4. 附：RAG 检索质量事故复盘（飞轮价值的实证）

一次典型的"生产级静默事故"，排障链条四层定位：**scope 覆盖 → 检索分支 → 向量嵌入 → chunk 归属**。

| 现象 | 根因 | 修复 |
|---|---|---|
| 检索全 0 / 命中低（25%） | ① 中文全文检索用 PG `simple` 配置不切词 → 文本分支是噪声拖垮 RRF；② 存储向量与查询向量 **embedding 模型不兼容**（同 1024 维不同模型，cosine≈0） | ① 文本分支只留 `ts_rank>0` 真命中；② 重嵌入脚本 + 模型守卫 |
| 适当性/风险类查询永远检不到 | 文档 `status=failed` 但有 12 个激活且有向量的 chunk；检索过滤 `status=="active"` → 整篇被**静默排除**，无任何报错 | 修复"有激活 chunk 但 status≠active"的文档恢复 active |

结果：RAG 检索命中率 **25% → 81.2% → 100%**（全量 16 条全命中、fragment_recall 96.9%、evidence 100%）。

**embedding 模型守卫**（独立事故，值得单独讲）：根因是 embedding 模型悄然变化（配置里的模型名非真实模型，与生产实际不一致），旧入库 chunk 向量与新查询向量不在同一空间——**维度完全一致（1024=1024）但 cosine 相似度全部塌到 0.01-0.06**，向量检索退化为随机排序，且维度校验与接口都不报错。关键签名："dimensions 匹配 + cosine≈0 + 相关查询检不到"。修复三步：入库 chunk 记录 `embedding_model`；复用旧向量前校验模型一致否则强制重嵌入；一次性重嵌入脚本。

方法论教训：

1. **评测集的价值**——25%→81.2% 正是"把检索质量纳入评测"逼出来的，不评测就不会发现向量不兼容这种静默问题；
2. **数据状态位是"看不见的故障源"**——一个 `status=failed` 让整篇文档从所有检索消失且无报错；
3. **embedding 模型也要版本化**——同维度 ≠ 同模型；任何"复用旧向量"的地方都必须带模型标识校验；
4. **排障要分层二分**——scope → 检索分支 → 向量 → chunk 归属，逐层定位比瞎猜快。
