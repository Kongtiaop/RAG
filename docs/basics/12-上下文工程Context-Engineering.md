# 上下文工程（Context Engineering）入门

> 类型: 通用基础知识（与项目无关）

## 一、是什么与解决什么问题

上下文工程（Context Engineering）是指：**在模型每次推理之前，系统性地决定"把哪些信息放进上下文窗口、以什么结构放、放多少、何时淘汰"的工程实践**。

它被视为 Prompt Engineering 的自然演进：

- **Prompt Engineering** 关注的是"一句话怎么写才好"——措辞、格式、few-shot 示例、思维链提示。它优化的是单条指令的质量。
- **Context Engineering** 关注的是"整个输入怎么组装"——系统指令、对话历史、工具返回结果、检索到的文档、外部记忆，这些都占用 token，都需要被管理。

为什么要演进？因为当应用从"单轮问答"走向"带工具的 Agent、长对话助手、RAG 系统"后，瓶颈不再是"提示词写得不好"，而是：

1. **模型每轮只看到你喂给它的东西**。它没有持久记忆，看不到你上一次裁剪掉的内容，看不到检索时没选中的文档。上下文之外的信息对模型等于不存在。
2. **上下文是稀缺资源**（下节展开）。
3. **组装方式影响输出质量**，有时甚至超过提示词本身的影响。同样的模型，喂入顺序、结构、噪声水平不同，效果差异巨大。

一句话定位：**上下文是模型的"工作内存"，上下文工程就是这门"内存管理"的学科。**

## 二、为什么上下文是稀缺资源

很多人以为"窗口越大越好，塞满就行"。实际上上下文至少在三方面是稀缺的：

### 1. 注意力衰减

模型对上下文的利用并不均匀。普遍观察到的现象（不同模型、不同版本表现有差异，但趋势是通用的）：

- **Lost in the middle**：模型对上下文开头和结尾的内容利用较好，位于中部的内容容易被忽略。关键信息应尽量放在开头（或最近的对话末尾），而不是埋在长文档中间。
- **噪声稀释**：无关内容不是"中性的"。塞入大量不相关文本会降低模型对相关内容的响应质量——模型需要花"注意力"去区分信噪比。
- **指令遗忘**：上下文越长，早期的系统指令和约束越容易被"漂移"违背。长对话中模型可能逐渐忘记开头的格式要求。

### 2. 成本与延迟

- 多数 API 按 token 计费，上下文越长越贵；Agent 场景中历史消息每轮都随请求重发，成本随对话轮次近似平方级增长。
- 长上下文增加首 token 延迟；即使支持 prompt cache，超出缓存前缀的部分仍要重新计算。

### 3. 窗口上限

即使号称"百万 token 窗口"，有效利用长度通常远小于标称值。把标称窗口当作硬预算去填满，是最常见的设计错误。

**结论：上下文预算永远比窗口上限小，分配要主动、有策略。**

## 三、核心概念：上下文预算与分配

### 典型的上下文组成

一次 LLM API 调用的输入通常由以下部分拼成：

| 组成部分 | 内容 | 特点 |
|---|---|---|
| 系统指令 | 角色、规则、输出格式、安全约束 | 相对固定，应放最前，优先级最高 |
| 工具定义 | 函数 schema 列表 | 固定但占 token，工具多时开销可观 |
| 检索内容 | RAG 文档、知识库片段 | 大块、低密度、易过期 |
| 工具结果 | 函数调用返回值 | 变长、可能极大（如整页 JSON） |
| 对话历史 | 之前的用户/助手消息 | 持续增长，含大量冗余 |
| 用户消息 | 当前输入 | 通常放末尾，注意力最强位置 |
| 外部记忆 | 记忆文件、状态摘要 | 小而密，高信息密度 |

### 分配策略的通用原则

没有普适的百分比，但决策逻辑是通用的：

1. **按"信息密度 × 任务相关度"排序保留**。系统指令和记忆文件密度高，优先保留；原始检索文本和长工具结果密度低，优先压缩或裁剪。
2. **为"新增内容"预留空间**。Agent 运行中工具结果和中间推理会持续进入上下文，预算不能一开始就用满。
3. **关键约束写在开头，当前任务信息放末尾**，利用注意力的"两端偏好"。
4. **每类内容问一句：这个 token 花得值吗？** 删掉它，模型输出会变差吗？如果答案模棱两可，通常可以删。

一个粗糙的起步参考（需按任务实测调整）：系统指令与工具定义合计控制在总预算的 10~20%；检索内容与工具结果是大头，目标是不超过 40~50%；历史消息经压缩后占剩余部分。

## 四、压缩与淘汰

当上下文接近预算上限时，有三类手段：

### 1. 摘要（Summarization / Compaction）

- 把旧的对话历史用模型总结成一段摘要，替换原文。摘要应保留：任务目标、已做决策、未完成事项、关键中间结果。
- 常见做法是"滚动摘要"：始终维护一份"截至上一轮的摘要 + 最近 N 轮原文"。
- 注意：摘要是有损的，细节（精确数值、代码片段、ID）应在摘要前外置到文件/数据库，需要时再按 ID 取回。

### 2. 裁剪（Truncation / Pruning）

- 直接丢弃旧消息或大块旧内容，比摘要便宜（不额外调用模型），但更粗暴。
- 适合丢弃"已经消费完"的内容：例如工具结果已被模型转述进回答，原始返回值就没有保留价值。

### 3. 结构化注入（Structured Injection）

- 与其塞入一大段自然语言，不如把信息转成**结构化、可扫读**的形态：列表、表格、键值对、带标题的分区。
- 给每块内容加"来源/时间/用途"标注（如 `[来源: 数据库查询, 2025-01]`），帮助模型判断可信度与新旧。
- 相比等长的散文，结构化文本的信息密度和被遵循率通常更高。

## 五、上下文的写入与维护

上下文工程不只是"读"（往窗口里放什么），还包括"写"（把什么持久化下来、放在哪）。

### 记忆文件

- 把跨会话需要的信息（用户偏好、项目约定、长期决策）写入持久化文件（如 markdown 备忘录），每次会话开始时注入精简版。
- 记忆文件本身也要维护：定期去重、合并、淘汰过期条目，否则会膨胀成新的"塞满上下文"问题。

### 状态外置（State Externalization）

- Agent 的任务状态（todo 列表、中间产物、已探索的路径）不必全放上下文。写到文件或数据库，上下文里只保留**当前状态的摘要 + 指针**（"详细清单见 /path/todo.md"）。
- 需要时通过工具读取，即"按需加载"。这本质上是把上下文当作 CPU 缓存，把外部存储当作主存。
- 好处：上下文稳定、可恢复（进程重启后从文件重建）、可审计。

## 六、工具结果的处理

工具返回值是上下文膨胀最常见的来源。处理原则：

### 1. 在进入上下文之前就瘦身

- **服务端裁剪**：工具执行层在把结果回传给模型前先过滤——去掉无关字段、只返回请求的分页、把大 JSON 转成摘要 + 关键字段。
- **截断要有信号**：允许截断时，明确告知模型"结果被截断，共 N 条，已显示前 M 条"，让它知道可以翻页或缩小查询范围，而不是误以为数据只有这么多。

### 2. 分页与按需加载

- 列表类结果默认返回首页（小 limit），提供 offset/cursor 参数让模型按需取更多。
- 大文档类结果返回目录/摘要，提供"读取第 X 节"的工具，让模型按需深入。

### 3. 结果与历史分离

- 工具结果被消费后（模型已基于它完成回答），在后续轮次可以替换成一行占位符（如 `[工具结果已省略：查询订单 12345，返回 3 条记录]`），保留线索、释放空间。

## 七、实践清单

- [ ] 给应用设定显式的上下文预算（远小于模型标称窗口），并监控每轮实际用量。
- [ ] 系统指令精简、前置；把"当前任务相关信息"放在输入末尾。
- [ ] 检索内容进上下文前做筛选和排序，而不是 top-k 直接倾倒。
- [ ] 工具结果在执行层裁剪、分页、截断时附带明确信号。
- [ ] 长对话实现滚动摘要；摘要前把精确数据外置到可检索的存储。
- [ ] Agent 状态写入外部文件/数据库，上下文只留摘要与指针。
- [ ] 给上下文内容加结构与来源标注，避免大段无结构散文。
- [ ] 定期审计：把真实对话的上下文打印出来人工检查，问"哪些 token 是浪费的"。
- [ ] 有条件时使用 prompt cache：把稳定内容（系统指令、工具定义）放前缀，动态内容放后缀。

## 八、新手常踩的坑

### 1. 塞满上下文

"窗口 128k，我全用上"——结果是注意力稀释、成本翻倍、指令遗忘。窗口上限是天花板，不是目标。有效上下文通常远小于标称值。

### 2. 把对话历史当数据库

期望模型"记得 200 轮之前说过的那个数字"。对话历史是易失的、会被压缩淘汰的，不是可靠存储。任何需要精确回溯的信息都应外置到结构化存储，而不是依赖历史消息。

### 3. 无结构的长文本注入

把整篇文档、整个网页原文直接贴进 prompt。模型要自己找重点，找到也未必重视。应预先切片、加标题、标注来源，让模型"扫一眼就知道每块是什么"。

### 4. 摘要丢掉了关键细节

摘要擅长保留"讲了什么"，容易丢"精确值"。订单号、金额、代码片段这类内容一旦被摘要抹掉，后续无法恢复。原则：**先外置、再摘要**。

### 5. 工具结果无限增长

每个工具调用返回几 KB 看似不大，Agent 跑 50 步后历史里堆着几 MB 的旧 JSON。要么在回传前瘦身，要么在后续轮次替换为占位符。

### 6. 只优化提示词，不优化上下文

反复调措辞却忽略输入里混进的过期检索内容、冗余历史。在长上下文应用里，**清理噪声的收益通常大于润色提示词**。

### 7. 记忆系统只写不删

把每次对话都往记忆文件里追加，几周后记忆本身成了超长文本，每轮注入成本高、相关性低。记忆需要 GC：去重、合并、按最后使用时间淘汰。

---

## 小结

上下文工程的核心心智模型：**上下文 = 模型的工作内存，token = 预算，你负责内存管理**。三个抓手：

1. **分配**：按信息密度和任务相关度决定放什么，关键信息放两端。
2. **压缩**：摘要、裁剪、结构化注入，配合状态外置和按需加载。
3. **维护**：工具结果瘦身、历史淘汰、记忆文件的持续清理。

与其追求"更大的窗口"，不如追求"更干净的输入"。
