# 数据飞轮 Data Flywheel

> 类型: 通用基础知识（与项目无关）

## 一、是什么与解决什么问题

**数据飞轮**指的是这样一个增强回路：用户使用产品 → 使用过程产生数据 → 数据回流到研发流程 → 产品/模型得到改进 → 体验更好带来更多使用 → 产生更多数据。一旦转起来，产品改进速度和用户规模互相加持，形成竞争对手难以复制的循环优势。

它要解决的问题很具体：**LLM 应用的效果提升不能只靠开发者坐在工位上想 prompt**。模型能力有上限、需求千差万别、badcase 层出不穷——没有系统性的数据回流，优化就是无源之水：你不知道用户真实遇到什么问题、不知道改动在真实分布上有没有变好。

飞轮的反面是"开环"：上线 → 偶尔看看报表 → 凭感觉改两行 prompt → 循环结束（因为根本没循环）。

## 二、LLM 应用里的飞轮长什么样

以一个典型的对话式/Agent 应用为例，飞轮的完整一圈：

```
用户使用
   │  产生
   ▼
对话日志 / 交互埋点（查询、回答、工具调用、用户反馈：点赞点踩、重试、转人工）
   │  筛选
   ▼
badcase 收集（用户明确不满的 + 抽样发现的 + 指标异常的）
   │  整理
   ▼
标注与归因（是检索没召回？prompt 不当？模型能力不足？需求本身模糊？）
   │  分流
   ▼
┌─ 进入评测集 → 保护性回归测试（确保改动不退步）
├─ 进入微调数据 → 模型迭代（数据量足够时）
└─ 直接改 prompt / 改检索策略 / 改工具配置
   │  产生
   ▼
效果提升 → 用户更信任 → 使用更多 → 更多数据 ……（回到顶部）
```

关键观察：

- **同一条 badcase 通常有两个去向**：进入评测集（防止回归）和驱动某次具体改动（修复问题）。只有第二个没有第一个，修好的问题随时可能被下一次改动悄悄弄坏。
- **用户反馈信号不只有"点赞/点踩"**：重试同一问题、立即转人工、复制走答案后流失、追问澄清——这些行为信号往往比显式反馈量更大、更真实。
- 飞轮不只服务于模型微调。大多数团队阶段里，**飞轮的产出主要是评测集和 prompt/策略迭代**，微调数据是数据量上来之后的事。

## 三、搭建飞轮的组件

### 3.1 日志与追踪（地基）

- 记录完整输入输出：用户查询、检索到的上下文、prompt 模板与版本、模型回复、工具调用序列、token 用量与延迟。
- 每条记录带**版本标签**：用的哪个 prompt 版本、哪个模型、哪套检索配置。没有版本标签的日志无法归因，也建不出可比的评测集。
- 结构化存储（数据库/数据仓库），而不是散落的文本文件，否则后面没法批量分析和标注。

### 3.2 badcase 收集入口

- 给用户一个低成本反馈通道（哪怕只是一个"不满意"按钮），同时从行为信号里自动挖掘疑似 badcase（重试、转人工）。
- 团队内部也要有入口：任何人发现 badcase，一条命令/一个表单就能提交，而不是在群里贴个截图然后沉底。
- 定期抽样常规流量做人工巡检——用户不反馈不等于没有问题，很多用户默默离开。

### 3.3 标注流程

- 归因优先：这条 badcase 是哪个环节的问题（检索/生成/工具/需求理解）？归因决定了修复动作落在哪。
- 简单的标注规范就够用：问题分类标签 + 预期答案/预期行为 + 严重程度。不要一开始就追求复杂本体。
- 标注结果要有去处：进评测集、进微调数据池、或直接开一个修复任务。**标注完没有下游去向的标注是纯成本。**

### 3.4 评测集版本化

- 评测集像代码一样管理：进 git（或至少有版本号与变更记录），每次修改可追溯。
- 分层结构：**核心回归集**（稳定的旧用例，每次改动必跑）+ **新增用例**（近期 badcase 转化而来）+ **holdout 集**（从不参与优化的保留集，防止对评测集过拟合）。
- 每条用例记录来源与日期，方便判断评测集是否还反映真实分布。

## 四、冷启动：没有用户数据怎么办

产品还没上线、或流量太小，飞轮转不起来。正确做法是**先造内循环**——用户数据还没有，就先用自己的问题当数据：

1. **自建种子评测集**：团队每人写 10~20 个真实场景问题（包括故意刁难的边界用例），配上预期答案或验收标准。
2. **跑基线**：当前版本在种子集上的分数存档。
3. **改 prompt / 改检索 → 重跑评测 → 对比基线**：每一轮改动都被测试保护，而不是改完凭印象判断。
4. 上线后第一批真实流量里收集 badcase，替换/补充种子集，逐步把"人造分布"换成"真实分布"。

内循环的意义：它让你在飞轮启动前就**养成"改动必须过评测"的习惯**，等真实数据到来时，回流管道是现成的。

## 五、闭环的关键：回流必须变成具体动作

飞轮最容易断的一环就在这里。看板上的曲线、"本周 badcase 数"的报表，本身不构成飞轮——**只有当数据触发了一个可执行的动作并跟踪到完成，闭环才闭合**。

可执行的动作包括：

- 一条新评测用例进入回归集（带 PR/commit 记录）；
- 一个 prompt 修改（明确写出它对应哪些 badcase）；
- 一次检索策略调整、一条知识库补充、一个工具修复；
- 一批微调数据进入训练队列。

配套机制：

- **每个 badcase 有状态**：待归因 → 已归因 → 已修复 → 已进评测集。定期清积压。
- **改动与数据双向可追溯**：从一条评测用例能找到当初的 badcase 来源，从一个 prompt 版本能知道它修复了哪些问题、是否引起其他用例回归。
- **定期复盘动作的有效性**：修复后重跑全量评测，确认没有按下葫芦浮起瓢。

## 六、一个最小可用的飞轮流水线（示意）

不需要复杂平台，冷启动阶段一张表加一个脚本就能跑起来：

```python
# badcase 队列：一行一条，唯一入口
# 字段：id / 日期 / 来源(用户反馈|行为信号|内部巡检) / 原始日志引用 /
#       归因分类 / 严重程度 / 状态(待归因|已归因|已修复|已进评测集) / 去向

import csv

def weekly_review(rows):
    """每周例会跑一次：按状态统计，列出待处理项"""
    pending = [r for r in rows if r["状态"] != "已进评测集"]
    print(f"未闭环 badcase：{len(pending)} 条")
    for r in pending:
        print(f"  [{r['归因分类']}] {r['原始日志引用']} -> {r['状态']}")
```

配套两个固定动作：

- **每周例会**过一遍队列，为每条新 badcase 指定归因人和去向；
- **每次改动前**跑核心回归集，改动后把新增评测用例连同修复 commit 一起归档。

工具不重要，重要的是状态流转有人维护。等流量上来，再把它升级到日志平台 + 标注工具 + 自动化评测流水线。

## 七、实践清单

- [ ] 上线第一天就记录完整结构化日志，每条带 prompt/模型/配置版本号。
- [ ] 给用户一个零成本的反馈通道，同时定义 2~3 个行为信号作为 badcase 触发条件。
- [ ] 建立 badcase 的唯一入口和状态流转（归因 → 修复 → 进评测集），指定处理责任人。
- [ ] 评测集版本化并分层（核心回归 / 新增 / holdout），badcase 优先转化为评测用例。
- [ ] 每个迭代周期检查：本周回流数据触发了哪些具体改动？改动是否都过了回归评测？
- [ ] 定期用真实流量分布校对评测集分布，偏差大时补采样。
- [ ] 涉及用户数据的日志采集、存储、标注，先过一遍隐私合规再动工。

## 八、新手常踩的坑

1. **只埋点不回流**：日志堆了几十个 G，从来没人分析；数据被"记录"了但从未被"使用"。判断标准很简单——过去一个月，日志触发了多少具体改动？答案是零就等于没有飞轮。
2. **评测集与真实分布脱节**：评测集全是构造出来的理想用例，真实用户的口语化、多轮、含混提问完全没覆盖。分数很好看，线上问题照旧。对策：评测用例必须持续从真实流量补充。
3. **隐私合规被忽略**：用户对话里天然混有个人信息。日志直接进数据仓库、被拿去标注甚至训练，可能违反隐私法规与平台条款。对策：上线前确定脱敏/匿名化方案、明确数据留存期限、标注数据的授权范围。
4. **飞轮只画在 PPT 上，没有 owner**：架构图很漂亮，但没有具体的人负责看 badcase 队列、没有固定的复盘节奏。飞轮不是"架构"而是"流程"，流程需要 owner 和例会。
5. **反馈信号被当成金标准**：用户点踩的原因可能是问错了对象、心情不好，自动判为 badcase 会引入噪声。反馈信号要结合人工复核再入库。同样，点赞多也不代表没问题，满意的用户往往不发声。
6. **急于微调**：数据才几百条就想微调模型。多数阶段里，把 badcase 转成评测用例 + 迭代 prompt/检索，投入产出比远高于微调；微调放到数据充足、且 prompt 已到瓶颈时再考虑。
7. **修复不回归**：改了 prompt 修好 A 问题，悄悄弄坏了 B 问题，没人发现。每个修复动作都要跑全量回归评测。
8. **把"数据多"当成"飞轮转"**：日志量、标注量只是中间产物，飞轮是否转起来的唯一标准是"数据驱动的改动是否持续发生并带来可测量的效果提升"。

## 小结

- 数据飞轮 = 使用 → 数据 → 回流 → 改进 → 更多使用的闭环，核心价值是让优化基于真实分布而非直觉。
- 地基是带版本标签的结构化日志；入口是 badcase 收集；转化是标注归因；保障是版本化的分层评测集。
- 冷启动先造内循环：自建种子评测集，把"改前必测"变成团队习惯。
- 闭环判据只有一条：数据有没有变成具体动作并跟踪完成。没有 owner 和例会的飞轮只是 PPT。
