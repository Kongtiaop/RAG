# Embedding 与向量索引原理：把"含义"变成"几何"

> 类型: 通用基础知识（与项目无关）；基于 2026-10 公开资料整理

## 一、是什么与解决什么问题

### 1.1 Embedding 的直觉：语义压成几何

Embedding 模型把一段文本（也可以是图片、音频）映射成一个固定长度的浮点向量，例如
`[0.12, -0.83, 0.41, ...]`（常见维度 384~3072）。关键性质是：

> **含义相近的文本，向量方向相近。** "如何退货"和"退款流程是什么"字面几乎不重叠，
> 但在向量空间里夹角很小。

于是"语义搜索"变成了"几何问题"：把所有文档变成向量存起来，查询时把 query 也变成
向量，找最近的那些点。传统关键词搜索匹配"字面"，向量搜索匹配"意思"，这是 RAG、
推荐、去重、聚类的地基。

### 1.2 一个心智模型

把想象中的"语义宇宙"想成地球仪：

- 每篇文档是上面的一个点，位置由模型根据训练语料中的语义规律摆放。
- 同一主题的点自然聚在一起（医疗一片、法律一片）。
- 查询向量是"你所在的位置"，检索就是"找最近的 K 个邻居"（KNN）。

## 二、主流模型格局与选型维度

### 2.1 两类来源

| 类型 | 代表 | 特点 |
|------|------|------|
| 开源自托管 | **BGE 系列（bge-m3、bge-large-zh 等）**、GTE、E5、Jina 系列 | 免费可私有化，需要自己管理推理资源；bge-m3 支持多语言+稠密/稀疏/多向量混合输出 |
| 商用 API | OpenAI text-embedding 系列、Cohere Embed、 voyage、阿里/百度等国内厂商 | 免运维、质量稳定，按 token 计费，数据要出本地 |

### 2.2 选型维度清单

1. **维度**：越高表达力通常越强，但存储和计算成本线性上涨（3072 维是 384 维 8 倍的存储）。
2. **语言覆盖**：纯中文场景选中文强的模型；混合场景选多语言模型。
3. **长文本支持**：模型最大输入 token（如 512 vs 8192）决定要不要分块、怎么分块。
4. **费用与时延**：自托管一次性批量建索引，API 按量付费；查询时延要求高的场景慎用外部 API。
5. **榜单参考**：MTEB / C-MTEB（中文）是常用基准，但**务必用自己的数据抽样评测**，
   榜单第一不等于你的场景第一。

### 2.3 最小示例

```python
from sentence_transformers import SentenceTransformer

# 开源模型示例（首次运行会自动下载）
model = SentenceTransformer("BAAI/bge-m3")   # 或 "BAAI/bge-large-zh-v1.5"
docs = ["如何申请退款", "退货政策说明", "今天天气不错"]
doc_vecs = model.encode(docs, normalize_embeddings=True)  # (3, dim)

query_vec = model.encode(["退款怎么弄"], normalize_embeddings=True)
scores = (doc_vecs @ query_vec.T).squeeze()   # 余弦相似度（已归一化）
print(scores)  # 前两条明显更高 → 语义检索生效
```

生产中更常见的是走向量数据库（FAISS / Milvus / Qdrant / pgvector 等），
它们的核心工作就是下面要讲的"ANN 索引"。

## 三、相似度度量：cosine、内积、L2 的关系

设两个向量 a、b：

- **余弦相似度**：`cos = (a·b) / (|a||b|)`，只看方向不看长度，取值 [-1, 1]。
- **内积（点积）**：`a·b`，同时受方向和模长影响。
- **欧氏距离（L2）**：`|a-b|`，空间直线距离。

三者存在恒等关系（对归一化后的向量）：

```
若 |a| = |b| = 1，则  L2² = 2 - 2·cos ，且  a·b = cos
```

**即：向量归一化后，内积排序 = 余弦排序 = L2 距离排序（反向）**。这就是为什么
实践中大家都"先归一化、再点积"——一次乘法搞定，且三种度量结果一致。

## 四、为什么需要 ANN 索引

### 4.1 暴力扫描不可行

精确最近邻 = 把 query 向量与库中**每一条**向量都算一次相似度再排序。计算量
`O(N × d)`：1 亿条 × 1024 维，一次查询就是千亿次浮点运算，即使 GPU 也难做到
毫秒级响应。所以需要 **ANN（Approximate Nearest Neighbor，近似最近邻）索引**：
牺牲一点点召回率，换几个数量级的速度。

### 4.2 三大索引原理直觉对比

| 索引 | 直觉 | 查询方式 | 优点 | 缺点 |
|------|------|----------|------|------|
| **FLAT**（暴力） | 逐个比对 | 全量扫描 | 100% 召回，实现零成本 | 大库太慢，只适合 <10 万条 |
| **HNSW**（分层图导航） | 像"跳表+社交网络"：多层近邻图，从顶层粗跳到局部细查 | 沿边贪心走查目标点 | 高召回+低时延，无需训练 | 内存占用大（要存大量边），建图慢，删除更新较麻烦 |
| **IVF-PQ**（聚类+量化） | 先 K-means 聚成 1 万个"桶"，桶内向量再做 PQ 压缩 | 先找最近的几个桶，再在桶内比对 | 内存极省（可压 10~30 倍），适合亿级库 | 召回率对参数敏感，有训练过程，精度有损 |

一句话总结两种思路：**HNSW 是"图导航"（跟着邻居边走过去），IVF-PQ 是
"先聚类缩小范围、再把向量压缩后比个大概"**。

### 4.3 召回-速度-内存三角

三个指标互相牵制，调参就是在这个三角形里找你的平衡点：

```
        召回率
        /    \
   速度快 ——— 内存省
   （HNSW 占前两个，IVF-PQ 用召回换后两个）
```

- HNSW 调参：`M`（每个点的边数，越大越准越耗内存）、`ef_search`（搜索候选队列
  长度，越大越准越慢）。
- IVF 调参：`nlist`（桶数，经验值 ≈ sqrt(N)）、`nprobe`（每次查几个桶，越大越准越慢）。
- PQ 调参：子段数 m 越大越准、压缩率越低。

## 五、量化与降维：给向量"减负"

- **标量量化（SQ）**：float32 → int8，内存省 4 倍，精度损失通常很小，性价比最高。
- **乘积量化（PQ）**：把向量切成 m 段，每段用小码本编码成 1 字节，压缩激进，
  大库场景标配（IVF-PQ 中的 PQ）。
- **降维**：PCA / 随机投影 / 直接选低维模型，把 3072 维砍到 512 维，
  适合"维度过高、成本敏感"的场景。
- 注意：**压缩率不是免费的**，每一步都要用自己数据测召回率（见第七节坑 4）。

## 六、什么时候向量检索"不对"

向量检索匹配语义，但很多需求恰恰不需要语义：

| 场景 | 为什么向量不行 | 更合适的做法 |
|------|----------------|--------------|
| 精确型号/订单号/错误码 | "ERR_40213" 无语义可学，任何文本都能"沾边" | 关键词/倒排索引精确匹配 |
| 代码搜索 | 标识符、运算符是强结构信息，语义模型反而模糊 | BM25 + 符号索引（如 ripgrep/ctags） |
| 法律条款引用、人名 | 一字之差就是不同对象 | 关键词 + 过滤条件 |
| 冷门缩写、新造词 | 训练语料里没见过，向量不可靠 | 关键词兜底 + 同义词表 |

结论：**生产级检索几乎都是混合检索（Hybrid Search）**——向量负责"意思相近"，
关键词（BM25/倒排）负责"字面必须对"，再用 RRF（倒数排名融合）或加权合并两路结果。
bge-m3 的稠密+稀疏双输出、主流向量库内置 BM25，都是在为混合检索服务。

## 七、新手常踩的坑

1. **维度不匹配**：query 和文档用了不同模型/配置，向量维度不同直接报错；或者
   分块时截断方式不一致导致同文不同向量。建库前固定模型与预处理流水线。
2. **归一化遗漏**：混用余弦 API 和点积 API，却没归一化向量，排序结果"看起来能用"
   但实际被模长污染。约定"入库即归一化"最省心。
3. **模型混用**：建索引用模型 A，查询用模型 B——两个模型的向量空间完全不同，
   相似度没有意义。模型版本要像数据库 schema 一样纳入管理，换模型必须全量重建索引。
4. **召回率不评测**：只看"搜出来感觉还行"，从不标注 ground truth 算 Recall@K。
   换索引参数、换压缩方式后性能悄悄劣化都不知道。建议：抽 100~500 条真实 query
   人工标注相关文档，建立最小评测集，任何改动前后跑一遍。
5. **分块策略随口定**：块太大（淹没细节）或太小（丢失上下文）都会拖垮召回质量，
   分块和 embedding 一样需要评测迭代。
6. **把 HNSW 当默认答案**：十万以下小库 FLAT 足够又省心；内存受限的亿级库
   HNSW 可能直接爆内存，IVF-PQ 更合适。先看数据规模再选索引。
7. **忘了元数据过滤**："只搜 2024 年之后的文档"这类条件靠向量相似度表达不了，
   要用向量库的标量过滤（先过滤再 ANN，或预过滤策略），设计时就该想清楚。
