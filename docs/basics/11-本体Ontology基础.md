# 本体基础：让机器共享同一套概念

> 本文与《08-知识图谱基础》互补：08 讲图数据库、图谱工程与 GraphRAG 流程；本文聚焦**本体建模这一层**——如何定义领域里有哪类东西、它们有什么关系、遵循什么约束。

## 1. 本体是什么：从哲学到工程

**本体（Ontology）** 一词源自哲学，研究"存在什么"以及"存在物如何分类"。亚里士多德的范畴论（实体、性质、关系……）本质上就是在做一份"世界万物清单"。

信息系统领域借用了这个词。被广泛引用的定义（Gruber, 1993）是：

> 本体是**概念化的显式规格说明**（An ontology is an explicit specification of a conceptualization.）

翻译成工程师语言：本体是一份**机器可读的、关于某个领域"有哪些概念、概念之间是什么关系、受什么约束"的形式化说明**。可以类比：

- 类比数据库：本体 ≈ **schema**，实例数据 ≈ 表里的行。但本体比传统 schema 表达力强得多（可定义继承、等价、推理规则）。
- 类比编程：本体 ≈ **类型系统 + 领域模型**（Domain Model），实例 ≈ 运行时对象。
- 类比协议：本体 ≈ 通信双方约定的**数据字典**，没有它，两边各说各话。

注意术语歧义：工程实践中说"一个 ontology"通常指**具体某个领域的概念模型文档/文件**；学术界说的"the ontology"才是哲学那个本体论。本文讨论前者。

一个常见的分层视角：

```
本体/Schema 层：  Person --worksAt--> Company   （概念与规则，相对稳定）
实例/数据 层：   张三 --worksAt--> ACME 公司    （具体事实，持续增长）
```

知识图谱就是"本体 + 实例"的具体载体；本体是其中相对稳定的骨架。

## 2. 为什么需要本体

三个核心动机：

### 2.1 数据互操作（Interoperability）

同一事物在不同系统里叫法不同：CRM 里的 `客户`、工单系统里的 `客户`、数据仓库里的 `customer_id`，含义和字段可能对不齐。本体提供**受控词表（Controlled Vocabulary）**：统一术语、统一含义、统一映射规则，是跨系统数据整合和主数据管理（MDM）的语义基础。

### 2.2 领域共识

一个领域内"什么算一个产品、什么算一次订单、退款算不算交易"这类问题，需要一份各方都认可的正式定义。本体把这些定义**显式化、可审查、可版本化**，而不是散落在代码、文档和某位老员工的脑子里。

### 2.3 推理（Reasoning）

本体不仅描述数据，还能**推出隐含的事实**。例如声明"每个项目负责人都是员工"，那么"张三负责项目 P"成立时，机器可以推出"张三是员工"以及"张三出现在所有'查询全体员工'的结果里"。这类推理不需要额外写 if-else，而是由本体定义 + 推理机（Reasoner）自动完成。

### 2.4 什么时候不需要

本体不是免费的：建模、对齐、维护都有成本。如果只是单系统内部用、概念很少变动、没有跨系统交换需求，一个普通的类定义或数据库 schema 就够了。**引入本体的信号**：多系统/多团队需要统一语义、需要标准化数据交换、需要基于类型的自动推理、领域知识需要长期沉淀复用。

## 3. 核心构件

用一个小例子贯穿：给"公司项目"领域建模。

### 3.1 类（Class）

类是**实体的类型/范畴**，如 `Person（人）`、`Company（公司）`、`Project（项目）`。类之间可以有**层级（Subclass）**：`Employee ⊑ Person`（Employee 是 Person 的子类）。层级支撑"子类实例也是父类实例"的推理。

注意与面向对象的差异：本体中的类更多是**集合式的分类**，关注"哪些个体属于这个集合、集合间有什么包含关系"，而非"对象有哪些行为"。

### 3.2 属性（Property / Attribute）

描述某个类实例的**特征**，通常取字面值（字符串、数字、日期）：

```
Person: name（姓名）, email（邮箱）
Project: startDate（开始日期）, budget（预算）
```

### 3.3 关系（Relation / Object Property）

连接两个实例的**有向边**，通常连接两个类的实例：

```
Person --worksAt--> Company      （就职于）
Person --manages--> Project      （负责）
Project --belongsTo--> Company   （属于）
```

关系同样可以有层级：`leads ⊑ worksOn`（"主导"是"参与"的子关系）。RDF 术语里属性和关系统称 Property，按取值是字面量还是资源分为 Datatype Property / Object Property——工程上记住"属性挂值、关系连点"即可。

### 3.4 实例（Instance / Individual）

类的具体个体，即实际数据：`张三 是 Person 的实例`、`Project-P1 是 Project 的实例`。本体定义"类与关系"，实例层存放"谁是谁"。08 篇讲的三元组数据，就是填充在本体骨架上的实例。

### 3.5 公理（Axiom）

公理是**形式化的约束与规则声明**，是本体区别于普通 ER 图的关键。常见几类：

- **域/值域约束（Domain / Range）**：`manages` 的主体必须是 Person，客体必须是 Project。
- **基数约束（Cardinality）**：每个 Project 必须恰好有一个负责人。
- **子类/子关系公理**：`Employee ⊑ Person`。
- **等价公理**：`Client = Customer`（两个类指同一集合，做数据对齐时极有用）。
- **不相交公理（Disjointness）**：Person 和 Company 没有公共实例，可拦截"某公司就职于某公司"这类脏数据。
- **传递/对称等性质（Transitive / Symmetric）**：`isPartOf` 是传递的，于是 A 是 B 的一部分、B 是 C 的一部分，可推出 A 是 C 的一部分。

### 3.6 小例子串起来

```
类：        Person, Company, Project, Department
子类公理：   Employee ⊑ Person
属性：      Person.name, Project.budget
关系：      worksAt(Person → Company),
            manages(Person → Project)   [domain=Person, range=Project]
不相交公理： Person 与 Company 不相交
实例：      张三, ACME, Project-P1
推理链：    manages(张三, P1) + manages 的 domain=Person
            ⟹ 张三是 Person
            + 张三 worksAt ACME + Employee ⊑ Person 的逆用/声明
            ⟹ 张三是 Employee，进而是 Person
```

前四类构件（类、属性、关系、实例）很多模型工具都有；**公理才是本体技术的增量**——它把"人类默认的理解"写成机器可校验、可推理的声明。

## 4. 标准与技术栈

W3C 语义网技术栈是本体的主流标准体系。各层角色：

| 标准 | 角色 | 一句话 |
|---|---|---|
| **RDF** | 数据模型 | 万物皆三元组（主语, 谓语, 宾语），实例层的基础 |
| **RDFS** | 轻量词表 | 定义类、子类、属性、domain/range，最基础的本体语言 |
| **OWL** | 本体语言 | 在 RDFS 上加公理表达力（等价、不相交、基数、性质），配合推理机使用 |
| **SPARQL** | 查询语言 | 图模式匹配式查询，类比 SQL 之于关系库 |
| **SHACL** | 约束校验 | 定义数据形状（Shape）并校验 RDF 数据是否合规，类比"数据质量规则" |

### 4.1 一小段 RDF/Turtle 示例

```turtle
@prefix : <http://example.com/company#> .

# 类与层级（本体层）
:Person   a owl:Class .
:Employee a owl:Class ; rdfs:subClassOf :Person .
:Company  a owl:Class .
:Project  a owl:Class .

# 关系及约束（本体层）
:manages a owl:ObjectProperty ;
         rdfs:domain :Person ;
         rdfs:range  :Project .

# 实例（数据层）
:zhangsan a :Employee ;
          :name "张三" ;
          :manages :p1 .
:p1 a :Project ; :budget 100000 .
```

### 4.2 SPARQL 查询

```sparql
# 查询所有管理者（即使数据里只声明了 manages，也能按 domain/range 找到人）
SELECT ?person ?project WHERE {
  ?person :manages ?project .
}
```

### 4.3 SHACL 校验

```turtle
@prefix sh: <http://www.w3.org/ns/shacl#> .

:ProjectShape a sh:NodeShape ;
  sh:targetClass :Project ;
  sh:property [
    sh:path :budget ;
    sh:datatype xsd:decimal ;   # 预算必须是数字
    sh:minCount 1 ;             # 必须有预算
  ] .
```

实践要点：

- **OWL 和 SHACL 是两种思路**：OWL 面向推理（开放世界假设，"没说的不算错"），SHACL 面向校验（封闭世界假设，"不符合 shape 即报错"）。数据质量把关用 SHACL 更直接。
- 工具链：Protégé 是经典本体编辑器；Apache Jena、rdflib（Python）是常用库；OWL 推理机有 HermiT、Pellet 等。
- **不必全栈使用**。属性图（Neo4j 等）生态通常只用"类 + 关系 + 简单约束"这一子集，用 YAML/JSON 定义 schema 也完全可行。标准的价值在互操作和推理，按需取用。

## 5. 建模方法论：复用优先

本体建模最重要的原则是**能复用就别自造**。

### 5.1 先找现成本体

| 现成资源 | 覆盖领域 |
|---|---|
| **Schema.org** | 通用实体：人、组织、商品、活动、评价……由搜索引擎推动，事实上的 Web 通用词表 |
| **FOAF** | 人物与社交关系 |
| **Dublin Core** | 文献与资源的通用元数据 |
| 领域本体 | 医疗（SNOMED CT）、财务（FIBO）、生物（GO）等，多为行业级、较重 |

复用的好处：术语已被广泛理解、跨系统天然兼容、避免重复踩坑。做法通常是"导入上层词表 + 定义本地子类扩展"，例如本地定义 `schema:Person` 的子类 `internal:Employee`。

### 5.2 从问题倒推（Competency Questions）

经典方法学（如 METHONTOLOGY、NeOn）都强调：先列出系统需要回答的**能力问题（Competency Questions）**，如"某项目的负责人向谁汇报"。这些问题的**词汇表**（出现的名词 → 类，动词 → 关系）就是本体的候选骨架。本体是为回答问题服务的，不是为完整刻画世界服务的。

### 5.3 迭代演进

本体不必一步到位。常见节奏：最小核心（3~10 个类）→ 挂实例数据验证 → 按新查询需求扩类与关系 → 定期重构。本体是**活文档**，应纳入版本管理（OWL 文件就是文本，天然适合 git）。

## 6. 本体与 LLM / RAG 时代

本体并不因大模型而过时，反而有新的结合点。

### 6.1 本体作为受控词表与结构化约束

LLM 的输出是自然语言，自由度高但不可控。把本体（允许的实体类型、关系类型、取值约束）注入 prompt 或函数签名，可以让 LLM 的抽取/分类输出**落到受控词表上**，而不是发明自己的标签。这是"LLM 输出结构化、可验证"的通用手段：prompt 给语义说明，本体给合法取值清单，SHACL/JSON Schema 做事后校验。

### 6.2 GraphRAG 中的 schema 层

GraphRAG（微软提出的图增强检索生成）流程中的抽取步骤，质量高度依赖 schema：给定清晰的本体（实体类型 + 关系类型清单），抽取一致性显著提升；不给 schema，LLM 会抽出一堆彼此对不齐的实体标签，图直接碎片化。08 篇讲过这个现象，其根源就是缺本体层。同时，schema 还可用于抽取后的**对齐与校验**：不合公理的三元组直接拦截。

### 6.3 LLM 辅助本体构建

反向地，LLM 也在降低本体构建门槛：

- 从文档/表格/代码中**起草**候选类、关系、公理，专家再审定（人机协作，LLM 提案、人拍板）；
- 帮助做**本体对齐**：判断两个词表里的类/属性是否等价；
- 把本体转成自然语言**解释**，或把自然语言需求转成 OWL/SHACL 草稿。

注意：LLM 起草的本体必须由领域专家审校——本体是长期共识资产，错误定义会被推理放大。

一句话：**LLM 负责"生成"和"解释"，本体负责"约束"和"沉淀"**。前者降低构建成本，后者保证长期质量。

## 7. 新手常踩的坑

1. **过度建模（Over-engineering）**：追求刻画"完整世界"，定义上百个类和深达七八层的类层级。本体是工具，answer 不了任何查询的精雕细琢都是负资产。对策：能力问题倒推，最小核心起步。
2. **为了完备牺牲可用**：等"建模完再进数据"。本体应随实例数据一起迭代；先有数据和查询，再让本体长出来。
3. **公理堆砌、推理翻车**：在 OWL 里声明大量复杂公理，结果推理机跑不动或推出意外结论（开放世界假设下，"少了一条数据"不会被当成矛盾，很多人会被此惊讶）。对策：公理从简，先理解开放世界假设再写等价/基数公理；质量校验交给 SHACL。
4. **与敏捷开发冲突**：把本体当成"必须冻结的需求文档"，或相反地频繁推翻重来。本体的正确定位是**可版本化、可演进的代码级资产**：有 review、有版本、有变更日志，但允许小步提交。
5. **词表不统一**：同一个关系有人写 `worksAt` 有人写 `employedBy`，实例层很快无法合并。对策：尽早立命名规范（URI 规则、大小写、单复数），并放进 schema 强约束。
6. **只建骨架不挂数据**：本体写得漂亮，实例数据从不校验对齐，最后 schema 是 schema、数据是数据。对策：每次写入做 shape 校验，让本体真正"管住"数据。
7. **一上来追求标准全栈**：团队没有语义网背景时，强行上 OWL 推理机 + 全套 W3C 栈，学习曲线会拖垮项目。可以先从"属性图 + JSON/YAML schema"起步，把概念（类/关系/约束）用对，标准工具链需要互操作时再引入。

## 8. 小结

- 本体 = **概念化的显式规格说明**：类、属性、关系、实例 + 公理，是知识图谱相对稳定的骨架。
- 核心价值：**互操作**（统一词表）、**共识**（显式化领域定义）、**推理**（由声明自动推出隐含事实）。
- 标准栈各司其职：RDF 管数据模型、RDFS/OWL 管本体定义、SPARQL 管查询、SHACL 管校验；可按需取用，不必全栈。
- 建模第一原则是**复用**（Schema.org 等现成词表），第二原则是**从能力问题倒推**，小步演进。
- LLM 时代本体没过时：它给 LLM 输出提供受控词表与校验约束（GraphRAG 的 schema 层），LLM 反过来降低本体构建与维护成本。
- 最大的坑是过度建模。本体是为回答问题和整合数据服务的，写不进查询、管不住数据的建模都是负债。
