# LLM 评测与 Harness 基础

> 类型: 通用基础知识（与项目无关）

## 一、是什么与解决什么问题

**没有 eval 的优化是盲猜。** 对 LLM 应用做任何改动——换模型、改 prompt、调检索参数——如果没有一套可重复的评测流程，你只能靠"感觉好像好了一点"来做决策。问题是 LLM 输出具有随机性、任务往往没有唯一正确答案、且改动的影响面常常出乎意料，肉眼抽查三五条样本完全不足以支撑判断。

评测（eval）要解决的就是：**把"这个改动有没有变好"变成一个可测量、可重复、可回归的问题。**

### 两个 harness：先消除歧义

"harness"这个词在 LLM 领域有两个常见含义，别混淆：

- **评测 harness（本文主角）**：数据集 + 运行器 + 打分器的自动化框架，负责把任务跑起来、收集输出、算分、出报告。类似软件工程里的"测试框架"。
- **Agent harness**：承载 Agent 运行的宿主环境——把模型接到工具、循环、上下文管理上，让 Agent 真正跑起来的那层程序（比如各类编码 CLI 的 agent 循环）。

本文以评测语境为主。记住一句话：**评测 harness 评的是"表现"，Agent harness 决定的是"怎么跑"。**

## 二、评测的基本构件

一套最小可用的评测体系包含四件东西：

1. **黄金数据集（golden dataset）**：一组带预期答案或评分标准的代表性输入。来源可以是真实用户案例、历史 badcase、人工构造的边界用例。关键是**有代表性**且**有标注**。
2. **任务定义**：清楚描述"输入什么 → 执行什么 → 产出什么"。对 Agent 应用还包括工具配置、执行步数上限等运行环境设定，且必须固定版本，否则结果不可比。
3. **打分器（scorer / judge）**：给每条输出打分的东西，可以是规则、断言、另一个 LLM，或人工。
4. **回归基线（baseline）**：把当前版本的分数存档。每次改动后重跑同一数据集，对比基线看回归还是提升。没有基线的分数是孤立数字，有了基线才是决策依据。

## 三、评测方法谱系

从便宜到贵、从客观到主观，常见打分方式按序排列。**原则：能用便宜的就用便宜的，只在必要时上贵的。**

### 3.1 精确匹配 / 规则指标

- 精确匹配（EM）：输出等于预期答案。适合抽取、分类、固定格式回答。
- 规则指标：正则匹配、必含关键词、格式校验（是否 JSON、是否包含引用来源）。
- 优点：便宜、确定、可重复。缺点：只能覆盖"有唯一答案"或"有明确形式要求"的任务。

### 3.2 单元测试断言

把评测当作软件测试写：每条用例是一组断言（输出包含 X、不包含 Y、字段 A 大于 0、调用了工具 B）。对 Agent 的工具调用序列尤其好用——可以断言"应该先查库再回答"。缺点是写用例有成本，覆盖不了开放性质量。

### 3.3 LLM-as-a-Judge

用另一个（通常更强的）模型给输出打分。适合开放式任务：总结质量、回答是否切题、语气是否得当。

要点：

- **原理**：把任务输入、模型输出（有时加上参考答案）连同评分标准一起交给 judge 模型，让它按 rubric 输出分数或判断。
- **rubric（评分细则）设计**：必须明确"几分的标准是什么"，例如"3 分 = 回答了问题且无事实错误；2 分 = 回答了但有遗漏；1 分 = 答非所问"。没有 rubric 的 judge 打分基本是噪声。rubric 最好附少量带分值的示例（few-shot 锚点）。
- **已知偏差**：
  - **位置偏差**：对比式 judge 倾向于偏好某个位置的答案（如总是选 A）。缓解：交换顺序评两次，或只取两次结果一致的样本。
  - **自偏好**：judge 偏好与自己风格相近的输出（比如同一家模型生成的文本）。缓解：judge 与被评模型用不同家族的模型。
  - **长度/格式偏好**：偏长、偏 markdown 排版漂亮的答案容易被打高分。缓解：rubric 中显式写明"长度与排版不计分"，或在 rubric 里惩罚冗余。
- **多 judge 投票**：用多个 judge（不同模型或不同 prompt 视角）独立打分，取多数或平均，显著降低单 judge 的随机性。成本上升，用于关键决策点。
- **先校准再用**：抽一小批样本，人工打分与 judge 打分对比，一致率可接受（通常看与人工的相关性）后才信任 judge 的分数。

### 3.4 人工评审的定位

人工评审最贵、最慢，但最接近真实质量。合理定位：

- 用于**建立校准集**（校准 LLM judge 用的小规模金标准）；
- 用于 judge 不确定、规则覆盖不了的抽样复核；
- 不必全量人工评审，抽样 + 分层（新用例多抽、老用例少抽）即可。

### 3.5 任务级指标 vs 组件级指标

| 层级 | 指标示例 | 说明 |
|---|---|---|
| 任务级（端到端） | 任务完成率、人工干预率、用户采纳率、一次通过率 | 衡量"整个应用有没有用" |
| 组件级（中间环节） | 检索召回率/精确率、答案忠实度（faithfulness）、工具调用正确率、延迟、token 成本 | 衡量"哪个环节拖后腿" |

端到端分数掉了时，组件级指标帮你定位是检索没召回、还是生成跑偏、还是工具调错了。评测设计时就应把组件级打点埋进去。

### 3.6 打分器的组合策略

实际项目里很少只用一种打分方式，常见的分层组合：

- **第一层：硬性门槛用规则**——格式合法、包含免责声明、引用了给出的来源，不满足直接判 0。便宜且可靠。
- **第二层：正确性用断言/精确匹配**——任务有确定答案的部分（抽取的字段、调用的工具、计算结果）逐条断言。
- **第三层：开放性质量用 judge**——语气、完整性、是否切题等主观维度交给 LLM judge 按 rubric 打分。
- **第四层：抽样人工复核**——对 judge 打的高分与低分样本抽样看一眼，持续校准 judge。

这样每条用例的总分由多个信号加权组成，既控制成本，又避免单一打分器的系统性偏差。

## 四、最小 eval 脚本示例

一个不依赖任何框架的骨架，说明 harness 的本质就是"跑 + 打分 + 报告"：

```python
def score(output: str, case: dict) -> dict:
    """规则打分器：可替换为 LLM-as-a-Judge"""
    checks = {
        "包含必备内容": all(k in output for k in case["must_include"]),
        "无违禁内容": all(k not in output for k in case["must_not_include"]),
    }
    return {"passed": all(checks.values()), "checks": checks}

def evaluate(cases):
    results = [score(run_task(c["input"]), c) for c in cases]
    rate = sum(r["passed"] for r in results) / len(results)
    report = {"通过率": rate, "失败明细": [
        {"input": c["input"], "checks": r["checks"]}
        for c, r in zip(cases, results) if not r["passed"]
    ]}
    with open("eval_report.json", "w", encoding="utf-8") as f:
        json.dump(report, f, ensure_ascii=False, indent=2)
    print(f"通过率: {rate:.0%}，报告已写入 eval_report.json")

if __name__ == "__main__":
    evaluate(CASES)
```

进阶做法：把 CASES 挪到版本化的数据文件（JSONL/CSV），把 `run_task` 换成被测流水线，把分数和 git commit 一起存档作为基线。现成框架（如各类 open-source eval harness）本质上就是把这个骨架工程化。

## 五、实践清单

- [ ] 任何优化动作前，先确认有一个能重跑、能对比的评测基线。
- [ ] 评测集里放进真实 badcase——它们比构造出来的完美样例更有价值。
- [ ] 打分器分层：能用规则和断言的不用 judge，能用单个 judge 的不用多个 judge。
- [ ] LLM judge 必须带明确 rubric，且上线前与人工评分做校准。
- [ ] 对比式评审要处理位置偏差（交换顺序 / 多 judge 投票）。
- [ ] 同时记录任务级与组件级指标，方便失败归因。
- [ ] 评测结果与代码/配置版本一起存档，形成可追溯的分数历史。
- [ ] 定期把新 badcase 转入评测集，让评测集随业务演化（见"数据飞轮"主题）。

## 六、新手常踩的坑

1. **用跑分代替业务指标**：公开 benchmark 分数高不等于你的场景表现好。评测集必须来自你的真实任务分布，通用跑分只能做初筛。
2. **judge 不设 rubric**：直接问 judge"这个回答好吗？1-10 分"，得到的是漂移的、不可比的噪声。必须给出分档标准和示例。
3. **数据集一成不变**：评测集半年不更新，模型早已 overfit 到这些题上，分数虚高而真实效果原地踏步。要有机制持续注入新用例。
4. **优化过拟合到评测集**：反复对着同一小集合调 prompt，评测集从"考试"变成了"背过的原题"。缓解：划分核心集与探索集、保留从未参与优化的 holdout 集、扩充用例多样性。
5. **评测随机性没控制**：LLM 输出有随机性，单次评测一个样本就下结论不可靠。温度设 0（或固定采样参数）、关键用例多次采样取稳定值、样本量足够大，分数才有意义。
6. **只看总分不看失败明细**：通过率从 82% 到 85% 没有意义，除非知道是哪些用例为什么翻盘/翻车。评测报告的价值在失败明细里。
7. **改动多个变量后跑评测**：一次改了 prompt + 模型 + 检索参数，分数变了也不知道归因给谁。每次评测尽量单变量改动。

## 小结

- 评测 = 黄金数据集 + 任务定义 + 打分器 + 回归基线，缺一不可。
- 打分方法从便宜到贵：规则/断言 → LLM-as-a-Judge → 人工评审，按需选用、逐层兜底。
- LLM judge 必须配 rubric 并做人工校准，警惕位置偏差与自偏好。
- 同时盯任务级与组件级指标；让评测集持续吸收新 badcase，评测体系才能长期有效。
