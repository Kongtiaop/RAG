# Agent 范式入门：ReAct、Plan-and-Execute、反思与多 Agent

> 类型: 通用基础知识（与项目无关）

## 一、是什么与解决什么问题

LLM 单次调用只能"读输入 → 写输出"。要完成需要多步、需要外部信息、需要根据反馈调整的现实任务（查数据再算结果、读代码再改 bug），就需要让模型**在循环中调用工具、观察结果、决定下一步**——这就是 Agent。

Agent 与"一次 prompt"的本质区别：**模型自己决定下一步做什么**，而不是由代码硬编码流程。

## 二、什么才算 Agent：五要素

判断一个系统是否算 Agent（以及算多强的 Agent），可以检查五个要素：

1. **目标（Goal）**：一个可以被表述和检验的任务目标，通常是自然语言描述的用户意图。
2. **循环（Loop）**：模型输出 → 执行动作 → 观察结果 → 再输出，能迭代多轮，而不是一问一答就结束。
3. **工具（Tools）**：能调用外部能力（搜索、代码执行、API），扩展模型自身能力边界。
4. **记忆（Memory）**：至少有对话内的工作记忆；更强的实现有跨轮/跨会话的外部记忆与状态外置。
5. **停止条件（Stop Condition）**：明确何时结束——任务完成信号、步数上限、预算耗尽、失败放弃。**没有停止条件的循环不是产品，是事故。**

五者齐备才是完整意义上的 Agent。只有"循环 + 工具"而没有明确停止条件的，是最容易失控的形态。

## 三、四大范式对比

| 维度 | ReAct | Plan-and-Execute | Reflection / 自我批判 | Multi-Agent 协作 |
|---|---|---|---|---|
| 核心机制 | 每轮"思考→行动→观察"交替，边走边看 | 先让模型产出完整计划，再逐步执行（执行器可换更便宜的模型） | 生成 → 自我审查/批评 → 修订，可迭代多轮 | 多个角色化 Agent 各司其职，通过消息/黑板协作，常有协调者 |
| LLM 调用形态 | 串行多轮，每轮都基于最新观察 | 规划 1 次 + 执行 N 次，规划可重排 | 至少 2 倍调用（生成 + 批判），可能多轮迭代 | 调用数 = Agent 数 × 轮数，通常最多 |
| 延迟与成本 | 中等；错误路径上会持续浪费 | 前置规划多花 1 次调用，但减少盲目试错 | 成本随迭代轮数线性增长 | 成本最高，通信与同步有额外开销 |
| 优点 | 简单、灵活、实现门槛最低；适合探索型任务 | 长任务有全局结构，方向不易跑偏；计划可人工审查 | 显著提升复杂推理和代码类任务的正确率 | 任务可分解并行；角色上下文各自纯净；可用不同模型混搭 |
| 缺点 | 缺乏全局规划，长任务易绕路；上下文随步数膨胀 | 环境与预期不符时，静态计划会失效（需配合重规划） | 自我批评可能"走过场"（说自己对了），或过度修订 | 错误会沿通信链传播；协调者可能成瓶颈；调试困难 |
| 典型场景 | 查询类、信息检索、单工具链调用：`查订单→查物流→汇总` | 多步骤交付型任务：调研报告、代码迁移、批量数据处理 | 代码生成与调试、数学推理、有明确质量标准的产出 | 软件开发流水线（规划/编码/测试/评审分工）、大规模并行研究 |

### 1. ReAct（Reasoning + Acting）

最小实现：模型每轮生成"想法 + 工具调用"，客户端执行工具，把结果拼回上下文，直到模型给出最终答案或触发停止条件。伪代码：

```python
while steps < MAX_STEPS:
    resp = llm(tools=tools, messages=history)
    if resp.tool_calls is None:
        return resp.text          # 最终答案
    for call in resp.tool_calls:
        result = execute(call)    # 客户端执行，非模型执行
        history.append(tool_result(call.id, result))
```

关键点：**工具由客户端代码执行**，模型只输出"想调用什么"；观察结果作为消息追加，驱动下一轮决策。

### 2. Plan-and-Execute

两阶段：先产出任务清单（可持久化、可审查），再逐项执行。执行中发现计划失效时触发**重规划**（Replan）。适合步骤多、有明确交付物的任务。与 ReAct 的本质差别：**先全局后局部**，避免"走一步看一步"的局部最优陷阱。

### 3. Reflection / 自我批判

在生成之后加一道审查：让模型（或另一个模型实例）依据明确标准检查产出，给出修改意见，再生成修订版。提升质量的两个前提：

- 批判要有**具体标准**（"检查是否处理了空输入"），而不是"再想想有没有问题"。
- 最好让**批判与生成分离**（不同上下文或不同模型），避免自我确认偏误。

### 4. Multi-Agent 协作

常见拓扑：

- **协调者-执行者（Orchestrator-Worker）**：一个主 Agent 拆解任务并分发，子 Agent 结果汇总。最常用、最可控。
- **流水线（Pipeline）**：规划 → 编码 → 测试 → 评审，串行接力。
- **辩论/群聊（Debate / Group Chat）**：多 Agent 就方案互相质询，用于需要多方视角的决策。

重要提醒：**Multi-Agent 不是银弹**。多数单 Agent 失败的任务，问题出在任务定义或工具质量，拆成多 Agent 只是把混乱放大。

### 范式组合是常态

四种范式不互斥，实际系统往往叠加使用。一个典型的"加重型"结构：

```text
用户任务
  └─ 规划（Plan-and-Execute）：产出任务清单
       └─ 每个子任务：ReAct 循环（思考→工具→观察）
             └─ 关键产出：Reflection 审查后修订
  └─ 大型子任务：交给协调者派发给子 Agent 并行完成
```

工程上的建议：**先用最轻的组合跑通，出现明确的失败模式（方向跑偏 → 加规划；质量不稳 → 加反思）再逐层加重**。每加一层复杂度，都要能指出它针对的失败案例，否则就是过度设计。

## 四、范式选择决策

按任务特征从上往下检查，命中即停：

1. **任务能通过 1~2 次固定工具调用完成？** → 不用 Agent 范式，直接编码调用链（workflow）。确定性流程用代码写，比让模型即兴发挥可靠得多。
2. **步骤不可预知、需要根据中间结果决定方向？** → ReAct。加步数上限和预算护栏。
3. **步骤多（>5 步）且有明确交付物、可预列清单？** → Plan-and-Execute，执行中允许重规划。
4. **产出有可检验的质量标准（代码、推理、格式）？** → 在上述基础上叠加 Reflection。
5. **任务天然可分解为多个独立子任务、单 Agent 上下文装不下？** → 考虑 Multi-Agent（优先协调者-执行者拓扑）。

### 什么时候树搜索才值得

在多个候选方向上探索（如复杂推理、求解难题）时，可以对"计划/分支"做树搜索（多路展开、评估打分、择优回溯）。但它把成本放大数倍到数十倍，只在**结果正确性价值极高、且无法靠单路径 + 反思达到**时才值得。工程上更常用的廉价替代：让模型生成 N 个独立方案，用评估器择优。

### 护栏设计（所有范式通用）

- **步数上限**：硬性最大循环次数（如 25 步），触发后强制收尾——让模型基于已有信息给出部分结果并说明未完成部分。
- **预算上限**：token/费用/时间上限，多 Agent 场景还要给子任务单独限额。
- **Human checkpoint**：不可逆操作（发送、支付、删除、发布、生产环境变更）前必须人工确认。这是安全底线，不是可选优化。
- **失败语义**：定义工具连续失败 N 次后的行为（换方法/报告失败），避免模型对同一个报错无限重试。

## 五、常见坑辨析

### 坑 1：CoT 不等于 Agent

让模型"一步步思考"然后输出答案，仍然是**单次生成**——没有行动、没有观察、没有根据反馈修正。CoT 只是提升了单次推理质量；Agent 的本质是**与环境的交互循环**。反过来也一样：加了工具调用循环但任务路径完全由代码固定，那是 workflow，不是 Agent。

### 坑 2：循环失控

症状：反复调用同一个失败工具、在两个动作间来回震荡、陷入自我对话不出结果。对策：

- 上文护栏四件套（步数/预算/checkpoint/失败语义）。
- 工具报错信息要"可行动"：告诉模型哪错了、该怎么办，而不是只给堆栈。
- 观察到重复模式（连续相同调用）时在框架层打断，注入提示"你已重复此操作，请改变策略"。

### 坑 3：把 workflow 包装成 agent

需求明明是固定三步流程，却写成"给模型一堆工具让它自己决定"。结果是不稳定、慢、贵、难调试。判别标准：**如果路径总能预先写死，就用代码写死；只有路径依赖中间结果、无法预知时才用 Agent 循环。** Agent 的灵活性是为不可预知性付费的，不要为已知流程付这笔钱。

### 坑 4：为炫技上 Multi-Agent

三个 Agent 互相聊天绕了十轮，不如一个 Agent 带好工具五步做完。Multi-Agent 的正当代价换来的收益只有两个：**并行加速**和**上下文隔离**。两者都不需要时，别拆。

## 六、实践清单

- [ ] 动手前用五要素自查：目标、循环、工具、记忆、停止条件，缺哪个补哪个。
- [ ] 默认从 ReAct 起步，跑通后再按决策树升级范式，不提前引入 Multi-Agent。
- [ ] 每个循环都有步数上限、预算上限，不可逆操作前有人工确认。
- [ ] 工具报错信息面向模型优化（可行动、可恢复），而不是面向人类调试。
- [ ] 记录每一步的完整轨迹（思考、调用、结果、耗时、token），用于调试与回归。
- [ ] Plan-and-Execute 的计划先展示给用户/开发者审查，再进入执行。
- [ ] Reflection 的批判标准具体化，并考虑与生成方分离上下文。
- [ ] 用固定的评测任务集对比范式选型，用数据决定，不凭感觉。

### 一个最小可用的 ReAct 骨架（语言无关伪代码）

供入门对照，生产实现可替换为框架：

```text
初始化: messages = [system(角色+规则+停止说明), user(任务)]
循环:
  1. resp = llm(messages, tools)
  2. 若 resp 是最终回答 → 返回
  3. 若 resp 是工具调用 → 校验参数 → 执行 → 追加 tool 消息（含错误修正提示）
  4. 步数+1；若达上限 → 注入"请基于已有信息收尾"的指令，强制最后一轮出答案
终止: 最终回答 / 达步数上限 / 达预算上限 / 连续失败 N 次
```

这个骨架只有约 20 行逻辑，却是检验后续一切扩展的基线：任何范式升级前，先确认这个基线在目标任务上的具体失败点。

---

## 小结

- Agent = 目标 + 循环 + 工具 + 记忆 + 停止条件，五要素缺一不可。
- 四大范式是一条复杂度递增的阶梯：ReAct → Plan-and-Execute → +Reflection → Multi-Agent，**按需升级，不越级**。
- 路径可预知的任务用代码写死（workflow），只有路径依赖中间结果的才配得上 Agent 循环。
- 护栏（步数/预算/人工确认/失败语义）不是可选项，是 Agent 从 demo 变成产品的分界线。
