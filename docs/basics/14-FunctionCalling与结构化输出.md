# Function Calling 与结构化输出入门

> 类型: 通用基础知识（与项目无关）

## 一、是什么与解决什么问题

LLM 原生只能生成文本。要让模型"查数据库、发请求、执行代码"，并且让返回的结果**可靠地被程序消费**，需要解决两个问题：

1. **如何让模型表达"我想调用某个函数，参数是这些"** → Function Calling（tool calling）。
2. **如何让模型的文本输出严格符合程序可解析的格式（JSON）** → 结构化输出（Structured Output）。

没有这两样，你只能用正则从自由文本里抠信息——脆弱、易错、无法规模化。这两项是构建 Agent、RAG、任何"LLM + 程序"混合系统的地基。

## 二、核心概念：Function Calling 的工作机制

理解关键：**模型从不执行任何函数，它只输出"调用意图"**。整个循环由你的代码驱动：

```text
① 声明        客户端把工具列表（名称 + 描述 + JSON Schema 参数定义）随请求发给模型
② 决策        模型判断需要调用工具时，输出结构化的调用请求（工具名 + 参数 JSON），
              而不是普通文本
③ 执行        客户端代码解析这个请求，在本地/服务端真正执行函数
④ 回传        客户端把执行结果作为 tool 消息追加到对话，再次请求模型
⑤ 回答        模型基于工具结果生成面向用户的最终回复（或决定再调用下一个工具，回到②）
```

要点：

- **②→③→④ 是一个循环**，可能转多圈（多步工具链），客户端负责编排和终止条件。
- 模型输出的参数本质仍是"模型生成的 JSON"，**不是 гарантиров 合法的**——校验责任在客户端（见第七节坑 4）。
- 工具执行权限、鉴权、副作用，全部是你的代码的事，模型侧没有任何保障。

## 三、用 JSON Schema / Pydantic 定义工具参数

工具声明由三部分组成：名称、描述、参数 schema。以 Pydantic 为例（它能同时充当"定义"和"校验"两职，推荐）：

```python
from pydantic import BaseModel, Field

class WeatherQuery(BaseModel):
    """查询指定城市的当前天气"""
    city: str = Field(description="城市名，如 '北京'")
    unit: str = Field(
        default="celsius",
        description="温度单位：celsius 或 fahrenheit",
        pattern="^(celsius|fahrenheit)$",
    )

tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "获取指定城市当前天气。当用户询问天气、温度、是否下雨时调用。",
        "parameters": WeatherQuery.model_json_schema(),
    },
}]
```

实践要点：

- **Field 的 description 是给模型看的**——写清楚取值范围、格式示例、边界情况，模型据此填参。
- 用枚举（enum）、pattern 约束取值，把"可能填错的自由度"在 schema 层封死。
- schema 是发给模型的输入，每次请求都会带上，**工具越多 token 开销越大**——这是控制工具数量的成本依据。

## 四、结构化输出：JSON Mode / Strict Mode / 约束解码

### 三种强度递进的机制

| 机制 | 原理 | 保证程度 | 说明 |
|---|---|---|---|
| 提示词约定 | 在 prompt 里要求"输出 JSON"并给示例 | 无保证 | 最脆弱，模型可能加解释、包 markdown 代码块 |
| JSON Mode | 服务端约束输出是合法 JSON 语法 | 语法合法 | 但不保证符合你的业务 schema（字段可能缺失/多余） |
| Strict / Structured Output | 提供 JSON Schema，服务端按 schema 强制生成 | 语法 + 结构 | 主流 API 的 `strict: true` / `response_format` 类能力，字段符合声明 |

### 约束解码（Constrained Decoding）

Strict 模式的底层原理：在生成的每一步，把"不符合 schema 的 token"从候选中屏蔽，只允许能产出合法结构的 token。这解释了两件事：

- Strict 模式能**保证**结构合法（不是靠运气）。
- 它可能增加延迟（需要预处理 schema），且**不保证语义正确**——字段类型对了，但内容可能仍是错的（如编造一个不存在的枚举外 ID）。

### 与 Function Calling 的关系

两者底层机制同源（都是约束模型输出结构化数据），定位不同：

- **Function Calling**：结构化输出的是"动作"（调哪个函数 + 参数），输出后需要你执行。
- **结构化输出**：结构化输出的是"数据"（如抽取的字段、分类结果、评分），输出后直接被程序消费。
- 经验法则：**需要触发副作用 → function calling；只需要提取/生成结构化数据 → 结构化输出**。不少 API 也允许把"返回固定 schema 的 JSON"本身当作一个伪工具来实现。

## 五、并行工具调用

当任务需要多个互不依赖的工具调用时，模型可以在**一轮输出中给出多个调用请求**（如同时查天气和查日历），客户端并行执行、并行回传，显著减少往返轮次。

```text
用户: 北京和上海今天哪个更热？
模型: [get_weather(北京), get_weather(上海)]   ← 一轮内两个调用
客户端: 并行执行两个请求，两条结果一起回传
模型: 上海今天 28°C，北京 21°C，上海更热。
```

处理要点：

- 客户端要按**调用 ID** 把结果与请求一一对应回传，不能错位。
- 有依赖关系时（先查 ID 再用 ID 查详情），模型会自然地分轮调用——客户端不应强行并行。
- 并行调用中的每个调用仍要独立校验，一个失败不影响其他成功的调用回传。

## 六、工具设计原则

工具是模型的 API。给模型用的 API 和给人用的 API，设计标准不同：

1. **少而清晰**。工具数量控制在个位数到十几个；功能重叠的工具（如 `search_web` 和 `web_query`）会让模型选择摇摆。能用一个参数区分的，不要拆成两个工具。
2. **幂等优先**。工具应尽量设计成重复调用无副作用（同一查询返回同一结果）；写操作工具要显式标记，并在客户端加确认层。模型重试、回退是常态，幂等性能兜底。
3. **参数即文档**。参数名自解释（`city` 而非 `c`），description 写清类型、单位、格式、示例、默认值。模型的填参质量直接取决于此。
4. **错误信息要能被模型读懂**。工具报错是给模型看的输入，不是给人类看的日志：
   - 差：`Error: ECONNREFUSED 0x8007274d`
   - 好：`查询失败：城市名 'bj' 无法识别。请使用完整中文城市名重试，如 '北京'。`
   错误信息里带"下一步怎么办"，模型才能自我修正。
5. **返回值精简且自描述**。只返回任务需要的字段；结果带足够的上下文（如字段含义），让模型不用猜。大结果做分页与截断信号。
6. **一个工具做一件事**。`create_user_and_send_welcome_email` 这种复合工具，一旦中途失败，模型不知道发生了什么、也无法重试。

## 七、新手常踩的坑

### 坑 1：工具太多，模型选择困难

注册几十个工具，模型频繁选错、或者索性不调用。对策：按场景裁剪工具集；动态注入（当前对话相关的子集）；合并语义重叠的工具；在描述中写清"何时用我 / 何时别用我"。

### 坑 2：schema 过于复杂

深层嵌套（超过两三层）、几十个可选参数、复杂 anyOf 组合——模型填参错误率飙升，Strict 模式的 schema 转换也可能失败。对策：扁平化参数、拆分工具、必填参数最小化，把可选参数给合理默认值。

### 坑 3：把业务逻辑写进工具描述

描述里塞满"如果用户提到退款必须先查风控状态，且金额超过 500 要走人工通道"之类的流程规则。描述用于说明**这个工具是什么、何时用**，不是业务规则容器——模型不一定遵循，且描述 token 每轮都花。业务规则应放进系统指令或代码层的校验逻辑。

### 坑 4：不校验模型输出直接执行

模型生成的参数 JSON 可能：缺字段、类型错、注入意外值（超长字符串、路径穿越、SQL 片段）。**任何参数在执行前必须过 schema 校验**（Pydantic `model_validate` 等），必要时再做白名单/权限检查。模型输出按不可信输入对待，这是安全底线。

### 坑 5：信任 Strict 模式的"结构正确"当作"内容正确"

Strict 只保证字段存在且类型合法，不保证值真实合理——模型可以在合法结构里编造订单号。需要真实的值时，用工具查询回填，而不是让模型凭记忆生成。

### 坑 6：工具结果无脑全量回传

一个查询返回 5000 行 JSON 全部塞进上下文，几轮之后上下文爆炸（详见上下文工程主题）。回传前裁剪、分页、摘要，截断时告知模型总量。

### 坑 7：调用循环没有终止保护

模型陷入"调用 → 失败 → 原样重试"的循环。客户端必须有最大调用次数/预算限制，且失败信息要含修正建议（见第六节原则 4）。

## 八、实践清单

- [ ] 每个工具用 Pydantic（或等价物）定义参数模型，schema 自动生成，执行前强制校验。
- [ ] 工具描述回答三个问题：做什么、何时用、参数怎么填；不含业务流程规则。
- [ ] 报错信息面向模型：说明错误 + 给出可行动的修正建议。
- [ ] 工具集保持精简，按对话场景动态裁剪；语义重叠的工具合并。
- [ ] 结构化数据提取用 Structured Output（strict），副作用操作用 function calling + 确认层。
- [ ] 并行工具调用按 ID 对应回传，每个调用独立校验与容错。
- [ ] 大结果在回传前裁剪/分页，附截断信号与总量信息。
- [ ] 客户端循环有调用次数与预算上限；写操作工具做幂等或确认设计。
- [ ] 对"模型填参 → 校验 → 执行"全链路打日志，便于定位是 schema 问题还是描述问题。

---

## 小结

- Function Calling 的本质：模型输出**调用意图**，你的代码负责**执行与编排**，循环由客户端驱动。
- 参数定义用 Pydantic/JSON Schema，校验在客户端，模型输出永远按不可信输入对待。
- 结构化输出与 function calling 同源异用：要数据用 strict 输出，要动作用工具调用。
- 工具设计四字诀：**少、清、幂、读**——数量少、描述清晰、操作幂等、错误可读。
