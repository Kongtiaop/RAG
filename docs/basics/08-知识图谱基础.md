# 知识图谱基础：从三元组到 GraphRAG

## 1. 什么是知识图谱，解决什么问题

知识图谱（Knowledge Graph, KG）用**图结构**表示知识：节点是**实体**（Entity），边是**关系**（Relation），实体和关系上可以挂**属性**（Property）。

最小单元是**三元组**（Triple）：

```
（主体, 关系, 客体）
（姚明, 出生于, 上海）
（上海, 属于, 中国）
```

属性则是"实体-属性名-属性值"或"关系-属性名-属性值"：

```
（姚明, 身高, 2.26米）
（姚明, 出生于, 上海）的（时间, 1980年）
```

知识图谱解决的核心问题是：**让机器能沿着关系做精确、可复用的推理**。

它和向量检索的本质差异：

| 维度 | 向量检索 | 知识图谱 |
|---|---|---|
| 表示方式 | 文本的语义向量 | 显式的实体与关系 |
| 擅长 | 语义相似、模糊匹配 | 精确查询、多跳推理 |
| "A 的朋友的合作公司有哪些" | 很难答（多跳） | 两条边遍历即得 |
| "文档里大概讲了什么" | 强项 | 弱项 |
| 可解释性 | 低（相似度分数） | 高（可以列出推理路径） |
| 构建与维护成本 | 低（embedding 即用） | 高（需 schema 和抽取） |

一句话：**向量回答"什么和这个意思相近"，图谱回答"谁和谁有什么确切关系"。**

多跳是关键分水岭。"A 公司的 CEO 曾任职的公司的主要竞争对手"这类问题，语义相似度无法直接命中，而图上就是几步遍历。

## 2. 本体（Ontology）与 Schema 设计入门

本体是知识图谱的"骨架"：定义有哪些**实体类型**（Person、Company、Product…）、哪些**关系类型**（WORKS_AT、SUBSIDIARY_OF…）、每种类型有哪些**属性**，以及约束（关系两端允许什么类型）。

最小可用的 schema 设计步骤：

1. **从要回答的问题倒推**。列出目标问题（competency questions），如"XX 产品的负责人是谁"，从问题中提取需要的实体类型和关系类型。schema 是为查询服务的，不是为"完整建模世界"服务的。
2. **实体类型尽量少**，通常 3~10 个；关系类型要有明确语义，避免什么都往 `RELATED_TO` 里塞。
3. **决定属性 vs 节点**："出生日期"做属性即可；"出生城市"如果要继续查城市的关系，就应是节点。

经验原则：**schema 从小做起，够用就好**，随真实查询需求演进。

## 3. 图谱构建路径

### 3.1 人工构建

领域专家用工具（如 Protégé）定义 schema 并录入数据。质量最高、成本最高，适合核心知识少而精的场景（如医疗术语表、企业内部组织架构）。

### 3.2 从文本抽取（主流路径）

用规则/模型/LLM 从非结构化文本中抽取三元组，流水线通常是：

```
文本 → 实体抽取 → 关系抽取 → 属性抽取 → 实体消歧/对齐 → 入图
```

用 LLM 抽取时，prompt 里应提供：schema 定义（允许的实体类型和关系类型清单）、few-shot 示例、输出格式约束（如 JSON）。抽取完成后通常还要：

- **实体消歧（disambiguation）**："苹果"是水果还是 Apple 公司？靠上下文判断。
- **实体对齐（alignment）**："MIT"和"麻省理工学院"合并为同一节点。这是保证图连通性的关键步骤，也是噪声重灾区。

### 3.3 混合路径（最常见）

schema 和核心节点人工定义，长尾实体和关系用 LLM 批量抽取，再人工抽检。

## 4. 存储选型

三大类选型：

| 类型 | 代表 | 特点 |
|---|---|---|
| 属性图（Property Graph） | **Neo4j**、NebulaGraph | 节点/边都可挂属性，查询语言 Cypher（Neo4j），生态最友好，应用开发首选 |
| RDF 三元组库 | Apache Jena、GraphDB | W3C 标准（RDF/SPARQL），语义网生态，标准化程度高，工程上手曲线更陡 |
| 关系型模拟 | PostgreSQL（节点表 + 边表）或 JSONB | 不想引入新组件时可用；深度多跳遍历性能和查询表达力明显受限 |

选型通用原则：

- 应用导向、快速迭代 → 属性图（Neo4j 是事实标准）；
- 需要严格标准、跨组织数据交换 → RDF；
- 图谱很小（几千三元组以内）或只是辅助 → 关系型模拟甚至内存结构即可，别引入新中间件。

## 5. Cypher 查询语言速览

Cypher 用 ASCII 画图：`(节点)`、`[关系]`、`->` 方向。

```cypher
-- 建节点（带属性）
CREATE (:Person {name: '姚明'}),
       (:Team   {name: '上海大鲨鱼'}),
       (:City   {name: '上海'})

-- 建关系
MATCH (p:Person {name: '姚明'}), (t:Team {name: '上海大鲨鱼'})
CREATE (p)-[:PLAYED_FOR {from: 2002}]->(t)

-- 单跳查询：姚明效力过的球队
MATCH (p:Person {name: '姚明'})-[:PLAYED_FOR]->(t:Team)
RETURN t.name

-- 两跳查询：姚明效力过的球队所在的城市
MATCH (p:Person {name: '姚明'})-[:PLAYED_FOR]->(t:Team)-[:LOCATED_IN]->(c:City)
RETURN t.name, c.name

-- 模糊匹配 + 变长路径（1 到 3 跳内的关联）
MATCH (p:Person)-[r*1..3]-(x)
WHERE p.name = '姚明'
RETURN p, r, x LIMIT 20
```

RDF 生态对应的是 SPARQL（`SELECT ?x WHERE { ?x foaf:knows ?y }` 风格），概念相通：都是图模式匹配。

一个很实用的组合是 **text2cypher**：把用户自然语言问题 + schema 交给 LLM 生成 Cypher，执行后把结果交给 LLM 组织答案。schema 越清晰，生成质量越高。

## 6. RAG + KG 的结合方式

知识图谱和向量检索不是二选一，而是互补。常见结合方式：

### 6.1 GraphRAG 的基本思路

微软提出的 GraphRAG 流程（简化版）：

1. **离线**：文档切块 → LLM 抽取实体和关系 → 构图 → 用 LLM 为每个实体/社区生成**摘要**（社区检测如 Leiden 算法分群后逐层摘要）；
2. **在线**：
   - **local 模式**：问题 → 命中相关实体 → 取该实体的邻居子图和摘要 → 生成答案。适合具体问题（"某人的合作者有哪些"）；
   - **global 模式**：问题 → 用各社区摘要做 map-reduce 式汇总 → 生成答案。适合全局性问题（"这批文档的主要主题是什么"）。

### 6.2 实体链接（Entity Linking）

最轻量的结合方式：用户问题先做实体识别，把"姚明"链接到图上的 `Person:姚明` 节点，然后：

- 取该节点邻接的子图、关系描述，连同向量检索的 chunk 一起放进 prompt；
- 图提供**结构化事实**，向量提供**上下文细节**，各司其职。

### 6.3 子图检索

对复杂问题，不检索"文本片段"而是检索"子图"：以问题中的实体为种子，按关系类型/边数扩展出 k 跳邻域，将子图序列化（或用 LLM 摘要）后放入 prompt。

### 6.4 路由

按问题类型分流：多跳/关系类问题走图谱链路，模糊语义类走向量链路，都走再做融合。

## 7. 什么时候需要 KG，什么时候不需要

**可能需要 KG 的信号**：

- 大量查询是**多跳关系推理**（A 的上司的汇报线、B 的供应商的竞争对手）；
- 需要**精确的事实**而非"语义上相关的内容"（合规、审计、风控）；
- 需要可解释的推理路径；
- 同一实体在多个来源出现，需要统一视图（实体对齐的价值）；
- 数据本身就有天然网络结构（供应链、社交、引用网络、系统依赖）。

**大概率不需要 KG 的信号**：

- 需求主要是"文档问答"和语义搜索，向量 RAG 已经够用；
- 知识变化极快、schema 无法稳定下来；
- 没有人力和预算做抽取质量控制与持续维护；
- 说不出"有了图之后要回答哪 10 个问题"。

**别为了图而图。** 判断标准很简单：先写下目标查询集，如果这些查询用"向量检索 + LLM"已经能答对，就没有引入 KG 的理由。图是有显著构建和维护成本的资产，需要明确的回报。

## 8. 新手常踩的坑

1. **schema 过度设计**：一上来定义几十个实体类型、上百种关系，结果大部分永远没被查询过。对策：从目标问题倒推，从 3~5 个类型起步。
2. **抽取噪声被低估**：LLM 抽取会产出幻觉三元组、错误对齐的实体，直接入图会污染所有下游查询。对策：schema 约束 + 置信度过滤 + 抽检，把入图当作有质量门槛的写入。
3. **维护成本被低估**：文档更新后图谱怎么同步？实体合并后旧引用怎么办？图谱是持续运营的资产，不是一次性构建的产物。上项目前先回答"增量更新策略是什么"。
4. **"RELATED_TO 万金油"**：所有不确定的关系都标成 RELATED_TO，图很快退化成一团无意义连线。关系类型必须有明确语义，宁缺毋滥。
5. **实体消歧缺失**：同一实体的多种写法（缩写、别名、错拼）变成多个孤立节点，图被割裂，多跳推理直接失效。
6. **用 KG 替代向量而不是互补**：图谱不擅长"模糊语义匹配"，全文细节还是要靠向量/全文检索。成熟方案几乎都是混合使用。
7. **text2cypher 不给 schema 约束**：不给 LLM 明确的类型和关系清单，生成的查询会发明不存在的属性名和关系名。始终把 schema 注入 prompt，并对生成查询做校验。
8. **一跳都跑不动的查询当多跳问题修**：先确认检索/查询本身的正确性（比如实体压根没链接上），再去怀疑推理深度。

## 9. 小结

- KG = 实体 + 关系 + 属性，三元组是最小单元；本质价值是**精确的多跳关系推理与可解释性**。
- 与向量检索是互补关系：向量管语义相近，图谱管关系确切。
- schema 从目标查询倒推，小步演进；抽取链路必须有消歧、对齐和质量过滤。
- 存储首选属性图（Neo4j/Cypher）起步；RDF 适合标准化交换场景；小图谱用关系型模拟即可。
- 与 RAG 的结合由轻到重：实体链接 → 子图检索 → GraphRAG 社区摘要。
- 引入 KG 前先写下目标查询集，答不出"为什么要图"就先别建图。
