# RAG 基础：检索增强生成入门

## 1. RAG 是什么，解决什么问题

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思路很朴素：**在让大模型回答之前，先把相关资料检索出来，塞进 prompt 里**，让模型"开卷考试"而不是"闭卷硬答"。

它主要解决 LLM 直接回答时的三类问题：

| 问题 | 表现 | RAG 的解法 |
|---|---|---|
| 幻觉 | 模型一本正经地编造事实 | 答案基于检索到的真实文档，可附引用来源 |
| 知识时效 | 训练截止后的事一无所知 | 新文档入库即可被检索，无需重新训练 |
| 私有知识 | 公司内部文档、个人笔记模型没见过 | 把私有语料做成可检索的知识库 |

一个常见的误解是"有了长上下文窗口就不需要 RAG 了"。实际上：

- 全量文档塞 prompt 成本高、延迟大；
- 上下文越长，模型对中间内容的注意力越弱（"lost in the middle"现象）；
- 无法对"哪段资料支撑了答案"做精细控制和溯源；
- 文档库超过窗口容量时依然无解。

RAG 的本质是**用"检索"缩小了模型需要阅读的范围**，这在工程上永远有价值。

## 2. 整体架构：离线链路 + 在线链路

RAG 系统天然分为两条链路，理解这个划分是入门第一步。

### 2.1 离线摄取链路（Ingestion Pipeline）

一次性或周期性执行，把原始文档变成可检索的形态：

```
原始文档 → 解析 → 切块 → Embedding → 入库
```

1. **解析（Parsing）**：把 PDF/Word/HTML/Markdown 等转成纯文本或结构化文本。PDF 是重灾区：双栏排版、表格、扫描件都会让解析质量崩塌，解析质量差是"检索不准"最常见的根因之一。
2. **切块（Chunking）**：把长文档切成适合检索的小段（详见第 3 节）。
3. **Embedding**：用 embedding 模型把每个 chunk 编码成向量。向量的语义相近度 ≈ 文本含义相近度。
4. **入库**：向量写入向量数据库（Milvus、pgvector、Qdrant 等），通常同时存原文和元数据（来源、标题、章节、时间等）。

关键实践：**给每个 chunk 保留元数据**。来源文件、章节路径、更新时间，在后续过滤和引用溯源时必不可少。

### 2.2 在线检索链路（Query Pipeline）

用户每次提问时执行：

```
用户问题 → 查询改写 → 召回 → 重排 → 生成
```

1. **查询改写（Query Rewriting）**：用户口语化的问题往往不适合直接拿去检索。常见手段：把多轮对话中的代词补全（指代消解）、拆解复杂问题、让 LLM 生成更适合检索的查询形式。
2. **召回（Recall）**：用向量相似度（也可混合 BM25）从库里取回 top_k 个候选 chunk。此阶段追求"别漏"，宁可多取。
3. **重排（Rerank）**：用更精细的模型对候选重新打分排序，取前几个进入 prompt。此阶段追求"排对"。
4. **生成（Generation）**：把问题 + 检索到的 chunk + 系统指令拼成 prompt，交给 LLM 生成答案，最好附引用。

## 3. 切块策略与权衡

切块是离线链路里最容易被低估的环节。核心矛盾：**chunk 太小则上下文碎、语义不完整；太大则检索噪声多、相似度被稀释**。

### 常见策略

- **固定长度切块**：按固定 token 数切，加一定 overlap（重叠）。实现最简单，效果也最"莽"——它完全不管语义边界，一句话可能被拦腰切断。
- **递归切块（Recursive Splitting）**：按分隔符层级递归切（先按段落 → 段落太大按句子 → 还大就按固定长度）。LangChain 的 `RecursiveCharacterTextSplitter` 是典型实现。这是**大多数场景的默认起点**。
- **按结构切块**：Markdown 按标题层级、代码按函数/类、HTML 按 DOM 结构切。对结构化文档效果最好，因为它尊重了文档自身的语义单元。

### 经验原则

- 常用 chunk 大小在几百 token 量级（如 256~1024），带 10%~20% overlap；
- 没有万能参数，**chunk 大小本质上取决于"答案通常需要多大范围的上下文才完整"**；
- 切块粒度可以和返回粒度解耦：检索时用小块（精准命中），返回时把小块所属的大块/父块一起给模型（small-to-big / parent-document 模式）；
- 表格、代码这类结构化内容应整体保留，不要按字符数硬切。

## 4. Embedding 模型选择要点

选 embedding 模型时关注以下几点：

1. **语言匹配**：中文场景优先选在中文语料上训练过的模型，不要默认英文模型够用。
2. **维度与性能**：维度越高通常表达能力越强，但存储和计算成本也越高。可用主模型 + 降维（部分模型支持 Matryoshka 截断）做权衡。
3. **上下文长度**：embedding 模型的最大输入长度有限，超长文本会被截断——这直接影响切块大小的上限。
4. **榜单参考**：MTEB / C-MTEB 榜单可以参考，但更可靠的是**拿自己的真实语料和查询做小规模评测**。
5. **一致性**：索引时和查询时必须用同一个模型（含同一版本），换模型就要全量重建索引。

通用原则：embedding 模型的替换成本很高（重建全量索引），初期选型宁可花点时间做对比实验。

## 5. 混合检索：向量 + BM25 + RRF

纯向量检索的短板：

- **专有名词、产品型号、人名、编号**这类精确匹配需求，语义相似度反而不如关键词；
- 稀有术语在 embedding 空间里可能区分度很低。

BM25（经典关键词检索算法）正好互补：它精确匹配词项，但不懂同义改写（"电脑"搜不到"计算机"）。

**混合检索 = 两路（或多路）召回，再融合结果。**

最常用的融合方法是 **RRF（Reciprocal Rank Fusion）**：对每一路返回的排名列表，给每个文档按 `1 / (k + rank)` 累加得分（k 通常取 60），按累加分重排。RRF 只用排名不用分数，天然避开了"向量余弦分数和 BM25 分数量纲不同"的问题。

```
RRF 得分 = Σ over 所有检索通道: 1 / (k + 该通道中此文档的排名)
```

## 6. 重排（Reranking）

召回阶段的向量检索用的是**双塔/bi-encoder**：query 和文档分别独立编码，速度快但精度有限——两者从未"见过面"。

重排阶段用 **cross-encoder**：把 (query, 候选文档) 拼在一起送进模型打分，能捕捉两者之间的细粒度交互，精度显著更高，但每对都要过一次模型，速度慢。

所以标准组合拳是：

```
向量+BM25 召回 top 50~100  →  cross-encoder 重排  →  取 top 3~10 进 prompt
```

召回用便宜的模型求全，重排用贵的模型求精。没有 cross-encoder 时，RRF 融合本身就是一种轻量级重排（纯排名融合，不引入模型）。

## 7. 评测基本指标

**不评测就调优 = 盲人开炮。** RAG 最常见的失败模式是凭感觉改 chunk 大小、换模型，永远不知道变好还是变坏。

最小可行的评测集：几十条 (问题, 标准答案/相关文档) 对，人工或半自动构建即可起步。

核心指标分两层：

- **检索层**：
  - **召回率（Recall@k）**：标准答案所在 chunk 有多大比例被召回。检索没召回对，后面全白搭，这是第一优先级指标。
  - Precision、MRR、NDCG 等可后续补充。
- **生成层**：
  - **忠实度（Faithfulness）**：答案是否严格基于检索到的内容（衡量幻觉程度）。
  - **答案相关性**：答案是否真的回应了问题。

现成工具：RAGAS、TruLens 等框架可以用 LLM 当裁判自动打分，适合快速起步；关键场景仍需人工抽检校准。

## 8. 进阶方向一览

- **HyDE**：让 LLM 先根据问题"幻想"一段假设性答案，再用它去检索——假设答案和真文档在向量空间里更接近，能缓解 query 和文档的语义鸿沟。
- **多路召回**：向量 + BM25 + 按元数据过滤 + 按标题/摘要召回等多通道并行，再融合。
- **GraphRAG**：抽取实体和关系构建知识图谱，检索时利用图结构做多跳关联（详见知识图谱篇）。
- **渐进式披露**：不一次塞全量内容，而是先给摘要/目录，模型（或流程）判断后再展开细节。适合超大文档和多轮深挖场景。
- **查询路由**：按问题类型分流——闲聊直接答、简单事实走轻量检索、复杂分析走多轮检索。

## 9. 最小示例（伪代码）

用伪代码把两条链路串起来，帮助建立整体感：

```python
# ---------- 离线摄取 ----------
def ingest(docs):
    for doc in docs:
        text = parse(doc)                      # 解析：转纯文本
        chunks = split(text, size=512, overlap=64)  # 递归切块
        vectors = embed(chunks)                # 批量向量化
        store.insert(                          # 原文 + 向量 + 元数据一起入库
            chunks, vectors,
            meta=[{"source": doc.path, "time": doc.mtime} for _ in chunks]
        )

# ---------- 在线检索 ----------
def answer(question, history):
    query = rewrite(question, history)         # 指代消解、问题改写
    c1 = vector_store.search(query, top_k=50)  # 向量召回
    c2 = bm25.search(query, top_k=50)          # 关键词召回
    fused = rrf_merge([c1, c2], k=60)          # RRF 融合
    top = rerank(query, fused[:50], keep=5)    # cross-encoder 重排
    prompt = build_prompt(query, top)          # 问题 + 上下文 + 指令
    return llm.generate(prompt)                # 生成（可要求附引用）
```

不必一次实现全部环节。最小可行版本是：**固定切块 + 纯向量召回 + 直接生成**，跑通后再按瓶颈逐个引入混合检索和重排。

## 10. 新手常踩的坑

1. **切块切断语义**：固定长度硬切把表格、代码、一句话切成两半。对策：优先用结构感知切块，表格代码整体保留。
2. **top_k 盲目调大**：以为塞得越多答得越好。实际引入大量无关内容，稀释注意力、增加幻觉概率、抬高成本。正确做法是：先重排，再按重排分数设阈值取优。
3. **检索质量不评测就上线**：换了个 embedding 模型感觉"应该更好"就全量切了。没有评测集，一切调优都是玄学。
4. **解析环节被跳过**：PDF 解析出来的文本顺序错乱、表格变乱码，后面切块和检索再精细也没用。解析质量要单独验证。
5. **只测简单问题**：评测集全是"XX 是什么"，上线后用户问多跳推理和聚合问题全崩。评测集要覆盖真实查询分布，包括难例。
6. **换 embedding 模型不重建索引**：新旧模型的向量空间不可混用，混用等于检索随机。换模型 = 全量重建。
7. **忽略查询和文档的措辞差异**：文档是正式书面语，用户查询是口语。查询改写、同义词扩展、混合检索都是为此服务的。
8. **引用溯源缺失**：不标注答案来源，用户无法验证，信任度低，也难以排查错误。让模型在答案中附 chunk 引用是低成本高收益的实践。

## 11. 小结

- RAG = 离线摄取（解析→切块→embedding→入库）+ 在线检索（改写→召回→重排→生成）两条链路。
- 切块尊重语义结构，chunk 粒度可与返回粒度解耦。
- 混合检索（向量 + BM25 + RRF）解决精确匹配短板；cross-encoder 重排解决排序精度。
- 建立评测集是一切调优的前提，检索层先看召回率，生成层先看忠实度。
- 从简单链路起步，遇到真实瓶颈再引入 HyDE、GraphRAG 等进阶手段。
