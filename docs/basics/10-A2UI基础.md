# A2UI 基础：让 Agent 安全地"生成 UI"而不是"生成代码"

> 类型: 通用基础知识（与项目无关）；基于 2026-10 公开资料整理

## 1. 是什么与解决什么问题

A2UI（Agent-to-User Interface）是 **Google 于 2025 年底开源**的协议与库集合（Apache 2.0 许可，CopilotKit 与开源社区参与贡献），解决一个具体问题：

> **AI Agent 如何安全地跨越信任边界，把丰富、可交互的 UI 发给用户？**

当前 Agent 展示界面的几条路各有硬伤：

- **纯文本 / Markdown**：信息密度低，无法承载交互（表单、按钮、图表都做不到）。
- **让 Agent 写前端代码并执行**（HTML/JS 注入或 iframe 沙盒）：表达力强，但 Agent 生成的代码不可信——XSS、UI 注入攻击、样式与宿主割裂、iframe 又重又难看。
- **直接操作 DOM**：只在本机可行，Agent 远程运行时完全走不通。

A2UI 的思路是把信任边界**从"代码"移回"数据"**：Agent 只发送**声明式 JSON 蓝图**，描述界面里有哪些组件、如何组织、绑定什么数据；客户端用**自己的原生组件库**（Flutter / Angular / React / Lit 等）渲染。官方的概括是：

> **像数据一样安全，像代码一样有表现力。**

这和 MCP 的工具模型一脉相承：Agent 只产出结构化 schema，执行权在宿主手里。

**现状（截至 2026-10）**：项目处于早期公开预览阶段，活跃开发中。当前生产版本为 v0.9.1（v0.9 于 2026 年 4 月发布），**v1.0 规范处于 RC 阶段**，v0.8 已视为 legacy。官方明确"expect changes"——接口仍可能变动。

## 2. 核心概念

### 2.1 四个关键词

- **Surface（界面）**：一块独立的可渲染 UI 区域。Agent 通过 `createSurface` 声明要创建一个界面区域，可以同时维护多个 surface。
- **组件目录（Catalog）**：宿主预先声明"我支持哪些组件"（Trusted Catalog）。Agent **只能引用目录里的组件**，这是安全模型的核心——白名单机制从协议层杜绝了 UI 注入。目录可自定义扩展（v0.9 起支持 custom catalogs），官方提供一组 "Basic" 通用组件。
- **邻接表模型（Adjacency List）**：界面不是一棵嵌套的 JSON 树，而是**组件的扁平列表**，每个组件有 ID，通过引用其他组件 ID 表示父子关系。这对 LLM 极其友好——模型可以一段一段地追加组件，不必一次性生成完美嵌套的 JSON。
- **数据绑定**：组件属性可绑定到数据模型上，数据更新时 UI 自动刷新，支持客户端与服务端之间的数据同步（如用户与 Agent 协作编辑表单）。

### 2.2 消息格式示意

A2UI 消息是流式的 JSON 指令序列。**以下为极简示意**（字段名以官方规范为准，v0.8→v0.9 之间有调整）：

```jsonc
// 1. 创建一个 surface
{ "createSurface": { "surfaceId": "s1", "catalog": "basic" } }

// 2. 追加组件（扁平列表 + ID 引用）
{ "updateComponents": { "surfaceId": "s1", "components": [
  { "id": "root", "type": "Column", "children": ["title", "form"] },
  { "id": "title", "type": "Text", "text": "预订确认" },
  { "id": "form",  "type": "TextField", "label": "入住日期", "value": "${booking.date}" }
]}}
```

关键点：**没有 HTML、没有 JS、没有样式代码**——只有对目录组件的引用和属性赋值。

### 2.3 典型交互流

```
用户发消息 → Agent 生成 A2UI 消息流（结构 + 数据）
→ 消息流式到达客户端 → 客户端用原生组件渐进渲染
→ 用户在 UI 上操作（点按钮/填表单）→ 动作回传 Agent
→ Agent 返回更新后的 A2UI 消息 → 界面增量刷新
```

因为是扁平组件列表 + ID 增量更新，UI 可以**边生成边渲染**——用户看到界面在 Agent 推理过程中逐步长出来，而不是等一个完整响应。

### 2.4 安全与信任：协议层的三道约束

1. **声明式数据，非可执行代码**：消息里没有脚本执行语义，XSS 类攻击从根上不成立。
2. **目录白名单**：Agent 只能使用宿主预批准的组件；目录之外的引用应被渲染器拒绝。宿主对每个组件的**渲染与行为**保留完全控制权（样式、事件处理、权限）。
3. **客户端函数受控调用**（v0.9+）：Agent 可以引用宿主注册的校验函数或回调，但只能"点名调用"，不能自定义逻辑。

需要注意：安全边界在**渲染端**。如果宿主把某个组件映射到了危险的实现（例如一个允许注入富文本的组件），协议管不住——目录设计本身仍需宿主自律。

### 2.5 三种 UI 生成方案的信任模型对比

| 方案 | Agent 发送什么 | 信任假设 | 主要问题 |
|---|---|---|---|
| 代码生成（HTML/JS） | 可执行代码 | 信任 Agent 的代码 | XSS / UI 注入；必须跑在沙盒里 |
| iframe 沙盒（MCP Apps 路线） | 完整网页，隔离执行 | 不信任代码，靠隔离兜底 | 重、视觉与宿主割裂、通信复杂 |
| **A2UI 声明式蓝图** | 组件引用 + 数据（纯数据） | 不需要信任 Agent——数据无害 | 表达力受目录组件上限约束 |

这张表解释了 A2UI 的设计哲学：**与其隔离危险代码，不如一开始就不让代码出现**。代价是宿主必须预先准备好足够丰富的组件目录，Agent 的"创造力"被限制在目录的组合空间内。

### 2.6 宿主侧：声明目录与渲染

宿主应用启动时向渲染器注册两样东西：

```jsonc
// 宿主声明自己的组件目录（简化示意）
{ "catalog": {
    "components": [
      { "name": "Text",      "props": { "text": "string" } },
      { "name": "TextField", "props": { "label": "string", "value": "string" } },
      { "name": "Button",    "props": { "label": "string", "action": "Action" } }
    ]
}}
```

渲染器收到蓝图后逐条处理：`createSurface` 开一块画布；`updateComponents` 里的每个组件 ID 在目录中查找实现，映射为框架原生组件（React 组件 / Flutter Widget / Angular 组件）后挂载；`childList` 引用组装出层级。用户点击 Button 时，渲染器把动作事件（含组件 ID 与参数）回传给 Agent——**交互回路依然走协议**，而不是组件内部自行处理业务逻辑。

这个设计的直接推论：**样式与行为 100% 由宿主掌握**。同一个蓝图，在深色 App 里渲染成深色卡片，在合规敏感的金融 App 里可以把 Button 渲染成需要二次确认的样式——Agent 对此毫不知情，也无从干预。

## 3. 与固定前端 + AG-UI 事件流的差异

A2UI 和 AG-UI 解决的不是同一层问题，容易混淆：

| 维度 | 固定前端 + AG-UI | A2UI 动态生成 UI |
|---|---|---|
| UI 由谁定义 | 前端开发者预先写死组件，Agent 事件驱动这些组件 | Agent 按对话上下文**临时决定**界面结构 |
| 消息内容 | 事件（状态变化、token 流、工具调用） | UI 蓝图（组件描述 + 数据） |
| 界面变化频率 | 改 UI 要发前端版本 | Agent 换一种输出，界面即变 |
| 灵活性 vs 可控性 | 可控性高、灵活性低 | 灵活性高，可控性靠目录白名单兜底 |
| 典型问题 | 每种交互都要提前设计 | 生成质量依赖模型，可能生成奇怪布局 |

重要事实：**两者是互补的，且官方打通了**。A2UI 不绑定传输层，它可以跑在 A2A、AG-UI、MCP、WebSocket、REST 之上——Agent 在 AG-UI 事件流里夹带 A2UI 蓝图，是 CopilotKit 官方支持的组合（`npx copilotkit@latest create my-app --framework a2ui` 可直接脚手架 React + A2UI 应用）。可以这样记：

- AG-UI 管"**对话如何流**"（事件通道）
- A2UI 管"**界面长什么样**"（UI 描述格式）

与 MCP Apps 的对比值得一提：MCP Apps 采用 iframe 沙盒 HTML 的反向信任模型（跑不受信代码但隔离起来），A2UI 则根本不允许代码。两种模型各有取舍——iframe 沙盒更通用但视觉割裂、更重；A2UI 更轻更原生，但表达力被目录约束。

## 4. 生态与采用情况

- **渲染器**：官方维护 Flutter、Lit、Angular、React（共享 web-core 库）渲染器，另有 Markdown 渲染器；仓库中还有 Kotlin / Swift 相关代码。同一份蓝图理论上可多端渲染。
- **Agent SDK**：Python Agent SDK（`pip install a2ui-agent-sdk`）封装了 schema 管理、目录加载和**流式 JSON 修复**（LLM 输出不完整 JSON 时的增量补救）。
- **采用方**：Flutter GenUI SDK（远程 Agent 场景底层用 A2UI）、Gemini Enterprise 与 Google Opal 等内部产品、Oracle Agent Spec 栈、AG2（AutoGen 团队）的 A2UIAgent、Vercel json-renderer（实验性）。
- **配套工具**：A2UI Composer（可视化编辑器生成 JSON，可直接贴进 Agent 提示词）、A2UI Theater（多渲染器流式演示）。
- **规范栈中的位置**：与 llms.txt、AGENTS.md、MCP、A2A 并列，覆盖"Agent → UI 交接"这一环。

需要客观指出：A2UI 的跨厂商背书目前**窄于 MCP**——采用方集中在 Google 自有产品和 AG-UI/CopilotKit 生态圈，微软、Anthropic 等尚未公开表态。把它当作"有 Google 撑腰的新兴标准"来评估，而不是"已是行业既定事实"。

## 5. 适用场景

- **表单/审批/配置类交互**：Agent 根据任务动态产出收集表单，比让用户打字描述高效得多。
- **数据展示**：图表、卡片、列表——文本塞不下的结构化信息。
- **跨端一致性要求高**：一份蓝图，Web / 移动 / 桌面各自原生渲染。
- **Agent 在不可信环境运行**：第三方 Agent 向你的应用投递 UI 时，目录白名单是天然防线。

不适合：界面结构基本固定的传统业务系统（预先设计的 UI 更可控）；需要高度定制视觉/交互的场景（受目录组件能力上限约束）。

## 6. 与 Agent 配合的实操要点

Agent 侧生成 A2UI 的常见做法是把协议说明 + 目录定义放进 system prompt，让模型以工具调用或结构化输出形式产出蓝图。官方 Python SDK 已经把这层封装好（schema 注入、目录加载、流式修复）。两个实操建议：

- **提示词里附上组件目录清单和若干蓝图示例**，生成质量会显著提升；A2UI Composer 生成的 JSON 可直接作为 few-shot 素材。
- **优先流式生成**：先 `createSurface`，再按布局从外到内逐块 `updateComponents`，用户端即可渐进渲染；等全部生成完再一次性发送会浪费协议最大的体验优势。

## 7. 常见坑

1. **版本陷阱最突出**：v0.8 / v0.9 / v1.0-RC 并存于网上资料中，字段名有过变更（如 v0.9 的组件目录从 "Standard" 改名 "Basic"，权限字段 `callableFrom` 更名为 `allowedCallers`）。**写代码前务必确认你看的文档对应哪个版本**，生产环境建议锁定 v0.9.x。
2. **规范仍在变**：项目自称"early stage public preview，expect changes"，不要把 A2UI 当成和 MCP 一样稳定的依赖来做长期架构承诺。
3. **别期望"任意 UI"**：Agent 只能用目录里的组件，目录贫乏会导致生成界面单调；反过来目录过于开放（含富文本类组件）会削弱安全模型。目录设计是宿主侧最重要的决策。
4. **LLM 生成 JSON 的可靠性**：模型可能输出不完整或非法蓝图，务必使用带增量修复的官方 SDK 或在渲染端做严格校验，不要直接 `JSON.parse` 后渲染。
5. **混淆 A2UI 与 AG-UI**：两者名字相似但分层不同，A2UI 可以承载在 AG-UI 上传输；选型时先问自己要解决的是"事件流标准化"还是"动态 UI 生成"。
