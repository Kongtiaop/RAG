# 分层记忆是怎么长出来的：不是设计出来的，是被需求逼出来的



## 碰到的问题：Agent 一转头就忘了

最早的版本里，我们的客服 Agent 是"金鱼"：每次请求独立处理，上一轮刚澄清完"您说的是哪只基金"，下一轮用户回答了，Agent 却不记得自己在问什么。

于是我们接入了第一块记忆：**短期记忆**。Redis 里存一个 JSON，key 按"客户+会话"隔离，TTL 半小时，里面放澄清上下文（`original_query`、`clarification`、`missing_parameter`）、待执行的计划、转人工状态、澄清计数。这一步很顺——快、随会话生命周期清理、丢了也不心疼，`redis=None` 时读写降级为空操作，主链路不受影响。

短期记忆接完，新的需求立刻冒出来：**"这个客户已知什么"跨不过会话。** 用户上周说过自己偏好稳健型产品，这周来问推荐，Agent 还是两眼一抹黑。这就需要长期记忆了。

再往后需求继续长：客服 Agent 观察到的客户偏好，投顾 Agent 能不能复用？反过来，员工做分析时产生的临时结论，会不会污染客户档案？最后还有一层：一个客户的零散观察，能不能聚合成组织级的洞察？

回头看，我们的记忆分层（L0~L3）就是这样**一步步被需求逼出来的**，不是某天坐下来"设计"出来的。

## 为什么分层是合理的：不同需求的生命周期根本不同

**每一层记忆的更新节奏和生命周期完全不同，硬塞进一个存储必然互相伤害。**

方法论上还有一个选型判断链，帮我们把"要建什么"收得很紧：

- 信息会被用户更新吗？——会，所以 Gen1 式的"只插不改"向量记忆不够；
- 存在"新信息覆盖旧信息"吗？——存在，所以至少要到 Gen2 的结构化记忆；
- 有跨实体关联查询需求吗？——目前没有明确需求，Gen3 记忆图谱就不建；
- 日活对话量撑得起图谱抽取成本吗？——撑不起，更不建。

最终落地边界：L0/L1 已实现，L2 场景档案与 Gen3 记忆图谱列为规划项，等真实需求出现再评估。

| 层级 | 内容 | 更新节奏 | 类比 |
|---|---|---|---|
| L0 原始流水 | 对话原文、审计记录 | 实时落盘，永不修改 | 录音笔 |
| L1 记忆卡片 | 结构化事实（偏好、事件） | 异步提炼 | 会议纪要便签 |
| L2 场景档案 | 同一情境下的卡片打包 | 按情境组织 | 项目文件夹 |
| L3 人格摘要 | 稳定的用户画像 | 周/月级 | 用户简历 |

有个方法论判断对我们影响很大：从 RAG 记忆（Gen1）到结构化记忆（Gen2）再到记忆图谱（Gen3），**每次换代都在把"生成层的负担"前移到"记忆层"**——Gen1 把矛盾留给模型现场判断，Gen2 在写入时就消解矛盾，Gen3 在写入时就建好关联。换句话说，记忆系统的价值不在于"存得多"，而在于**写入时就替模型把脏活干了**。

这也让我们认清了一个概念：**RAG 向量库是"记忆的素材库"，不是记忆本身。** 余弦相似度不认识时间语义，没有 update 语义——用户改了风险偏好，旧记录只是"多了一条"，模型检索时会同时看到新旧两条，矛盾甩给它现场裁决。这不是记忆，这是素材堆。

落地时我们没有教条地按 L0~L3 建四套存储，而是收敛成**两层物理存储 + 一个共享语义层**：

- **短期**：Redis，存"这一轮聊到哪"——澄清上下文、待执行计划、转人工门控；
- **长期**：PostgreSQL 的 `customer_memory` 表 + `customer_memory_event` 事件审计表，存"这个客户已知什么"——只允许白名单低风险类型（客户确认的参数、服务偏好、非敏感会话事实）；
- **共享语义层**：在长期记忆之上叠 scope（private/shared/organization）和每类 Agent 的读写权限，让一个 Agent 的观察能被其他 Agent **安全地**复用。

L0 对应现有业务表（会话/消息/审计），不由模型改写；L1 就是记忆卡片表；L3 稳定摘要后来靠异步提炼闭环实现；L2 场景档案到今天仍是规划项——**需求没到，就不建**。

这套收敛有个判断标准可以明确说出来：**Redis 管"这一轮聊到哪"，PostgreSQL 管"这个客户已知什么"。** 前者是快速恢复上下文的缓存，允许丢失，会话结束或转人工就清理；后者是业务事实库，用 PG 事务保证一致。两者的内容边界同样清楚：短期记忆存的是澄清上下文和待执行计划这类"过程状态"；长期记忆只存三类白名单内容——客户明确确认的参数、服务偏好、非敏感会话事实。写入长期记忆走 upsert 语义，且同一事务内追加一条事件审计记录，每条记忆的来龙去脉可追溯。

读侧同样收敛在白名单里：`load_long_term()` 只取少量低风险键组装进上下文，而不是把客户的全部记忆一股脑塞给模型。这一点在金融场景不是洁癖——记忆读得越多，"旧快照被模型当成事实"的面就越大，白名单是第一道闸。

在方法论上，L0~L3 的分层还附带一个推理顺序的约定：**先看 L3 定基调，再查 L0/L1 做决策。** 稳定画像（"这是个稳健型投资者"）放在最前面定上下文的调子，原子事实（"他上周确认过 5 万的申购参数"）放在后面支撑本轮决策。顺序反了，一条孤立的旧事实就可能带偏整轮对话。

## 共享与隔离：这块边界我们踩了三次坑

分层本身不难，难的是"谁能读谁的、谁能写谁的"。这是我们踩坑最密集的区域。

### 坑一：员工分析写进了客户记忆

迭代早期，员工向（Supervisor 里的数据分析）的处理结果，沿着客户向客服的逻辑一路执行——落客服知识库断言、转人工、建工单，甚至**写客户记忆**。内部员工的分析探针被当成了客户会话侧写，客户档案被内部角色上下文污染。

修复分了三步：员工分析未命中时返回明确的 `unsupported`，不再掉进客服兜底；客户记忆严格 gate 到客户本人链路；员工/投顾按 subject-scope 授权**只读**被服务客户的共享档案，只读不写。

这次教训确定了我们的记忆规则：**写入必须带归因（`actor_user_id`）且仅限客户亲口自述的低风险偏好；员工的任何分析产物绝不落客户记忆。** "写方是谁、读方是谁、可读哪个 subject"必须在做接入的那一天就收紧——事后补，污染已经发生了。

### 坑二：唯一索引漏了 scope，private 和 shared 互相顶掉

共享记忆引入了 scope 字段之后，我们的文档一度把唯一约束写成 `(customer_id, key)`——字面意思是"一个客户一个 key 只有一条"。但真实的索引是 `(customer_id, key, scope)`：**唯一性是三维的（客户，key，作用域）**。

为什么差一列是大事？因为"共享不覆盖私有"正是这套抽象的核心：客服 Agent 有一条 private 的风险偏好记录，投顾侧代客户写入了一条 shared 的——同一个 key，两个作用域，**应该各存一份**。如果唯一键漏了 scope，这两条记录会因唯一冲突互相顶掉，写入方默默丢失数据，还没有任何报错。

### 坑三：记忆注入入口被并发打崩

`/profile/me` 是一个"读取合成"接口：记忆事实 + 风险测评 + 持仓，一并列出。50 并发压测时 500 报错，低并发却完全正常。

排查发现根因不在记忆本身：接口依赖的"派生估值"在客户当日无快照时触发重估，对持仓行逐条 `SELECT … FOR UPDATE` 再更新——同一客户多并发首读，全部冲进这个分支互相等锁，Postgres 死锁。

修复用 per-user advisory lock 把同一客户的重估串行化；顺带还给多 worker 启动时的 schema/seed 加了全局 advisory lock——四个 worker 并发做 DDL 也可能死锁，这是同一次排查送的第二条经验。

但真正记进我们设计笔记本的是那个**隐藏耦合**：记忆注入读的是"客户总览"，而它依赖的派生重算把一个"读接口"悄悄变成了"会写行的重估"。要么给读口喂已物化的无锁数据，要么用锁串行化——**一个读接口的下游不该有写路径，这是需要显式审查的耦合点。**

## 让记忆"活"起来：L3 摘要的异步闭环

分层的最后一块拼图是 L3 稳定摘要。需求是：每次对话结束，把本轮的诉求、结果、待办提炼成一段稳定的会话摘要，跨 Agent 共享，供下次服务时注入。

我们没有在主链路里同步做这件事——LLM 摘要又慢又有外部依赖，同步会拖垮对话响应。整条链路是异步的：

```
对话执行完成 → 每轮写 outbox（memory.summary_extract，与业务同事务 commit）
→ outbox_worker 搬运到 Redis :memory stream
→ memory_worker 消费 → 受控 Qwen 生成结构化 JSON 摘要
→ 读取已有 summary 做合并更新（递进提炼）→ 落 shared 记忆
```

三条可靠性底线：入队走 outbox，"对话成功 ⇒ 摘要事件必落库"；摘要重复投递安全（upsert 语义）；**任何一环失败都只降级，绝不阻塞转人工**——摘要锦上添花，转人工雪中送炭，两者的优先级不能搞反。

还有一条贯穿性的设计原则：**业务事实表永远高于记忆。** 风险等级、资产、持仓，永远从业务表实时读取，记忆只做上下文补充。模型拿"旧快照当事实"是金融场景的通病，我们的防线是职责分离——记忆负责"客户说过什么"，业务表负责"客户是什么"。遗忘也是同理：遗忘是检索降权，不是物理删除；日常记忆自然沉底，风控、投诉等关键场景强制唤醒。

## 教训

1. **"模块写完"不等于"链路用起来了"。** 验收记忆系统的标准是 grep 调用方，不是看 service 层存不存在；每个"已落地"的主张都要能指到一个具体的调用点，否则迟早要么高估要么低估自己。
2. **共享边界必须在接入第一天收紧。** 谁写、谁读、写哪个 subject，晚定义一天，污染和越权就多发生一天；而且加了 scope 维度，唯一约束要同步扩维，少一列就是静默丢数据。
3. **给读接口做下游依赖审计。** 记忆注入看起来是纯读，但挂在前面的派生重算会让它在并发下死锁——读路径上藏着写路径，是最隐蔽的炸弹。
4. **记忆是上下文，不是事实源。** 业务表永远高于记忆，宁可每次多查一次库，也不要让模型拿着过期快照当真相。
