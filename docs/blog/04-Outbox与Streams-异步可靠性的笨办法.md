# Outbox 与 Streams：异步可靠性的笨办法



## 碰到的问题：每个功能都正确，系统却一起出错

我们是在吃了亏之后才开始认真对待异步可靠性的。

那一天我们修了 21 个缺陷，其中五个是同一种模式：**两个各自验证通过的功能，在共享状态或时序的接缝上相遇后失效**。问"多久到账"被当成要下单；重试成功后陈旧的 error 残留导致误转人工；第 1 轮的澄清错误污染了第 2 轮。

这五次失效教会我们两件事。第一，**功能正确 ≠ 系统正确**——组合失效是静默的：不报错、状态 `completed`、指标全绿，监控完全抓不到。第二，这类失效有个残酷的严重度排序，后来成了我们所有改进的北极星：

```
编造答案（合规事故） ≪ 答非所问（烦） ≪ 澄清/转人工（可接受）
```

无法保证不失效，但必须**锁定失效的下限**：宁可没答到点上，绝不自信地编造。

而在架构层面，失效的高发区就是异步接缝。我们最初的异步化是"天真"的：业务请求里直接调 embedding、直接发通知、直接写 Redis 队列。三种方案各炸了一次：

- **同步调用**：Qwen embedding 一慢，发客服消息的接口跟着慢；同步调用失败还会污染业务事务——重试吧，业务可能已经提交了一半；放弃吧，事件就丢了。
- **直接写 Redis Pub/Sub**：Pub/Sub 不持久化。发布那一刻消费者恰好不在线，消息就永远消失了，而且无迹可查。
- **"业务和消息分两个事务"**：业务提交成功后进程崩溃，消息还没发——出现"业务成功但下游永远不知道"的幽灵状态。

三个方案共同的问题是：**"业务成功"和"事件可达"之间没有可靠的桥。**

## 怎么解决的：Outbox，把消息塞进业务事务里

Outbox 模式的核心想法笨得可爱：**既然业务数据和事件都落同一个数据库，那就让它们在同一个本地事务里提交。**

```
BEGIN;
  INSERT INTO business_table (...);      -- 业务行
  INSERT INTO outbox_event (...);        -- 事件行，status=pending
COMMIT;
```

一个事务，原子提交，没有 2PC，没有跨库协调。"业务成功 ⇒ 事件必落库"由数据库的事务性直接保证。这就是笨办法的力量——它不发明新机制，它复用最古老的机制。

落库之后谁来搬？一个 `outbox_worker`，它的流程每一步都有讲究：

1. `SELECT ... WHERE status='pending' ... FOR UPDATE SKIP_LOCKED`——行锁加跳过已锁行，多实例并发认领互不干扰；
2. **先把 attempt+1 落库再发布**——把"认领"这个动作先固化，进程崩了也不会计数错乱；
3. 逐条发布到 Redis Stream（按 event_type 前缀路由：`memory.` 进记忆流、`knowledge.` 进摄取流……）；
4. 成功才标记 `published`；失败则重试，3 次后置 `dead` 等人工处理。

注意第 3、4 步之间：发布和标记成功是**两个事务**。发布成功后进程崩溃，事件仍是 pending，下一轮会被**再发一次**——所以这套机制天生是"至少一次"投递，必然重复。重复不是缺陷，是诚实的代价，用幂等消费兜住（见下文）。

**为什么 outbox_worker 是全系统唯一的 DB 轮询 worker？** 因为 outbox 表本身就是关系型持久化队列，需要行锁认领语义，轮询是它应得的待遇。其余所有 worker 都走 Redis Streams 消费组——搬运完成后，高性能队列接管。

拿一个真实场景把整条链路串起来：客服对话的 L3 会话摘要。每次对话执行完成，主流程往 outbox 写一条 `memory.summary_extract` 事件（与业务同事务 commit），payload 带客户 ID、会话 ID、本轮诉求、结果和低置信转人工原因；outbox_worker 把它搬到 Redis 的记忆流；memory_worker 消费后调受控 LLM 生成结构化摘要（只允许"本轮关注/已解决/待办/偏好提示"四个字段，禁止敏感明细），读取已有摘要做合并更新——递进提炼，然后落共享记忆。

这条链路上的三条可靠性底线，正好对应组合拳的三个部件：入队走 outbox，"对话处理成功 ⇒ 摘要事件必落库"；投递是至少一次的，摘要 upsert 语义天然可重复提炼；生成失败被 try/except 包住只降级，**绝不阻塞转人工**——摘要锦上添花，转人工雪中送炭，优先级不能反。

## 组合拳的第二拳：Redis Streams + Consumer Group

选 Streams 而不是 Pub/Sub，看中的是三件事：持久化、重放、崩溃恢复。消费组模式的几个关键动作：

- `XGROUP CREATE ... MKSTREAM` 建组，`BUSYGROUP` 错误幂等处理；
- `XADD ... MAXLEN ~10000`——近似裁剪控制内存，流不会无限膨胀；
- `XREADGROUP ... COUNT 10 BLOCK 5000`——阻塞式消费，不是空转轮询；
- **异常时不 ack**——消息留在 PEL（pending entries list）里等待重试；
- `XPENDING_RANGE` + `XCLAIM`（min_idle 30 秒）——消费者挂掉后，它没 ack 的消息 30 秒后由同组其他消费者自动接管。

最后一条是 Streams 相比"手撸队列"的本质差距：worker 崩溃后的恢复语义是现成的，不需要我们自己发明"心跳超时重新入队"这种容易写错的逻辑。

## 幂等与死信：不是可选项，是这套体系的承重墙

既然承认至少一次投递，幂等就不是"最好有"，而是**架构成立的前提**。我们的幂等做了双层：

1. **先查后插**：按 `user_id + idempotency_key` 查已存在则直接跳过；
2. **唯一索引兜底**：部分唯一索引保证并发场景下重复插入触发 `IntegrityError` → rollback → 返回失败。

为什么要两层？因为第一层是应用逻辑，第二层是数据库约束——在并发投递时，"查"和"插"之间有窗口，两个消费者可能同时通过第一层检查，此时只有唯一索引能挡住。**应用层判断挡逻辑重复，数据库约束挡物理重复。**

死信同理。重试有尽头，尽头不是"丢弃"，是**可观测、可人工干预的终态**：

- Outbox 层：`dead` 事件可在 admin 接口查询并人工 retry（写审计留痕）；
- 任务层：`AsyncTask` 状态机走到终态时，把 `{task_id, task_type, error}` 发布到专门的死信流；
- outbox 表本身就是投递审计——status、attempt、error、published_at，每一次投递尝试都有档可查。

冷静想一下：这套 Outbox + Streams + 幂等 + 死信的组合拳，没有一处是"聪明"的设计，全是分布式系统教科书里写了二十年的东西。但它把三种消息丢失场景（业务没成功事件就发了、业务成功事件没落库、消息发了没人收）全部关掉了。

**可靠性工程里，笨办法往往是最贵的聪明。**

## 断点续跑：必须先回答"怎么知道断在哪"

异步可靠性的另一面是长任务。我们有 AML 日批要扫几千个客户、有 Agent 多意图查询要跑多个子任务、有 ReAct 循环要烧多轮 token。以前 Worker 执行到一半崩溃，客户就要重新提问，已烧掉的 token 全部浪费。

这类场景的痛点可以列成一张清单：单个客户失败导致全批次重跑；多意图查询崩溃后客户重新提问；ReAct 第 3 轮崩溃后前 2 轮 token 白烧；未来等银行接口时进程阻塞无法释放资源。共同点只有一个——**执行状态散落在进程内存里，进程一死状态就没了。**

做断点续跑时我们犯过方向性错误：一开始就想着"怎么恢复执行"，后来越做越乱，才意识到真正要设计的是**打断判定**——系统怎么知道"断在哪一步"。恢复逻辑只是把判定结果执行一遍而已。

所以设计的顺序应该是反的：**先定义什么算"完成"、什么算"进行中"、什么算"没开始"，再谈恢复。** 落地成四层恢复模型：

- **任务级**：执行快照。每完成一个子任务就保存 `completed_task_ids`，执行前再存一次当前任务的状态。重启后加载快照，跳过已完成、续跑进行中、超过 3 次恢复标记失败转人工。Worker 启动时专门跑一个恢复流程，扫描未完成任务并处理。
- **会话级**：LangGraph Checkpointer，以 `conversation_id` 为 thread_id，多轮推理中断后从断点继续，不重复调用前几轮的 LLM——token 不白烧。
- **批次级**：AML 扫描按客户粒度记 `succeeded_customer_ids`，单个客户失败记录后**继续下一个客户**，不中断批次；补跑时跳过已成功客户。5000 个客户扫到第 300 个失败，批次状态是 `completed_with_errors` 而不是全批重来。
- **外部等待级**：Agent 等银行接口时存 `ExternalWaitState`，立即返回 `waiting_external` 释放 Worker，Webhook 回调后从快照恢复，24 小时无回调超时转人工。

这四层共享同一条原则：**快照保存在"每个最小可恢复单元"的边界上**——子任务边界、推理轮次边界、客户边界、外部请求边界。打断判定之所以要先设计，就是因为边界划错了（比如以"整个批次"为单位保存快照），恢复粒度就粗到没有意义。

还有一条容易被忽略的底线：**所有恢复操作必须幂等**。恢复本身就是一次"可能重复的执行"——worker 重启、消息重投、用户刷新，都可能触发恢复流程。没有幂等，断点续跑就会变成"断点重跑"。我们的幂等键按版本区分（`nl-draft:{id}:v{version}`），同版本重复确认天然幂等，不同版本天然区分。

快照本身也要考虑存活：Redis 快照设 7 天 TTL 并配过期清理，避免 checkpoint 表无限膨胀；Redis 丢了还有 AsyncTask 的持久化字段兜底——**快照的可靠性不能单点押注在一个存储上**，这和事件投递是同一条哲学：承认任何一环都可能消失，为消失准备退路。

恢复机制的验收也不能只看 happy path：worker 崩溃、消息重复回调、快照版本不兼容、恢复超过次数上限——每一种都要注入故障去测。**续跑逻辑只有在"真的断过"之后被验证过，才算存在。**

## 为什么这么选

有人问过：为什么不用消息队列中间件（RabbitMQ/Kafka）一步到位？我们的场景判断是：关键词腿只是辅助、向量腿才是主力的架构里，为一个异步事件流引入一整套独立中间件的运维成本，远大于"PostgreSQL + Redis 这两样我们本来就要运维的东西"的边际成本。Outbox 的好处恰恰是把"队列"退化成一张表——备份、监控、审计全部复用现有设施。

回过头看整个演进：从"直接调"到"直接发"再到 Outbox，我们实际上是在逐步诚实地回答同一个问题——**"业务成功"和"下游感知"这两个事实，到底由谁、以什么顺序、在什么事务边界内保证？** Outbox 的答案是"同一个事务"，Streams 的答案是"消费组 + PEL"，幂等的答案是"至少一次 + 去重"，断点续跑的答案是"快照 + 打断判定"。四个答案拼起来，才是完整的异步可靠性。

## 教训

1. **功能正确不等于系统正确，接缝才是事故高发区。** 评审新功能时，别只看它自己跑不跑得通，要问：它写的每个字段谁会读？它依赖的前置判断在什么语境下会失效？
2. **"恰好一次"是幻觉，"至少一次 + 幂等"是现实。** 主动接受重复投递，用业务幂等键加数据库唯一索引做双层去重——试图消除重复的方案，最后都输给了进程崩溃。
3. **死信是功能，不是兜底姿态。** 没有可查询、可人工 retry 的死信终态，重试就只是把"立刻失败"变成"三天后悄悄失败"。
4. **断点续跑的第一性问题不是"怎么恢复"，而是"怎么知道断在哪"。** 先把最小可恢复单元的边界划清楚、快照在每个边界上落盘，恢复逻辑自然水到渠成；反过来做，全是返工。
