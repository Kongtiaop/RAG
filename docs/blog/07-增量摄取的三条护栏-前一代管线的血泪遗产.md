# 增量摄取的三条护栏：前一代管线的血泪遗产



## 一、以为做完了，翻出一份伤亡名单

agentic_rag 的增量摄取上线那天，我是满意的：按文件 sha256 判定变化，未变的整篇跳过（零 embedding 成本），变更的单篇替换，磁盘删了的从库里清理。二次运行 27 篇全部跳过，测试全绿。

直到我翻出上一代实验管线 pg_prefect 的封盘总结。那个项目干的就是同一件事——文档注册表、内容 hash Diff、SimHash 血缘、Prefect 编排，把本地脚本型 RAG pipeline 演进成支持文档版本管理和增量更新的 ingestion 服务。它的封盘文档里躺着 15 个问题，其中三条，恰好是我这次实现**没有设防**的。

这份文档像一份伤亡名单：每一条护栏背后，都是一次真实发生过的数据事故。对照读下来，我发现自己在无意识中已经继承了一条，暴露了两条。

## 二、护栏一：身份和版本是两个东西

pg_prefect 的第一课：**单独使用 content hash 无法区分三种情况**——文件重命名、文件移动、内容相同但业务身份不同的文档。

解法是把两个概念拆开：

```text
document_key   文档业务身份（它"是谁"）
content_hash   当前内容版本（它"现在长什么样"）
```

对照我的实现：doc_id 由"层-文件名前缀"生成（`blog-01`、`basics-15`），这本质上就是 document_key；content_hash 是版本。身份和版本的分离，我无意中做对了——代价是**文件名前缀成了身份契约**：改前缀等于换人，同层出现重复前缀等于两个人共用一个身份证。

这条教训的通用形态是：**任何增量系统，先回答"什么东西的身份"再回答"什么东西变了"**。顺序反了，后面的 Diff 算得再精都是在错误的身份上做文章。

## 三、护栏二：新版本失败，不许弄脏旧版本

pg_prefect 的第二课：如果新文档处理失败，**不能让旧版本失效**。它为此设计了显式的版本切换状态机：

```text
旧版本 active
新版本 processing
新版本成功 → 新版本 active，旧版本 superseded
新版本失败 → 新版本 failed，旧版本继续 active
```

对照我的实现：单篇替换在数据库事务里（先删后插一个 transaction），embedding 失败发生在事务开启之前——**旧数据纹丝不动**。这条护栏被事务边界天然覆盖了。

但诚实地说，这是"恰好做对"而不是"刻意设计"：如果当初把 embedding 放进事务里、或者先删后异步插入，事务就保不住了。pg_prefect 用状态机显式表达的约束，我只是靠运气用一个事务隐式满足了。**显式的护栏优于隐式的巧合**——下个改动者未必还有这个运气。

## 四、护栏三：目录异常的批量误删（这条我暴露了）

第三条是我真正暴露的。

pg_prefect 的事故场景：**volume 没挂载，扫描结果看起来像"所有文件都消失了"**。如果系统忠实地执行"磁盘没有的从库里删除"，就是一次全库清空。它的防御是一套组合拳：

```text
目录不存在 → 返回 missing_path，直接拒绝
普通扫描 → 永远不执行删除
full_sync=true → 才允许缺失同步
删除比例阈值 → 超过 20% 阻断
删除数量阈值 → 超过 1000 条阻断
```

而我的 ingest：`collect_documents()` 扫描目录，glob 返回什么就处理什么。**如果部署环境里 docs 目录没挂上（容器路径错了、volume 漏了、或者只是 CI 上传时序问题），扫描结果是 0 篇 → 现有的 27 篇全部判定为 stale → 全部 DELETE。** 完整复刻那场事故，只差一次手滑。

这次补上的护栏，几乎是对 pg_prefect 方案的致敬：

```python
# 护栏 1：扫描为空且库里有数据 → 大概率目录没挂上
if not full and not docs and existing:
    print("扫描结果为空但库中有文档——疑似目录缺失（missing_path），拒绝执行。")
    return

# 护栏 2：批量删除双阈值（比例 20% / 数量 1000），超限阻断
if stale_ids and not allow_mass_delete:
    ratio = len(stale_ids) / len(existing)
    if ratio > 0.2 or len(stale_ids) > 1000:
        print(f"删除护栏触发：stale {len(stale_ids)} 篇占库 {ratio:.0%}，疑似异常，已阻断。")
        stale_ids = []
```

有意思的是阈值本身：20% 这个数字不是算出来的，是**事故换来的**——低于它，正常的批量改稿能通过；高于它，大概率是基础设施在说谎。护栏阈值从来不是数学，是伤亡统计。

## 五、附赠一课：SimHash 不能复用 Embedding

pg_prefect 还有一个"接入了但差点用错"的组件：SimHash。

直觉很诱人：新旧 chunk 的 SimHash 相似，说明文本差不多，那 embedding 是不是可以直接复用，省一笔 API 钱？

**不行。** 相似文本不代表语义不变——尤其数字、日期、金额和否定词的变化：`涨了 5%` 和 `跌了 5%`，SimHash 视角下几乎一样，embedding 视角下南辕北辙。所以它的最终设计是：

- 精确 content hash 相同 → 才直接复用 embedding；
- SimHash 只用来判断新旧 chunk 是否属于**同一血缘**（lineage，用于新旧版本关联）；
- 血缘上判定为"变化"的 chunk，**老老实实重新生成 embedding**。

这也是一条通用教训：**便宜的相似度信号只能用来做分组和关联，不能用来省昂贵的精确计算**。省钱的企图必须在语义无损的边界内。

## 六、尾声：护栏是从伤亡名单里抄来的

把这份封盘总结读完，我对"经验复用"这个词的理解又具体了一层。以前说的复用是选型结论（用 pg_search 不用 ES）、是架构模式（混合检索、版本切换）——这次不一样，**复用的是防御工事**：一个没有 volume 挂载导致的批量误删、一次新版本覆盖旧版本的风险、一个 SimHash 省钱省出语义错误的陷阱。

这些事故的原主人是我自己（前一代实验管线也是我写的），所以抄起来毫无心理负担。但方法本身是通用的：**接手或新建任何增量系统之前，先问三个问题——身份怎么定义？版本失败会怎样？删除有没有护栏？** 三个都答得上来，才配开始写第一行 Diff 代码。

至于我的 agentic_rag：三条护栏，一条无意中做对了，一条被事务顺带覆盖，一条这次真补上了。伤亡名单还在增长，但至少下一份事故报告里，不会再有"目录没挂载导致全库清空"这一条。
