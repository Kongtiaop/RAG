# 权限为什么必须先于路由：Agent 化之后，权限不再是接口的属性

## 问题什么时候变尖锐的

做传统 CRUD
系统的时候，权限问题听起来很"标准化"：每个接口挂一个权限校验，谁能调这个接口，查表就行。权限是**接口的属性**。

Agent 一进来，这个前提塌了。

用户不再直接调接口，而是说一句话，由 Agent
理解、规划、然后**代替用户去调工具**。于是权限校验的对象从"谁在调接口"变成了"模型替谁、查了什么、拿到了谁的数据"——它变成了**每一次模型决策的属性**。我们没有立刻意识到这个转变有多尖锐，是被真实缺陷教育了几次才明白的。

第一次教育：后台"Agent
控制台"最初复用客户侧的执行管线，结果员工查客户数据，被回答"知识库没有足够依据，建议转人工"——因为员工请求被接进了客户向的客服兜底逻辑，而那个语义只对真人客户成立。员工问个人资产查不到数据，因为管线按"当前登录者=客户"在拿员工本人的
id
查持仓。更糟的是记忆语义混用：员工查询把结果写进"员工=客户"的桶里，**污染客户档案归属**。

第二次教育：LLM 意图回退开关上线后，暴露出一个缺陷——高置信的事实类意图被映射表压成
faq 模板桶，用户问"查一下我的持仓"被回复"转人工"，数据明明就在库里。

第三次教育：知识库语料里 39 个 chunk 被标成 `staff` 权限，而
`staff` 不在任何客户 scope 的允许列表里——**没有任何 scope
能取到的孤儿内容**，检索侧怎么调 top_k 都是空。

这三件事共同指向一个结论：**权限不能是路由之后的过滤器，必须是路由之前的闸门。**

## 设计动因之一：能力白名单——先筛人，再路由

我们的主 Agent 是 Supervisor 模式：理解请求、拆任务、分派给子
Agent。分派之前的第一步不是"哪个 Agent 最合适"，而是"**这个用户被允许见哪些
Agent**"：

```text
用户角色/权限 → available_agents / denied_agents → 只在白名单内路由
```

这个顺序换过来的代价是具体的：如果先路由再鉴权，用户会看到"内部 Agent
拒绝访问"这类暴露内部结构的报错，审计日志里也解释不清"为什么没有调用某个
Agent"。先过滤，这些问题都不存在，而且减少了无效调用。

操作级权限我们全部落在服务端依赖注入上，三道门各管一件事：`require_permission`
校验权限码，`is_super_admin`
直接放行；`require_staff_permission` 在权限之外**额外拒绝持有
customer
角色的用户**——防止客户调工作人员接口；`require_advisor_permission`
要求角色和权限码同时满足。前端隐藏菜单只是体验优化，不是授权依据——手工请求、调试工具、爬虫，都绕得过去。

配套还有一个细节：JWT 里虽然放了
roles，但**每个请求都从数据库重新加载用户、角色和权限**，并校验用户仍是
active 状态。角色改了、用户被禁用了，下一个请求立即生效，不等 token
过期。JWT 只是"身份 + 过期"的凭证，永远不是授权源。

这套矩阵还配了严格的测试标准：每个受保护 API 至少覆盖未登录 401、无权限
403、客户访问员工接口 403、跨客户访问 403、审计员访问状态变更接口
403——而且超级管理员也要按明确授权契约测，**不以"默认全放行"作为测试依据**。矩阵本身有可执行的种子实现，每次启动把角色权限收敛到种子定义的状态，不靠人肉记忆。

## 设计动因之二：Subject Scope——"能做什么"和"能对谁做"是两件事

能力白名单解决"能不能做"，但投顾场景里真正要命的是另一个维度：投顾有
`advisor:recommend`
权限，不代表他能看**所有**客户的持仓——只能看**授权给他的**客户。

所以我们把数据范围做成了独立的一层：`SubjectScopeService`
从授权表算出每个用户可见的客户 id 集合，授权记录要求
`status=active`、在有效期内、未被撤销。而且 scope 不只是 id
集合，还携带金额上限、产品范围、风险等级上限——授权不是开个名单，是带条款的。所有授权变更走单一写入口（行锁防并发重放），变更经
Outbox 事件驱动缓存失效，事件与数据变更同事务提交，崩溃可重试。

这一层最关键的防越权机制，是我们认为自己做得最对的一个决定：**SQL 的 subject
参数在服务端被改写为授权闭包**。用户问题里提取的客户标识，先和授权集合求交集，出现任何不在集合内的
id 直接拒绝；然后模板的 subject 参数由服务端替换成授权 id
集合（普通用户则是本人 id）。**客户在请求里传什么 customer_id 都进不了最终
SQL**——不是"前端传参、后端校验"，而是后端根本不用前端传的那个值。

我们明确否决过 ORM 模型层全局 query filter
的方案：它隐式、难审计、多角色并集/交集语义混乱、join 复杂，而且覆盖不了"模板 SQL
参数"这种动态路径。显式传参 + 显式校验，可测试、可读、可审计。

## 权限版本化缓存：解决"改了权限，缓存还认旧的"

权限上了缓存之后冒出新问题：管理员改了某用户的角色，缓存里还是旧的权限指纹，旧答案继续命中。最直觉的解法是"改权限时把该用户相关的缓存
key 删掉"——但这要枚举、要扫描 Redis，还不原子。

我们的方案是**版本号**：每个用户两个版本键（权限版本、scope
版本），管理员改用户角色时 bump
一次；改角色权限时，遍历该角色**全部受影响用户**逐个 bump；授权变更走 Outbox
事件同样 bump。版本号参与缓存 key 指纹的计算——**版本一变，指纹就变，新生成的
key 和旧 key 不同，旧条目逻辑上不可达**，靠 TTL 自然回收。不需要扫描删除任何
key，INCR 原子，粒度精确到用户。

但真正让我们安心的设计是**双重保险**：缓存 key
的指纹里本来就包含实时的角色码和权限码——就算版本号 INCR
失败了，权限本身变了指纹照样变。版本号是"急切失效"，指纹是"安全底线"。缓存读取任何异常都返回
None 走实时查询，写入失败只返回
False。角色变更和授权变更用两个独立的版本号，互不串扰。

一句话：**缓存不承担任何授权职责。授权结果 100% 来自数据库实时计算，Redis
挂掉的代价只是变慢，不是变不安全。**

## "先跑通再加权限"为什么是坑

我们真踩过这个坑，所以有资格说它为什么是坑。

当时的想法很"敏捷"：先把管线跑通，权限后补。结果是权限变成了**到处打补丁**——上面说的三个案例（员工被当客户、意图降级、孤儿语料）全都是"先跑通"留下的债。最典型的是孤儿语料：语料导入时没有权限校验，`staff`
权限的内部文档进了客户可见的检索范围，等发现时 39 个 chunk
检索不到，排查时还一度误判成"类目过滤没生效"——权限先把它拦掉了，与类目无关。**权限不是最后加的装饰，它决定了数据在系统里能不能被看见。**

"后补"还有个隐蔽形态：**开关的默认值说谎**。我们的 LLM 意图回退，6
份文档都写"默认关闭"，实际生产 compose 里是
`${LLM_INTENT_FALLBACK_ENABLED:-true}`——线上开着。排查时正是被文档误导，把一个生产降级缺陷当成"仅
shadow
模式"而没有优先处理。这个开关后来真实暴露了上面说的意图降级缺陷。默认值有三层（代码默认 /
compose 覆盖 / 本地 .env），排查"某能力是否生效"必须追到部署清单的最终值。

前端旁路是第三个坑：部分交易意图仍走前端本地关键词判断，没有收敛到后端受控工作流。前端的判断绕过了后端的权限和一致性检查，是一个天然的权限缺口——它时刻提醒我们"前端只做体验"这条原则必须靠收敛执行，不能靠自觉。

LangGraph
切流的经历补上了最后一课：图的权限、scope、幂等校验和管线是两套调用路径，**切流前必须逐点对齐**。影子双跑对照抓到图缺
4 个持久化副作用——如果只看"功能跑通了"就切，这些问题会直接上生产。

所以现在我们的设计原则第一条写的是：**权限先于 Agent
路由。**这不是审美偏好，是几次事故换来的顺序。

## 教训

1. **Agent 化之后，权限的对象从接口变成了每一次模型决策。** 先按权限筛掉不可见的 Agent 和工具，再做语义路由——顺序反了，报错暴露内部结构，审计也说不清。
2. **"能不能做"和"能对谁做"是两层，要分开建。** 能力白名单管操作，Subject Scope 管数据；防越权的根本是服务端改写参数为授权闭包，而不是校验用户传来的值。
3. **缓存永远不改变授权结果。** 版本号做急切失效，实时权限指纹做安全底线，授权答案只信数据库。
4. **"先跑通再加权限"的债是静默的。** 孤儿数据、被误导的排查、说谎的开关默认值、绕过后端的前端旁路——权限欠账不会报错，只会在你最忙的时候变成最难的 bug。
