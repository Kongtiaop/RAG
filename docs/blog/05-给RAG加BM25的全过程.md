# 给 RAG 加 BM25 的全过程



## 一、问题：检索在精确词上失灵

我们做了一个金融客服的 RAG 系统，检索走的是 pgvector 向量检索 + PostgreSQL 内置全文检索的双路混合。

设计上听起来很完整，但实际用起来，有一类问题向量检索总是答不利索：**用户问的是精确词**——产品型号、错误码、制度名词这种。

"什么是适当性管理"这种语义问题向量检索没问题，可一旦用户拿一个精确术语来问，embedding 未必能把这个词和正确的文档片段拉近。

我们本来的兜底是文本腿：`to_tsvector + ts_rank_cd`。但很快发现这条腿在中文场景下**基本是废的**——PostgreSQL 的 `simple` 配置不做中文切词，整句扔进去 ts_rank 算出来常年是 0，文本腿频繁退空。

也就是说，我们的"双路混合"在中文下实际上退化成了**纯向量检索**，我们一直引以为傲的架构冗余，其中一个分支根本没在工作。

问题清楚了：需要一条真正能打的关键词腿，也就是 BM25。但怎么把它接进来，比想象中麻烦——后来的全过程证明，"引入一个索引"背后牵着代码架构、事务模型、分词、评测方法、镜像部署一整串事。

## 二、选型：不为一根辅助腿引入一个引擎

第一个决策是技术选型。摆在面前的两条路：

1. **Elasticsearch/OpenSearch**：标准 BM25，久经考验。但要新增一个服务，多一套部署、监控、数据同步链路。
2. **ParadeDB 的 pg_search**：在同一个 PostgreSQL 库内提供 BM25 索引，和 pgvector 共存一个库。

我们选了 pg_search，理由很简单：**关键词腿只是辅助，向量腿才是主力**。为一条辅助腿引入一个独立的搜索引擎，运维成本和它带来的收益完全不成比例。我们整个知识库架构的卖点就是"pgvector 单库少运维"，这条原则不该被一个 BM25 破坏。选 pg_search 的本质是承认"够用比标准更重要"。

当然，这个选择也有代价——pg_search 相对小众，后面踩的坑证明了这一点。

代码层的设计我们刻意保守：配置里新增一个 `fulltext_backend` 开关（`tsvector` / `pg_search`），**代码默认值钉在 tsvector** 作安全兜底；检索仓储里的文本腿抽成独立的分支函数，按开关分发到旧的 ts_rank 逻辑或新的 BM25 逻辑。BM25 那条分支带 scope 和激活状态过滤，并且**用独立连接做事务隔离**——为什么强调这一点，见下面坑一。

中文检索还差一块拼图：pg_search 不认识中文词。我们在应用层写了一个拆词器：剥掉停用词，把长短语切成字 bigram，用空格连接——pg_search 对空格分隔的词默认走 OR 语义。这个拆词器配了专门的单元测试，是整条链路里我们最有把握的一环。

## 三、落地：那些教科书不会写的坑

### 坑一：pg_search 失败会把整个会话炸掉

最阴险的一个 bug：pg_search 查询失败时，会把共享 session 的事务 abort 掉。我们的降级逻辑本来的设计是"pg_search 出问题就回退 tsvector"，听起来很稳。但实际运行时，降级路径一跑就报 `InFailedSqlTransactionError`——**兜底逻辑本身被主逻辑的尸体拖死了**。

这个 bug 教会我们一件事：在一个共享事务里，前一条语句失败后，后面的语句连执行资格都没有。所谓"自动降级"如果降级路径和主路径共用一个事务，那不是降级，是陪葬。

修法：pg_search 分支改用**独立连接做事务隔离**。黑盒扩展的失败不应该污染主事务——这是现在我们写任何"可选增强"时的默认动作。

### 坑二：中文整句 0 命中

BM25 是词级检索，我们第一次拿"什么是适当性管理"这种整句去查，结果是 **0 命中**。中文整句不分词，BM25 根本不知道你要找什么。

我们没有急着上 jieba 分词器，而是先在应用层做了个轻量方案：剥停用词、长短语用字 bigram 切开、空格连接走 pg_search 默认的 OR 语义。

实测效果：单独查"适当性"能精确命中 12 条，整句经代码路径返回 5 条正确文档，相关文档排在前面。

这个方案糙但有效——因为**语义排序的活儿由向量腿干，关键词腿只负责"把含有这个词的候选捞进来"**，OR 宽召回完全够用。如果后面召回精度不够，再升级成真正的 jieba tokenizer 也不迟。

### 坑三：key_field 写错，整表写入静默失败（这是最贵的一课）

这是整个项目里最值得记的一笔。BM25 索引我们有两种写法：

```sql
-- A 形态：key_field 指名的列写进字段列表
CREATE INDEX ... USING bm25 (id, content) WITH (key_field='id');

-- B 形态：只写 WITH
CREATE INDEX ... USING bm25 (content) WITH (key_field='id');
```

B 形态**能建索引、能查询**，看起来一切正常。但任何 INSERT 都会报 `No key field defined`——**整张表的所有写入全部失败**，包括后台上传接口和 ingestion worker。

更可怕的是，错误只发生在写入侧，检索侧一切正常，所以它**长期没有被发现**。知识库灌不进数据，大家还以为是上传流程没跑完。

排查过程本身就值得复盘，因为我们连错了三次：

1. 猜"配置是 tsvector、索引是遗留物"——查了配置，`pg_search`，索引真在用。证伪。
2. 猜"索引由旧 DDL 创建、key_field 解析不了"——看元数据，key_field 好好的，而且**查询能用**。证伪。
3. 猜"元数据陈旧、REINDEX 能修"——REINDEX 成功，写入照样失败。证伪。

真正的转折是一个看起来不起眼的观察：**读写不对称**。读侧正常、写侧失败。如果 key_field 真的解析不了，查询也该挂。这个观察把问题锁定在写入路径。

于是放弃推理，做**临时表对照实验**——四种索引形态各建一张临时表，逐个试写入。结果一目了然：只有 A 形态写入可行。`key_field` 指名的列必须出现在索引字段列表里，只写在 `WITH` 里不够。

修的时候又遇到两个坑。

一是 ParadeDB 限制一表只能有一个 bm25 索引，"先建新索引再平滑切换"**在架构上根本不可能**，只能单事务 DROP+CREATE+写入探测、失败整体回滚。

二是我们自己写的诊断脚本有个 bug：探测写入后无论成败都 `rollback()`，把同一事务里的 DROP+CREATE 一起撤销了，脚本却报告"修复成功"——**假成功**，比失败更危险。后来改用 SAVEPOINT，并用 sqlite 造了反例验证探测逻辑真的有效。

事后补了两件事：把索引纳入 migration 管理（之前它游离在版本管理之外，和扩展版本脱节了都没人知道），以及这个对照实验的教训——**早做一次，能省三轮推断**。

### 坑四：镜像与版本

部署环节的坑属于"杂但烦"：DaoCloud 加速源对某些仓库直接 403；顺手拉 `latest` 结果是 PG18 的镜像，和 PG16 的数据卷不兼容。最终钉死 `paradedb/paradedb:pg16`，并确认镜像内 PGDATA 路径和原来一致——主版本一致加路径一致，旧数据卷可以无缝换引擎。另外 pg_search 必须先加进 `shared_preload_libraries` 并重启，才能 `CREATE EXTENSION`——这个顺序不能反，我们先 CREATE 才发现加载不了扩展，又回头补配置。

还有一条容易被忽略的运维事实：容器重建要用对 compose 文件。旧的 postgres 容器是 p0 那套 compose 项目起的，用错 compose 文件去重建，容器名对不上、环境变量也全变——这类"部署脚本各管一段"的错位，每次都能白耗半小时。

换镜像前先备份数据卷，这条纪律救过我们不止一次。`docker run --rm` 挂上数据卷打个 tar 包，五分钟的事，换来的底气是"最坏情况能整体回滚"。

### 回退安全网：让新能力随时可以关掉

上线设计里我们准备了**两级回退**：第一级，出问题只关 BM25——改一个环境变量重启 API 即可，代码自动降级回 tsvector，不用动任何数据；第二级，怀疑镜像本身——恢复备份的数据卷，compose 镜像换回原来的 pgvector 镜像。

生产部署走的是 CI/CD：提交后 GitHub Actions 跑全量测试，通过后自动 SSH 到服务器重建容器。pg_search 的运行时就绪（改 shared_preload、建扩展、建索引）是手动做的一次性动作，做完逐项验证：`SHOW shared_preload_libraries` 确认加载、确认扩展版本、确认索引存在。检查清单里有意的留了两项待办没打勾——"后台灌入知识数据"和"灌数据后复测 BM25 命中"。**功能就绪和经过实测是两个状态，检查清单不替你说谎。**

## 四、评测：三路召回到底谁在干活

功能上线后需要回答一个灵魂问题：加的这条 BM25 腿，到底有没有用？

最初想用 RAGAS 这类现成的 RAG 评测框架，发现它依赖过时的包，直接弃用。反而逼出一个更好的方案：**确定性评测**。以每条用例标注的 `gold_fragments`（标准答案所在的文档片段）为基准，计算 fragment_recall 和 hit_rate——不经过 LLM，结果可复现、可回归，每次改检索逻辑都能跑一遍对比。

我们设计了**三路召回评测**：只向量、只关键词（BM25）、双路（RRF 融合）各跑一遍，对比在真实知识库上的召回。几个设计决策：

- **gold 必须真实存在**。评测集从 16 条扩到 64 条，新增的 48 条全部基于真实文档内容，每条 gold 逐条校验确实存在于库中——不编造。编造的评测集只会产出自我安慰。
- **按 intent 分层报告**。64 条样本的 intent 分布天然不均，整体汇总会掩盖差异，这是我们一开始就吃过亏的。

结果出乎意料地有信息量：向量腿在语义问答语料上 recall 最高（99.2%），BM25 腿补精确词，hybrid 的 hit_rate 达到 100%。但中间出现过一个吓人的数据——**双路的 recall 居然低于单路**。差点据此下"混合检索有害"的结论，追查后发现是 RRF 融合的 top_k 截断造成的评测假象，不是真实退化。

> 评测框架给出的数字会诚实呈现，但"数字在什么口径下产生"需要人自己去审。按 intent 一分层，假象立刻现形：hybrid 的 hit_rate 最高，靠的正是补上了 keyword 单路漏掉的 faq 和 company_info 类目——**关键词腿的增量价值恰恰藏在分层视角里，整体平均一眼根本看不出来**。

## 五、为什么这套设计站得住

回头看，这次改造有几个决策我们认为是对的：

1. **可插拔 + 默认兜底**。代码层默认 `tsvector`，pg_search 是配置项打开的可选增强，异常自动降级。任何新能力都应该做到"一换不崩、随时能退"。
2. **不引独立引擎**。这个选择让我们少养一个服务，代价（踩 pg_search 的坑）是可控且已付清的。判断依据是角色权重：关键词腿是辅助、向量腿是主力，辅助腿配"重装备"不划算。
3. **检索失败不传染**。独立连接隔离，让可选扩展的失败半径被硬性圈住——降级逻辑必须保证降级路径自己活着。
4. **中文问题在应用层解决，不动索引层**。拆词 + bigram + OR 的方案糙但可控，还保留了"以后升级成真正的分词器"的接口。分层解决问题，每一层保持可替换。

## 教训

1. **一个组件能建、能查，不代表它能写**。只验证读路径不验证写路径，key_field 这种错误会让整表写入静默失败数周。任何索引变更，把 INSERT 也跑一遍再上。
2. **中文下别信"内置全文检索"**。PG 的 simple 配置不切词，ts_rank 常年为 0，你以为的双路可能只是单路——架构图上的冗余要实测验证，不能只看图。
3. **推理连错三次时，去做对照实验**。临时表四种形态摆一起，一次定位。能跑的探测永远比聪明的推断便宜。
4. **评测结论先审口径**。"双路不如单路"这种反直觉数据，先查评测框架自身（top_k 截断、样本分层），再怀疑系统。反直觉的数字多数是评测假象。
