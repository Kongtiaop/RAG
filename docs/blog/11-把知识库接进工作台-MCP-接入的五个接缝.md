# 把知识库接进工作台：一条 MCP 连接上的五个接缝

## 一、功能正确 ≠ 别人连得上

MCP Server 写完的那天，本地 stdio 模式跑得很顺：握手、list tools、search_docs 返回命中，一切符合预期。那时的判断是"接入做完了"。

真正的验收发生在另一个位置——把服务挂到公网，让 WorkBuddy 这样的远程客户端连进来。同一个服务，同一批工具，五个接缝依次爆出来，每一个都不在"检索是否准确"的范畴里，每一个都只在**两个各自正确的部分相遇时**才现形：

```text
服务端 FastMCP（HTTP 传输）  ×  nginx 反向代理（路径重写 + 门禁）
客户端 SDK（版本 A）        ×  服务端 SDK（版本 B）
工具定义（开发视角）        ×  模型视角（描述即 API）
```

这条链上的教训是通用的：**功能本身很少出错，接缝几乎一定出错，而且静默**。

## 二、接缝一：门禁放在代理层，不放业务层

MCP 服务直接暴露 9001 端口是裸奔。第一个念头是在 `mcp_server.py` 里校验 token —— 但这条路会把鉴权逻辑和工具实现缠在一起，而且每个新工具都要记得加。

最后选的是：**mcp 容器只监听内网，nginx 在 `/mcp` 路径上做门禁**。

```nginx
location /mcp {
    if ($http_x_mcp_token != "${MCP_TOKEN}") { return 403; }
    proxy_pass http://mcp:9001;
}
```

token 不进镜像，由 compose 传环境变量、启动时 `envsubst` 渲染模板。好处是三条：

1. 鉴权只有一处，加工具不用管它；
2. 密钥不落仓库（`.env` 在服务器上，镜像里没有）；
3. **验证方式变得可判定**——无 token 拿 403、带 token 才可能握手，这是一条能写进脚本的断言，不是"我试了能连"。

代价也很明确：门禁**只认头，不认路径内的凭据**。所以任何客户端都必须支持自定义 HTTP header —— 这一条后来成了选客户端时的硬门槛。

## 三、接缝二：尾斜杠引发的 307

配好之后客户端报错，指向一个 `307 Temporary Redirect`。

原因是 URL 写法和代理写法对不上：FastMCP 的服务端路径是 `/mcp/`（带尾斜杠），而 `proxy_pass http://mcp:9001/mcp/;` 这种**带 URI 的写法会重写路径**，一重写就和客户端的 URL 拼出不一致的位置，服务端按规范回 307 让你去"正确的位置"，客户端跟着跳，跳到门外。

修法是最朴素的那种——**代理不做路径重写，让路径原样透传；客户端 URL 也不写尾斜杠**：

```nginx
proxy_pass http://mcp:9001;   # 注意：没有 /mcp/，路径原样透传
```

这条踩完的收获不是"nginx 要这样写"，而是：**307 是服务端在说"你的路径不对"，不是网络问题**。看到 3xx 先怀疑路径拼接，别去查防火墙。

## 四、接缝三：无状态才有远程可用性

Streamable HTTP 默认是有会话的（服务端发 `Mcp-Session-Id`，后续请求要带上）。本机测试完全没问题，因为一个客户端对一个进程。

但经过 nginx、可能还有多实例时，会话粘滞立刻成为负担：请求打到另一个实例，会话不认。

```python
mcp = FastMCP("agentic-rag", stateless_http=(TRANSPORT == "streamable-http"))
```

无状态模式的取舍要说清楚：**牺牲了服务端推送和跨请求上下文**，换来"任何一个请求都能被任何实例处理"。对检索类工具（每次调用自带完整参数、无多轮状态）这笔交易划算；对有长会话的 Agent 服务就不划算。选型时先看工具是否真的需要会话状态，而不是抄配置。

## 五、接缝四：客户端 SDK 的大版本

验证脚本用 `mcp` 2.x 写，报了一堆参数不匹配。查下来是 1.x 和 2.x 的客户端入口签名不一样：

```python
# mcp 1.x
async with streamablehttp_client(url, headers=headers) as (r, w, _):
    ...

# mcp 2.x：自带 http_client
async with streamable_http_client(url, http_client=httpx.AsyncClient(headers=headers)) as (r, w, _):
    ...
```

服务端反而必须钉在 `mcp<2`（`FastMCP` 在 2.x 更名 `MCPServer`）。也就是说**同一个项目里服务端锁 1.x、客户端用 2.x**，这不是矛盾，是两侧依赖要分开声明。把服务端锁版本的理由写进 `requirements.txt` 注释里，比写在心里可靠。

## 六、接缝五：工具清单在连接时就被抓走了

第五个接缝是今天才踩的，也是最容易反复踩的。

语料后来长出了第三层（每天一份的开源日报）。服务端加了 `latest_daily` 工具、`search_docs` 也支持按层过滤——代码对、部署成功、容器内实跑全对。但工作台里的机器人还是只会查博客。

原因不在服务端：**MCP 客户端在建立连接时就把工具清单抓走了**，之后一直用缓存，不重连就不会刷新。所以"我改了工具"和"客户端看见新工具"之间隔着一个必须由人完成的动作：重连或重启客户端。

这不只是缓存问题，它反向定义了工具设计的约束：**工具清单是低频变化的接口面，每加一个工具都意味着一次客户端侧的人工动作**。于是更要紧的不是"多给几个工具"，而是"给对的那几个"——工具数量本身就是一种成本。

## 七、描述即 API：模型看不见你没写的东西

第五个接缝修的时候，顺手把工具面重做了一遍，发现三个更隐蔽的问题，全在**模型视角**上：

1. **描述里没写的层，等于不存在。** `search_docs` 的描述写的是"技术博客与基础知识库"，模型就只在那两层里找，日报明明在库里也检索不到——不是检索错了，是模型根本没被授权知道它存在。
2. **枚举写死会堵死新数据。** `list_documents(layer)` 的 `enum` 还是 `["blog","basics"]`，第三层加进来时没人记得改这里，模型连列举都做不到。
3. **时序语料不适合交给向量。** 日报是"每天一篇、标题带日期"的语料，"最近几天有什么新项目"这种问题，语义检索会把三个月前的相似条目排上来。正确做法是给它一个专用工具：按日期倒序取清单，再按 `doc_id` 读全文。

于是工具面变成四个：`search_docs`（三层，可用 `layers` 限定）、`latest_daily`（最近 N 天清单）、`get_document`（读全文）、`list_documents`（清单 + 各层文档数）。参数层面只有一个原则：**层是闭集，非法值显式报错并回报可选值**，不静默忽略——静默忽略会让模型以为限定了范围，实际全库在查，而它自己永远不会发现。

## 八、可复制的配置

给同类客户端的配置就三行关键信息：

```json
{
  "mcpServers": {
    "agentic-rag": {
      "url": "http://<你的域名>/mcp",
      "headers": { "X-MCP-Token": "<服务器 .env 里的 MCP_TOKEN>" }
    }
  }
}
```

- URL **不带尾斜杠**；
- 自定义头 `X-MCP-Token` 是门禁凭据，等价于知识库读权限，不进聊天、不进截图、不进仓库；
- 只支持 stdio 的客户端（如 Claude Desktop 旧版）用 `npx mcp-remote <url> --header "X-MCP-Token: ..."` 桥接；
- 改过工具定义之后，**必须重连客户端**才看得到新工具。

验证按三层来，每层都可判定：无 token 403 → 带 token 握手成功且拿到工具列表 → 一次真实检索命中预期文档。

## 教训

**接缝不会自己暴露，得给它设计探针。** 这次的探针是三条：403 断言（门禁真的在拦）、握手后打印工具清单（工具真的在册）、一次带期望结果的检索（链路真的通）。三条都写进脚本，比"我连上了，挺好"可靠得多。

**工具描述的写法，就是接口的可用性。** 模型不会读到你的代码、你的表结构、你的目录约定，它只读描述和参数 schema。描述里少一句"还有第三层"，就是一个功能对用户不存在。

**版本、缓存、路径，这三样东西的错都长得像"网络问题"。** 每次都先怀疑环境，每次都发现是自己拼接错了。定位顺序应该是：先看服务端日志里请求到底有没有到，再看路径、再看版本，最后才怀疑网络。

最后一句是给自己留的：这次的"接缝"里有两个是**别人（客户端/代理）的行为**，我改不了；有三个是**我自己的设计选择**，当时都觉得没问题。后者才是可以提前防的部分。
