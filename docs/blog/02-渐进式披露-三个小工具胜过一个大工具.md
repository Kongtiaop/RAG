# 渐进式披露：三个小工具为什么胜过一个大工具

## 碰到的问题：检索把上下文撑爆了

我们正在做 agentic RAG，让 Agent 直接面对文档库回答问题。最开始的想法非常直觉：给 Agent 一个"大而全"的检索工具——输入问题，返回 top-k 个最相关的文本块，模型读完就作答。一次调用搞定一切，接口简单，实现也快。

跑起来之后问题一个个冒出来：

**第一个问题是上下文被碎片占据。** 一个问题触发一次检索，返回 10 个 chunk，每个 chunk 几百上千 token。但 Agent 场景往往不是一次检索就完事——多轮工具调用之后，上下文里堆着几十个碎片，其中大半和最终答案无关。模型要在噪声里找信号，注意力被稀释，幻觉率跟着上升。

**第二个问题是"chunk 视角"天生看不全文档。** 制度类、产品说明书类文档，答案经常横跨多个章节——"这个产品的风险揭示"分散在风险条款、费率、流动性三个地方。按 chunk 检索，每块都只命中一半，模型把它们拼起来时容易拼错顺序、拼错前提。

**第三个问题最隐蔽：检索器和文档结构互相不知道对方的存在。** 我们明明知道"这份 PDF 有 12 页，风险揭示在第 5 页"，但检索返回的 chunk 没有任何结构信息，模型只能盲猜"这段内容来自文档哪个部分"，引用溯源也就无从精确做起。

总结成一句话：**我们把"检索"做成了"把可能相关的东西全部塞给模型"，而模型真正需要的是"只把刚好相关的那一小段给我"。**

## 尝试：先试着在提示词里修

第一反应是省事的做法：在系统提示词里加约束——"优先检索概要类内容""不要过度检索""引用时说明来源章节"。

效果几乎为零。这不是模型不听话，而是**接口根本没有给它"克制"的能力**：工具只有一种调用方式（全文检索），模型没有别的选择，提示词写得再好，它也只能反复调同一个粗粒度工具。

这次失败给了我们一个重要启发：**能用接口结构保证的行为，就不要指望提示词。** 提示词是建议，接口是物理约束。

## 怎么解决的：把"一次检索"拆成三级台阶

借鉴"先看目录、按需打开"的思路（这套思路和 Claude 的记忆文件系统是同源的），我们把一个大检索工具拆成了三个小 MCP 工具，构成一条从便宜到昂贵的渐进链路：

```
file_search（搜文件，只查元数据） → file_outline（看大纲，结构感知） → file_read（读文件，按定位直读片段）
```

核心思想一句话：**先用最便宜的手段把候选缩到最小，再逐层打开，最后才读真正相关的内容——让模型永远不把无关内容读进上下文。**

### 第一级：file_search——只搜"抽屉标签"，不碰正文

`file_search` 只在元数据层检索（标题、摘要、别名、分类），完全不读正文。返回的是一份"候选清单"：

```jsonc
{
  "file_id": "...",
  "title": "XX 产品说明书",
  "summary": "含费率结构与风险等级揭示",   // 一句话摘要
  "category": "prospectus",
  "size_bytes": 102400,
  "structured": true                     // 预标记：有没有结构可导航
}
```

这里有个容易被低估的设计点：**summary 的质量决定了整条链路的效率**。模型靠这一句话判断"要不要打开这个文件"，所以摘要必须写成有检索价值的形态——"订单服务的幂等和重试"远比"订单模块"有用。这一级几乎不花上下文预算，却能把候选从"全库"缩到"一两个文件"。

### 第二级：file_outline——返回的不是目录，是"带指针的地图"

这是整个方案里最核心、也最难的一环。我们一开始的版本只返回标题列表，模型拿到后还是不知道"风险揭示在文档的哪里"——**没有位置指针的大纲只是目录，没法导航。**

所以 `file_outline` 返回的是层级 + 位置指针：

```jsonc
{
  "status": "structured",
  "headings": [
    { "level": 1, "title": "风险揭示", "page": 5, "start_char": 12345, "char_len": 2000 }
  ]
}
```

位置指针用 **page + start_char 双保险**：PDF 按页跳，纯文本按字符偏移跳。

另外一个关键设计是 status 三态，让大纲层学会"知难而退"：

- `structured`：有清晰层级，`file_read` 按位置指针跳转；
- `flat`：有文本但推断不出层级（纯文本、表格堆叠），退回全文读取；
- `skip`：文档太短（比如不到 2000 字），直接 `file_read` 全文，**省掉一跳**。

这个自适应规则很重要——渐进式披露不是死板的流程，短文档硬要走三步反而是浪费。判断依据是字数和结构复杂度的阈值，运行时动态决定。

### 第三级：file_read——按指针直读，读完即引用

`file_read` 接收 `file_id + page/start_char`，直读那一小段正文，并返回 `source/page/start_char`。这直接解决了溯源问题：答案可以绑定到"文档→章节→页码"三级坐标，审计时一眼可查。

## 大纲是怎么长出来的：一条"先免费后昂贵"的降级链

`file_outline` 的实现是我们花时间最多的部分。我们的原则是：**先试"免费且精确"的原生结构，解析不到才降级到推断，实在不行才动用 LLM。**

```
Markdown 标题正则 → DOCX 标题样式 → PDF 内嵌书签(get_toc)
→ 字体字号推断 → (扫描件) MinerU/OCR → LLM 兜底
```

- **Markdown**：正则解析 `^#{1,6}` 标题，最简单；
- **DOCX**：读 Word 的 Heading 样式（前提是作者用了样式，没用的走大纲级别字段）；
- **PDF 有书签**（Word/LaTeX 导出的通常都有）：`doc.get_toc()` 一条命令拿到精确大纲加页码，最准；
- **PDF 无书签但有文本**：按字体字号推断——"字号大于正文阈值或加粗 = 标题"，用阈值分级 H1/H2/H3。这是启发式，但覆盖了大量"生 PDF"；
- **扫描件**：先用 MinerU 做版面分析加 OCR，输出结构化 Markdown 再走第一级；
- **实在没结构**：把文本喂给 LLM 返回结构化大纲 JSON——最贵，所以放最后。

每一级解析器输出统一为 `{level, title, page, start_char, char_len}`，上层完全不用关心下面走的是哪条路径。

落地时我们没有贪心：P0 只做 Markdown、DOCX、PDF 书签三类——它们覆盖了大部分结构化的制度和产品文档，且最准、最好做；字体推断放 P1，OCR 和 LLM 兜底放 P2 作降级。**把免费路径做扎实，比把昂贵路径做花哨更有价值。**

## 权衡：省下的上下文 vs 多花的一次调用

三步链路比一次大检索多了调用次数，这笔账我们认真算过：

**代价端**：每级一次工具调用，多 1~2 轮推理延迟。但第一级（file_search）返回的只有元数据，每条几百字节，上下文成本可忽略；只有最终 `file_read` 把正文读进上下文——而那正是我们本来就要读的部分。

**收益端**：无关 chunk 不再进入上下文。粗粒度大检索的 top-10 里往往七成是噪声，渐进式披露把这些噪声从"占着上下文"变成"只占一条文件标题"。

**误检的处置**：如果第一级就搜错了文件，模型会在第二级（看大纲）就发现"这份文档没有我 要的章节"，成本只有一次大纲调用，可以回头重搜——错误在大纲层被发现和纠正，远比在生成层被发现便宜。搜不到就澄清，读不到就转人工，复用现有的 handoff 通道，不让低置信的答案硬撑。

这套权衡能成立的前提是**权限和分库预筛放在最前面**：`file_search` 只在该问题对应的库/分类内搜，这是第一道过滤也是权限边界；每个 MCP 都校验 RBAC 权限码和 KnowledgeScope，`file_read` 返回内容前还要二次校验文件权限——无权的文件，搜不到也读不到。三个工具全部只读，不碰任何写操作。

## 为什么是三个工具，不是一个工具带三个参数

有人问过：把 `file_search`、`file_outline`、`file_read` 合成一个工具，用 `mode` 参数区分，不是更省工具位吗？

我们的答案是否定的，理由有三层：

1. **接口顺序天然强制流程**。三个独立工具的依赖关系（必须先 search 拿到 file_id，才能 outline；先 outline 拿到位置，才能精准 read）写在工具签名里，模型想跳步都跳不了。合成一个工具，"先查目录再读"就退化成了提示词里的建议——而我们已经验证过，建议靠不住。
2. **职责单一让每个工具都可独立测试和替换**。大纲生成的降级链迭代了很多轮，如果它和大检索耦在一个工具里，每次改动都要回归整条链路。
3. **成本可观测**。每个工具的调用次数就是每一级披露的流量指标——如果 `file_read` 的调用次数远高于 `file_outline`，说明大纲层没起到筛的作用，该去修大纲质量。合成一个工具，这层观测就糊掉了。

## 与既有体系的衔接

这套方案不是空中楼阁，它复用了我们已有的底座：`KnowledgeScope`（分库预筛+权限）、`knowledge_document/version/chunk`（文件元数据与版本）。`file_outline` 从文档原始文件实时生成，不依赖预存 chunk——意味着切分策略的调整不影响大纲链路。

它和 NL2SQL 那边的设计其实是同一个原则的两次出现：数据目录对 Schema 做渐进式召回，文件系统对正文做渐进式披露——**先目录、按需加载，永远不让模型一次看到全部**。

## 教训

1. **提示词管不住行为，接口才管得住。** "先看目录再读"写在提示词里是一句建议，拆成三个有依赖关系的工具就是一条物理约束——能把流程编码进接口的，就不要编码进 prompt。
2. **位置指针是导航的灵魂。** 没有页码和字符偏移的大纲只是装饰；做结构感知时，第一件事就是把"每个标题在哪里"钉死。
3. **便宜的路径要优先做扎实。** 原生结构（Markdown 标题、DOCX 样式、PDF 书签）免费又精确，LLM 兜底是最后手段——降级链的顺序就是成本曲线的形状。
4. **拆分不是目的，可观测才是。** 三个小工具让每一级披露的效率都能被单独测量和优化；大工具的"简单"，代价是整条链路变成黑盒。
