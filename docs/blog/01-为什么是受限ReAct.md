# 为什么我们从"全自动多 Agent"退到了受限 ReAct

## 碰到的问题：越自由，越不敢上线

我们做的是一个财富管理场景的客服 Agent 系统。立项的时候，团队里最诱人的构想是那张经典的架构图：一个中央 Supervisor，周围一圈专家 Agent，模型自主规划、自主选工具、自主协作，看起来无所不能。

但这个系统要动的是钱。转账、赎回、下单、风控处置，每一样都有合规要求：可预测、可复现、可审批、可审计、可回滚。而自由 ReAct 的本质恰恰是"运行时才决定下一步做什么"——它没法提前承诺这五件事。

我们最初的方案确实是奔着"全自动多 Agent 自由协作"去的，很快就发现三个绕不过去的坎：

1. **无限循环**。模型会陷入"检索→不满意→换个说法再检索"的循环，没有机制叫停。
2. **工具越权**。只要工具列表里有写操作的接口，模型总有概率在错误的时机调用它——哪怕概率只有千分之一，在金融场景就是事故。
3. **成本不可控**。每一轮推理都是真金白银的 token，没有预算上限的 Agent 就是一张没有额度的信用卡。

于是我们退了一步，问了一个更根本的问题：**模型到底需要多大的自由度，才能把活干好？**

## 尝试与被证伪的假设

### 假设一："给模型更大的自由度，效果会更好"——证伪

我们复盘了客服场景的真实问题。典型的多跳检索长这样：

```
检索政策 → 发现缺少适用条件 → 补充检索产品说明
→ 结合客户只读事实 → 回答并提供证据
```

这种场景确实**需要**迭代：单步路由覆盖不了。但需要的迭代量是多少？我们数了一下：绝大多数知识类问题，一次检索不够、两次检索加一次查询精炼就够了。三轮以上还没收敛的，基本是问题本身有问题——该澄清或者转人工，而不是让模型继续烧 token。

也就是说，我们不需要"无限自由"，我们只需要"有预算的几次尝试"。自由 ReAct 是被想象出来的需求，不是被真实问题逼出来的需求。

### 假设二："权限校验放在路由之后就行"——证伪

早期的思路是：先让规划器自由地决定该调哪个 Agent，然后在执行入口做权限校验，拦住越权的。

这个方案的问题不在"拦不住"，而在"解释不了"。审计同学会问你：为什么这个请求没有调用 RiskAgent？你只能说"因为权限校验把它拦了"——但规划器为什么会产生这个调用意图？这一步在权限体系之外，是一笔糊涂账。

更糟的是浪费：规划器兴冲冲地拆出了一堆任务，一半在执行层被权限拒绝，前面所有的推理和拆分都是白干的。

## 怎么解决的：权限先于路由

最终我们确立的流水线是：

```
用户请求
→ 权限与能力筛选（AgentCapabilityRegistry）
→ 轻量意图规划（CustomerIntentPlanner）
→ 受控任务路由与执行
→ 统一结果、审计、事件与人工接管
```

关键变化是顺序：**先按用户角色算出 available_agents / denied_agents，规划器只在可用 Agent 白名单里做语义路由**。这带来三个直接收益：

- 无效调用显著减少——被权限排除的 Agent 根本不会进入候选；
- 内部 Agent 不会暴露给不该看到的用户；
- 审计可以正面回答"为什么没有调用某个 Agent"——因为它一开始就不在白名单里，而不是"调了被拦了"。

权限决策集中在入口一处，而不是散落在每个执行器里各拦各的。

## 分层执行：不是所有任务都配拥有 ReAct

下一步是回答"哪些任务可以给模型推理自由，哪些必须走确定性流程"。我们给每个任务显式打了 `execution_mode` 标记，分成三类：

- **bounded_react**：低风险、只读、需要多跳检索的知识问答。给预算、给白名单、必须带证据。
- **controlled_workflow**：资金、订单、风控处置、权限修改。走状态机：权限→参数→规则→风控检查→确认/审批→幂等→审计，模型在其中的角色只是理解和解释。
- **Plan + Rules**：适当性判断、风险分级这类"结论必须可解释"的场景。模型只负责组织证据，最终结论由规则/评分服务输出。

映射规则很朴素：知识问答、政策、流程、FAQ 走 bounded_react；凡是碰资产、订单、工单、权限的，一律 controlled_workflow。

### 受限 ReAct 长什么样

落到 `CustomerTaskExecutor` 的知识类意图里，我们的受限 ReAct 是这样的：

```
retrieve（只读知识检索）
→ observe（只保留工具结果状态与 evidence 摘要）
→ 仅当 low_confidence 时，最多精炼一次查询
→ retrieve
→ answer / clarification / handoff
```

约束清单：最大 20 轮、最大 6 次工具调用、工具白名单只有 `search_customer_knowledge`、默认只读、必须产出 evidence、失败时澄清或转人工。

有一个细节我们纠结过：**审计要不要记录模型的思维链？** 最后决定不记。审计只记任务 ID、意图、结果状态、工具名、调用次数这类受控字段，不记用户原始问题、检索内容、私有推理文本。这是金融场景的最小化审计原则——审计要能回答"系统做了什么"，不需要偷看"模型在想什么"。

顺带说一个后续踩的坑：`overall_status` 状态机只表达"完成度"不表达"一致性"。两个子任务都成功、但答案互相矛盾（一个说"您有风险限制"、一个说"未显示风险限制"）的情况，状态机照样判 `completed`。这是维度缺失，不是判定错误——但它提醒我们，"成功"本身也需要被审视。

## 双管线拆分：一次架构层面的纠错

受限 ReAct 上线后，我们迎来了另一类问题——不是模型不够聪明，而是**两种身份的用户共用了一条管线**。

后台"Agent 控制台"（员工/投顾/管理员）最初直接复用客户侧的执行管线，产生了四类真实缺陷：

- 员工查客户数据，被回答"知识库没有足够依据，转人工"——因为员工请求被接进了客户向的客服兜底，这个兜底语义只对真人客户成立；
- 员工问"我的资产"，系统按"当前登录者=客户"执行，员工用本人 id 去查客户持仓，当然查不到；
- 已批准的数据分析模板跑不起来——模板的 `user_id` 绑定的是授权主体范围，超管的主体范围为空时回退成了管理员自己的 id，查了个空；
- 员工查询把结果写进了"员工=客户"的记忆桶，污染了客户档案的归属。

看到第四条的时候我们意识到：这不是某句输入没处理好，是**架构缺陷**。"员工向"和"客户向"的意图、兜底、记忆语义完全不同，却共用同一条"意图→执行→兜底→记忆"管线。

我们讨论过小修方案：员工调用时禁用转人工和建工单。改动小，但共线不变，记忆和兜底语义继续混用，以后每加一个功能都会重新漏一次。最终决定拆双管线：

- **客户向**：入口是智能客服，兜底是"知识库不足→转人工/建工单"（对真人客户合理），记忆写客户本人；
- **员工向**：登录者永远是员工，查询主体是 `target_customer`（被服务的授权客户），意图只保留数据分析、代客下单草稿、查授权客户资产等少数几类，兜底是明确返回"不支持"——**不接客服知识库、不建工单、不转人工**；记忆默认零写入。

拆完之后有个意外收获：因为员工向的记忆是"只读被服务客户的共享档案"，我们被迫把"谁可以写客户记忆"这件事第一次认真定义清楚——只有客户亲口自述的偏好才能由客服侧代为写入，员工随手做的分析探针绝不落库。

## 子代理并行：受控的并行才有意义

性能上我们遇到了另一个诱惑：子任务串行太慢，是不是可以让多个 LLM 子代理并行跑？

实测给了我们答案。3 个独立的知识检索子任务：串行 8969ms，并行（max_concurrent=3）2469ms，降低 72.5%。收益是真实的——**但只对"只读分析"类任务成立**。

我们列了一张并行边界矩阵：风控事实分析、产品解释、RAG 多路检索、只读画像分析可以并行；订单创建、资金操作、风控最终结论、跨客户聚合写回，绝不并行——它们必须走确定性状态机。一句话：**并行的是"分析"，不是"决策权"。**

即便在可并行的范围内，落地时也踩了一串坑，每一条都有实测依据：

1. **不能采信模型自报的并行性**。实测中模型在"先查限制再解释"的用例上，正确填了 `depends_on`，却把 mode 写成了 parallel。如果只信 mode，有依赖的子任务会被并发跑，结果就是错的。规则改为：**模式以 `depends_on` 为准**。
2. **串行模式必须拓扑排序下发**。`Semaphore` 只限流不排序，而模型返回的任务列表可能是倒序的。
3. **知识类子任务必须接答案生成器**。工具返回的是"引用 + 占位串"，不接生成器会得到"状态 success、内容为空"的假成功。
4. **超时预算按真实工作量定**。知识类子任务=检索+生成，实测 11.5 秒，初版设的 8 秒必然超时——超时预算不是拍脑袋，是测量出来的。
5. **并行子任务不注入前序事实**。互不依赖的任务注入上下文只会引入非确定性。

安全性上我们做了物理层保证：子代理只暴露一个 `dispatch_read_tasks` 工具，capability 值域直接取自只读能力枚举——模型**物理上无法**编造一个写操作的能力名。安全验证也确认：模型返回 `create_order`、`transfer_money` 时不会发生任何对应的工具调用；`customer_id` 由服务端注入并覆盖模型提供的值，防止越权读他人数据。

融合也是确定性的：多个子代理结论冲突时不用"多数票"，标注冲突交人工或确定性规则裁决。业务事实结论一律以确定性 Service 为准。

## 为什么这么选

回头看这一路，所有决策其实都指向同一条原则：**理解层的自由度可以有预算地放开，执行层的闸门绝对锁死**。模型可以优化"怎么理解问题"，但永远改不了"能不能执行某个操作"。

权限先于路由，是因为权限是执行的先决条件，不是执行的补丁；受限 ReAct 而非自由 ReAct，是因为真实需求的迭代深度是可测量的（3 轮够了）；双管线拆分，是因为身份语义是架构级的差异，不是输入级的差异；受控并行，是因为并行的收益来自"读的并发"，而风险全部集中在"写的时序"——把两者切开，就两全了。

## 教训

1. **自由度是成本，不是默认配置。** 给模型多少自主权，应该由真实问题的迭代深度测量出来，而不是由架构图的审美决定。
2. **权限校验放在路由之前，不只是安全，更是可解释性。** "为什么没调" 比 "调了被拦" 好回答得多——审计问题要在设计阶段回答，不要留给运行时。
3. **共用管线是最隐蔽的架构债。** 两种身份语义共用一条管线，每个新功能都会在接缝处漏一次；小修兜不住，拆分才是终点。
4. **模型自己报告的信息（mode、参数、意图）都不能单独采信。** 用结构化的、由代码生成的字段（depends_on、服务端注入的 customer_id、enum capability）做权威，把模型的话当成参考。
